For infrastructure teams

One list of pending updates for every operating system you run

Most infrastructure teams patch a mixed fleet with a tool per operating system: one for Windows, another for each Linux family, something for the Macs, and a shell loop for the BSDs. SysManage puts the inventory and the pending updates for all of them in one console, holds changes for the maintenance window, and records who did what in the audit log. The free Community edition does all of that.

A tool per operating system, for the two jobs you do every week

Inventory and patching are the work that never stops. When each platform has its own tool, the same question -- what is pending, where, and did it go in -- has to be asked several times and the answers stitched together by hand.

🗂️

Inventory in several places

Hardware, software and certificates live in a different console for each platform, so no single list says what you run.

🩹

Patching on several schedules

Each tool has its own idea of a maintenance window, so keeping changes out of business hours means configuring the same rule several times.

📋

Proof assembled by hand

When someone asks whether last week's security updates went in, the answer is an export from every tool, merged in a spreadsheet.

🐡

The BSDs left out

Endpoint-management products such as Intune, Landscape, Satellite and Jamf do not manage FreeBSD, OpenBSD or NetBSD, so those hosts are often patched by hand.

Monday, 9:04

An example week with SysManage. Every step below works in the free Community edition unless it says otherwise.

  • 9:04 -- see it. Open Patching > Updates: pending updates from Windows, Linux, macOS and the BSDs in one list, security updates first, with the package manager for each.
  • 9:10 -- hold it. Select the security updates and apply them. Hosts covered by a maintenance window hold the command until the window opens, so nothing installs during business hours.
  • Tuesday, 02:00 -- apply it. The window opens, the held updates go out, and each host reports what installed, what failed, and whether it needs a reboot.
  • Tuesday, 9:00 -- prove it. The audit log records who queued which update on which host, and when, one entry per package per host.
  • Going further. Knowing which of those updates close a CVE, and scheduled PDF and HTML reports, are Professional. Rolling one change across a whole fleet in waves with fleet jobs is Enterprise. See pricing.

Updates are applied on the Debian, Ubuntu, RHEL and Fedora families, Windows, macOS (Homebrew), FreeBSD and OpenBSD's base system. On openSUSE, Arch and NetBSD they are detected but not yet applied. The supported platforms page has the details.

What the free Community edition already does

Community is open source under the AGPLv3, with no limit on hosts. What each capability does differs by operating system; the supported platforms page lists every difference.

🖥️

Inventory

Hardware, operating system, software and certificates on Linux, Windows, macOS, FreeBSD, OpenBSD and NetBSD, kept current by an agent that reports changes as they happen.

📦

Updates

Detect and apply updates through each platform's own package tools. Applying is not yet available on openSUSE, Arch and NetBSD, and OpenBSD third-party package updates are not detected. Details.

⬆️

OS upgrades

Operating system version upgrades on Windows, macOS, FreeBSD and OpenBSD, and on Ubuntu, Fedora and openSUSE among the Linux distributions. Not yet on NetBSD. Details.

🕑

Maintenance windows

Allowed windows, blackouts and audited emergency overrides, per host or per tag. The server holds changes until a window opens, so they work the same way for every operating system.

⌨️

Scripts

Run scripts and commands on hosts of every supported operating system from the same console, with each host's output returned to you.

📝

Audit log

Host approvals, package installations, update runs and other changes recorded with who did it and when -- the record you point to when someone asks whether the patch went in.
