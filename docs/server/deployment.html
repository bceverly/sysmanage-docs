Deployment Guide

Production deployment strategies and best practices for scalable, secure, and reliable SysManage infrastructure.

Deployment Overview

Every SysManage deployment is the native server package on a host you control: a physical machine, a virtual machine or a cloud instance. SysManage does not publish container images. What varies is where the database lives and how many sites you run.

Single Server Deployment

The supported topology, from a handful of hosts to tens of thousands. The Scaling Guide has the measured numbers.

  • One server runs the API, the web interface and the agent connections, with several worker processes
  • PostgreSQL on the same host, or on its own machine for large fleets
  • Simple configuration and maintenance

Highly Available Database

One SysManage server against a PostgreSQL cluster that fails over

  • The server rides through a database primary failover on its own
  • Works with Patroni, streaming replication or a managed cloud database

Several Sites

A server at each site, coordinated by Multi-Site Federation (Professional+ Enterprise)

  • Each site keeps working if the link to the coordinator is lost

Several SysManage servers behind a load balancer are not supported yet. An agent holds one connection to one server, and parts of the server assume they are the only instance. Server high availability is planned for ROADMAP Phase 34; until then, protect the server with backups and a highly available database.

All of the configurations above are single-tenant deployments and cover the vast majority of installations. SysManage can also run as an opt-in multi-tenant SaaS control plane that hosts isolated tenants in separate databases -- an advanced mode that is disabled by default and does not affect single-tenant, on-prem, or federated installs. See the Deploying Multi-Tenancy guide.

Installation Steps

# 1. Install the server from the Launchpad PPA, with a local PostgreSQL
sudo add-apt-repository ppa:bceverly/sysmanage
sudo apt update
sudo apt install sysmanage postgresql

# 2. Create the database
sudo -u postgres createuser sysmanage
sudo -u postgres createdb sysmanage -O sysmanage
sudo -u postgres psql -c "ALTER USER sysmanage WITH PASSWORD 'choose-a-strong-password';"

# 3. Set the database password and admin_userid
sudo vim /etc/sysmanage.yaml

# 4. Create the database schema
sudo sysmanage-migrate

# 5. Install the TLS certificate (see the installation guide), then start
sudo systemctl start sysmanage
sudo systemctl restart nginx

The Server Installation Guide covers every step in detail, including the TLS certificate, the firewall and the packages for other platforms.

Database High Availability

Database HA is a first-class, tested capability.

The SysManage server runs against a highly-available PostgreSQL cluster and survives a primary failover with no manual intervention -- a stable read-write endpoint (libpq multi-host DSN or a VIP/proxy), connection pre-ping and recycling, bounded promotion-gap retry, and a database-aware readiness endpoint. The connection-endpoint strategy, exactly what the server does during a failover, the OpenBAO consideration for multi-tenant deployments, and a fully-automated local failover test rig are documented in PostgreSQL High Availability, which is the reference for this setup.

Monitoring & Logging

System Monitoring

Prometheus Configuration

With telemetry enabled (telemetry: enabled: true in /etc/sysmanage.yaml), the server serves Prometheus metrics on 127.0.0.1:9090, on loopback only. Scrape it from a Prometheus on the same host, or forward the metrics with an OpenTelemetry collector.

# prometheus.yml (Prometheus on the SysManage host)
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'sysmanage'
    static_configs:
      - targets: ['127.0.0.1:9090']

Health Check Endpoint

# Is the server up?
curl https://sysmanage.example.com/api/health
{"status":"healthy"}

# Is the database reachable too?
curl https://sysmanage.example.com/api/health/db

Log Management

The server writes /var/log/sysmanage/backend.log and rotates it itself, once a day, compressing old files and keeping 14 days. No logrotate rule is needed. Its output also goes to the systemd journal, which your log shipper can forward:

sudo journalctl -u sysmanage -f
sudo tail -f /var/log/sysmanage/backend.log

Backup & Disaster Recovery

Database Backup

#!/bin/sh
# /usr/local/bin/backup_sysmanage.sh

BACKUP_DIR="/backup/sysmanage"
DATE=$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"

# Database backup
sudo -u postgres pg_dump sysmanage | gzip > "$BACKUP_DIR/db_backup_$DATE.sql.gz"

# Configuration, certificates and OpenBAO unseal material
tar -czf "$BACKUP_DIR/config_backup_$DATE.tar.gz" \
  /etc/sysmanage.yaml /etc/sysmanage/ /var/lib/openbao/init.json

# Keep only last 30 days
find "$BACKUP_DIR" -name "*.gz" -mtime +30 -delete

# Cron entry: 0 2 * * * /usr/local/bin/backup_sysmanage.sh

Copy the backups, and above all /var/lib/openbao/init.json, to storage off this machine. See Backup for restoring a server.

Disaster Recovery Plan

  1. Assessment: Determine scope of failure and affected systems
  2. Communication: Notify stakeholders and users of the incident
  3. Isolation: Isolate failed components to prevent further damage
  4. Recovery: Reinstall the package on a host with the same name, restore the configuration and the database, and start the server; agents reconnect on their own
  5. Verification: Test restored systems and verify functionality
  6. Post-mortem: Document incident and improve procedures

Performance Optimization

Database Tuning

# PostgreSQL optimization settings
# postgresql.conf

# Memory settings
shared_buffers = 256MB                  # 25% of RAM
effective_cache_size = 1GB              # 75% of RAM
work_mem = 4MB
maintenance_work_mem = 64MB

# Checkpoint settings
checkpoint_completion_target = 0.9
wal_buffers = 16MB
default_statistics_target = 100

# Query optimization
random_page_cost = 1.1                  # For SSD storage
effective_io_concurrency = 200          # For SSD storage

Size max_connections from the server's workers and pools, as the Scaling Guide describes.

Application Tuning

The server picks its worker count for the machine it runs on. To choose it yourself, set api.workers in /etc/sysmanage.yaml and restart the service. Keep to about 2,500 agents per worker. Leave api.host on localhost: nginx terminates TLS and is the only listener on the network.

Security Hardening

Network Security

# Firewall rules (ufw example)
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow ssh
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow from 10.0.1.0/24 to any port 5432  # Only if PostgreSQL serves other hosts
sudo ufw enable

Application Security

  • HTTPS Only: Enforce TLS for all connections
  • HSTS: HTTP Strict Transport Security headers
  • CSP: Content Security Policy implementation
  • Rate Limiting: API endpoint rate limiting
  • Input Validation: Comprehensive input sanitization
  • Audit Logging: Log all administrative actions

Maintenance & Updates

Update Procedure

  1. Backup: Create full system backup before updates
  2. Testing: Test updates in staging environment
  3. Maintenance Window: Schedule maintenance with user notification
  4. Update: Upgrade the package (sudo apt upgrade on Ubuntu), then run sudo sysmanage-migrate and restart the service
  5. Verification: Verify all systems function correctly
  6. Rollback Plan: Have rollback procedures ready if needed

Maintenance Tasks

Daily

  • Monitor system health and performance
  • Review application logs for errors
  • Verify backup completion

Weekly

  • Review security logs and alerts
  • Update system packages
  • Test backup restoration procedures

Monthly

  • Security vulnerability assessment
  • Performance analysis and optimization
  • Capacity planning review
