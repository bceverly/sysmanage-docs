Scaling Guide

How many agents one SysManage server carries, what to give it, and what to change as the fleet grows. Every number here was measured, not estimated, unless it says otherwise.

What Was Measured

The numbers come from the scale harness in the server's source tree (tests/load): simulated agents that behave like the real agent, run from other machines, against a server and PostgreSQL on a machine of their own. The hardest case was chosen: the server restarts while every agent is connected, so the whole fleet reconnects and reports at once.

A run passes when every agent reconnects, no queued message expires, no agent is locked out or pushed to HTTP polling, and no host is marked down because of the outage.

Agents Tenants Server machine Workers 95% reconnected Heartbeat p95 Queue peak Marked down
10,000 1 8-core laptop auto 195 s 1.2 s 51,732 0
10,000 20 12-thread desktop 9 115 s 1.1 s 21,154 6*
20,000 20 12-thread desktop 9 230 s 1.6 s 141,424 2
30,000 20 12-thread desktop 6 93% by the end 4.1 s 208,299 550

* Caused by a registration fault fixed in the same release (a lost registration reply left the agent without its credential).

Every run worked through every queued message and lost none, and none locked an agent out or pushed it to polling. At 30,000 agents with six workers each worker ran at about 85% of a core: reconnects and heartbeats were answered late, so some agents had not reconnected when the run ended and 550 hosts were marked down. More workers would have needed more memory than that machine had.

Sizing the Server

Plan about 3 CPU cores and 4 GB of memory for the server per 10,000 agents, plus the database. Measured: 2.7 cores at 10,000 agents and 4.5 at 20,000 (averages over a restart storm), and 1 GB of memory per worker at about 2,200 agents per worker.

PostgreSQL used about 10 GB of memory at 20,000 agents in 20 tenants on the same machine. Give it its own machine past roughly 20,000 agents, and size its max_connections as described below.

Workers set how much of the machine the server uses: each one serves its agents from one event loop on one core. Keep it to about 2,500 agents per worker; the runs at 1,100 and 2,200 agents per worker kept up, the run at 5,000 per worker did not. The server picks the count for its machine (one per CPU, minus a quarter for PostgreSQL and the operating system, at most one per GB of memory beyond 2 GB, at most 16); set api.workers in sysmanage.yaml to choose it yourself. See Configuration for the pool and worker settings.

50,000 agents on one server has not been measured yet; by the numbers above it needs about 14 server cores and a separate database machine. The measurement is planned, and this guide will carry its result.

Database Connections

Every worker keeps its own connection pools. PostgreSQL's max_connections must hold them all, plus 10 kept free for everything else:

max_connections >= workers x (size + max_overflow)
                + workers x tenants x (tenant_size + tenant_max_overflow)
                + 10

Without multi-tenancy only the first term applies. With the defaults on a 12-thread machine (9 workers, a pool of 32 plus 32 overflow, 20 tenants at 2 plus 6), that is about 2,000 connections: set max_connections to 2,500 and restart PostgreSQL.

If the connections do not fit, the server does not refuse to start: it shrinks the pools to fit and logs a warning that names the numbers. With multi-tenancy the main pool then keeps at most half of each worker's share and the tenant databases share the rest, at least one connection each. A server squeezed that way works, slowly: one run with one connection per tenant database per worker took 26 minutes to enroll 10,000 agents. Raise max_connections rather than live with the warning.

A tenant database can live on another PostgreSQL server (its placement), which takes its connections off the main one. A transaction-mode connection pooler such as PgBouncer is not supported: the server holds session-level advisory locks to coordinate its workers.

After a Server Restart

When the server comes back, every agent reconnects within a few minutes and sends its reports. What to expect, and what keeps it orderly:

  • A queue peak of up to about 7 messages per agent (141,000 at 20,000 agents), worked through in about 15 minutes at 20,000 agents. Nothing is lost while it drains.
  • Spread first reports. A busy server asks each reconnecting agent to spread its first reports over a window sized to the work already queued (initial_report_drain_per_second, initial_report_messages_per_agent, initial_report_max_window_seconds).
  • No false alarms. For the heartbeat timeout plus 8 minutes after it starts (13 minutes by default) the server marks no host down; after that, a host still silent is.
  • Agents behind one address. Connection limits are per registered agent (30 per window) and per address for agents not yet registered (600). A large fleet registering for the first time from behind one NAT address may need a higher per_address.

Fleet-Wide Pushes

A change that reaches every host goes out in waves, so a large fleet is never asked to do the same thing in the same minute:

  • Antivirus deployment (automatic deployment, or a new version of the deployment plan): at most 250 hosts per database every 5 minutes, about 3,000 an hour. Each host also waits its own share of 5 minutes before its first signature download.
  • Package catalogs: each host is asked about once a day, at most 500 per database an hour. A host that has not answered is not asked again for 6 hours, so hosts that never answer cannot hold up the rest.
  • Scheduled configuration for more than 50 hosts runs as a fleet job, at the job's concurrency.

Measured with 2,000 agents: the antivirus wave reached every host exactly once, 250 per pass, while heartbeats were answered within 1 second (95th percentile).

Engine Updates

A Professional+ server checks for engine updates about every 6 hours, at a time of its own, and downloads at most 3 engines at once. A new engine is downloaded, checked and swapped in before the old one is let go: a download that fails, stalls or arrives damaged leaves the installed engine in use, and the next check tries again.

Measured: 40 servers updated through a minute of refused, stalled, damaged and out-of-date downloads, and none was without its engine at any moment.

Federation Sites

Each site syncs with its coordinator every 5 minutes by default, each wait varied by up to a fifth, and its first sync after a start comes within a minute, so sites restarted together do not sync together. After a coordinator outage a site retries after 30 seconds, doubling up to 15 minutes, each wait between half and all of that, so the sites return spread out.

A site sends its host directory in full once a day and after a restart, and in between only the hosts that changed. At 20,000 hosts the full directory is about 6.4 MB.

Checklist

  • Server: about 3 cores and 4 GB per 10,000 agents, at most about 2,500 agents per worker.
  • PostgreSQL: max_connections from the formula above, and its own machine past about 20,000 agents.
  • After a restart, check the server log for "Database pool reduced to fit the server"; if it is there, raise max_connections.
  • Many tenants: count their pools, or place some tenant databases on another PostgreSQL server.
  • Large fleets behind one NAT: raise per_address before they first register.
