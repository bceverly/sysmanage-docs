Server Installation Guide

Install the SysManage server from the package for your platform, then finish the setup in a few short steps. Building from source is only needed for development.

Before You Begin

  • A host with a DNS name. Agents connect to that name, and the TLS certificate must match it.
  • PostgreSQL 12 or newer, on the same host or a remote one. The packages do not create the database for you.
  • Inbound port 443, plus port 80 for the HTTPS redirect and for Let's Encrypt. Nothing else needs to be reachable from the network.
  • Root or sudo access on the host.

You do not need to install Python, Node.js or any build tools yourself. The package brings everything the server needs, including nginx and OpenBAO.

Install from Packages (Recommended)

Ubuntu (Launchpad PPA)

The SysManage server is published in the ppa:bceverly/sysmanage Launchpad PPA for Ubuntu 22.04 LTS, 24.04 LTS and 26.04 LTS. This is the recommended way to run the server.

sudo add-apt-repository ppa:bceverly/sysmanage
sudo apt update
sudo apt install sysmanage

The package installs the server in /opt/sysmanage and downloads its Python dependencies into a private environment there, so the host needs internet access while it installs. It also creates /etc/sysmanage.yaml with secrets generated for this installation, installs and unseals OpenBAO, and configures nginx. The SysManage service is enabled but left stopped until you finish the steps under After Installing.

Later releases arrive through sudo apt upgrade. An upgrade keeps your configuration and database, and prints the two commands to run afterward: the database migrations and a service restart.

Other Platforms

Packages for the other platforms are published on the GitHub releases page and in the repositories below. Replace X.Y.Z with the release you are installing. Every package prints its own post-install instructions, with the paths for that platform already filled in.

Debian 12 and newer install from the SysManage APT repository. Ubuntu can use it too, but the PPA above is the recommended source on Ubuntu.

# Install the archive signing key
sudo install -d -m 0755 /usr/share/keyrings
curl -fsSL https://repo.sysmanage.org/server/sysmanage-archive-keyring.gpg \
  | sudo tee /usr/share/keyrings/sysmanage-archive-keyring.gpg > /dev/null

# Add the repository, verified against that key
echo "deb [signed-by=/usr/share/keyrings/sysmanage-archive-keyring.gpg] https://repo.sysmanage.org/server/deb stable main" \
  | sudo tee /etc/apt/sources.list.d/sysmanage-server.list

sudo apt update
sudo apt install sysmanage

RHEL, Rocky Linux, AlmaLinux, Oracle Linux and CentOS Stream 8, 9 and 10 (x86_64 and aarch64) install from the bceverly/sysmanage Fedora Copr project. Fedora itself is not built for the server at the moment; use Building from Source there.

sudo dnf install epel-release
sudo dnf copr enable bceverly/sysmanage
sudo dnf install sysmanage

openSUSE Leap 15.6 and Tumbleweed install from the openSUSE Build Service project home:bryaneverly. Leap 15.6 tracks the latest release; the Tumbleweed build can trail it.

# openSUSE Leap 15.6
sudo zypper addrepo https://download.opensuse.org/repositories/home:/bryaneverly/15.6/home:bryaneverly.repo

# openSUSE Tumbleweed
sudo zypper addrepo https://download.opensuse.org/repositories/home:/bryaneverly/openSUSE_Tumbleweed/home:bryaneverly.repo

sudo zypper refresh
sudo zypper install sysmanage

Arch Linux installs the sysmanage package from the AUR, with any AUR helper:

yay -S sysmanage

Alpine Linux 3.20, 3.21 and 3.22 packages are direct downloads from the releases page. Pick the file for your Alpine release (alpine320, alpine321 or alpine322) and check its .sha256 before installing.

sha256sum -c sysmanage-X.Y.Z-alpine321.apk.sha256
apk add --allow-untrusted ./sysmanage-X.Y.Z-alpine321.apk

The server is published to the Snap Store in the stable channel, with strict confinement:

sudo snap install sysmanage

Download sysmanage-X.Y.Z-macos.pkg from the releases page and install it. The installer uses Homebrew to add nginx if it is missing.

sudo installer -pkg sysmanage-X.Y.Z-macos.pkg -target /
sudo cp /etc/sysmanage.yaml.example /etc/sysmanage.yaml

After the steps under After Installing, start the server with sudo launchctl load /Library/LaunchDaemons/com.sysmanage.server.plist.

Download sysmanage-X.Y.Z-windows-x64.msi (or sysmanage-X.Y.Z-windows-arm64.msi on ARM) from the releases page and run it as an administrator. It installs the server in C:\Program Files\SysManage Server and registers the SysManageServer, SysManageNginx and SysManageOpenBAO services. nginx is downloaded during the install and its SHA-256 is checked before use.

msiexec /i sysmanage-X.Y.Z-windows-x64.msi

The server is left stopped. After the steps under After Installing, start it from an administrator PowerShell with Set-Service SysManageServer -StartupType Automatic, Start-Service SysManageServer and Restart-Service SysManageNginx.

The server is also published to winget: winget install sysmanage.sysmanage installs the same MSI.

Download sysmanage-X.Y.Z.pkg from the releases page and install it:

sudo pkg add ./sysmanage-X.Y.Z.pkg

Start the services with sysrc sysmanage_enable=YES, sysrc nginx_enable=YES, service sysmanage start and service nginx start.

A pre-built package is published for OpenBSD 7.8 and 7.9. It bundles the backend, the web interface and the Python dependencies, so it needs no compiler. Use openbsd78 or openbsd79 to match your release.

ftp https://github.com/bceverly/sysmanage/releases/download/vX.Y.Z/sysmanage-X.Y.Z-openbsd79.tgz
doas pkg_add sysmanage-X.Y.Z-openbsd79.tgz

Start the services with doas rcctl enable openbao sysmanage and doas rcctl start openbao sysmanage.

Download sysmanage-X.Y.Z-netbsd.tgz and its .sha256 from the releases page, check it, and install it as root:

sha256 -c sysmanage-X.Y.Z-netbsd.tgz.sha256 sysmanage-X.Y.Z-netbsd.tgz
pkg_add sysmanage-X.Y.Z-netbsd.tgz

No internet access on the server? Use the air-gapped installation, which carries every package and dependency on one bundle.

After Installing

These steps are written for Ubuntu and Debian. They are the same on every platform; only the paths and the service commands differ, and the table at the end of this section lists the paths for each one.

Step 1: Create the Database

To use a local PostgreSQL server, install it and create the sysmanage user and database. Choose a strong password; you will put it in the configuration file next.

sudo apt install postgresql
sudo -u postgres createuser sysmanage
sudo -u postgres createdb sysmanage -O sysmanage
sudo -u postgres psql -c "ALTER USER sysmanage WITH PASSWORD 'choose-a-strong-password';"

A remote PostgreSQL server works just as well. Create the same user and database there and use its host name in the configuration.

Step 2: Edit the Configuration

The package created /etc/sysmanage.yaml and already generated this installation's jwt_secret, password_salt and recovery admin_password. Set the database password, and set admin_userid to your own email address:

sudo vim /etc/sysmanage.yaml
registry:
  user: "sysmanage"
  password: "choose-a-strong-password"   # the password from step 1
  host: "localhost"                      # or your remote PostgreSQL host
  port: 5432
  name: "sysmanage"

security:
  admin_userid: "you@example.com"        # must be an email address
  # admin_password was generated at install time; leave it as it is

Leave api: host set to localhost: the server is reached only through nginx. The configuration builder can generate a complete file if you want to set more options, and the Configuration Guide describes every setting.

Step 3: Run the Database Migrations

The migrations create the database schema. --status shows what is pending; the second command applies it. Run the same two commands after every upgrade.

sudo sysmanage-migrate --status
sudo sysmanage-migrate

# Packages without the sysmanage-migrate command (BSD, macOS, older releases):
cd /opt/sysmanage
sudo -u sysmanage .venv/bin/python scripts/sysmanage_migrate.py --status
sudo -u sysmanage .venv/bin/python scripts/sysmanage_migrate.py

Step 4: Install a TLS Certificate

SysManage serves the web interface, the API and the agent connections on port 443, and nginx refuses to start until a certificate is in place. This is deliberate: a management console must never come up in cleartext, and agents verify the certificate by default. By default nginx reads:

/etc/sysmanage/tls/server.crt
/etc/sysmanage/tls/server.key

To use a certificate stored elsewhere, change these two lines in /etc/nginx/sites-available/sysmanage-nginx.conf:

ssl_certificate     /etc/sysmanage/tls/server.crt;
ssl_certificate_key /etc/sysmanage/tls/server.key;

Let's Encrypt with certbot (HTTP challenge)

If port 80 on this host is reachable from the internet, certbot can answer the challenge itself. nginx holds port 80 once it runs, so the hooks stop it during each renewal and start it again afterward. certbot saves the hooks and renews automatically.

sudo apt install certbot
sudo certbot certonly --standalone -d sysmanage.example.com \
  --pre-hook "systemctl stop nginx" --post-hook "systemctl start nginx"

Let's Encrypt with a DNS challenge (DigitalOcean DNS)

If your domain's DNS is hosted at DigitalOcean, certbot can prove ownership through DNS instead. Port 80 does not need to be reachable, and nginx keeps running during renewals. Create a DigitalOcean API token with write access to DNS and store it in a file only root can read:

sudo apt install certbot python3-certbot-dns-digitalocean
sudo mkdir -p /etc/letsencrypt
sudo install -m 600 /dev/null /etc/letsencrypt/digitalocean.ini
sudo vim /etc/letsencrypt/digitalocean.ini
#   dns_digitalocean_token = your-api-token

sudo certbot certonly --dns-digitalocean \
  --dns-digitalocean-credentials /etc/letsencrypt/digitalocean.ini \
  -d sysmanage.example.com \
  --deploy-hook "systemctl reload nginx"

With either method, point the two nginx lines at the files certbot wrote, then check the configuration:

ssl_certificate     /etc/letsencrypt/live/sysmanage.example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/sysmanage.example.com/privkey.pem;
sudo nginx -t

Step 5: Start the Services

sudo systemctl start sysmanage
sudo systemctl restart nginx
sudo systemctl status sysmanage

The server writes its logs to /var/log/sysmanage/. If it stops right after starting, check the database settings in /etc/sysmanage.yaml and confirm the migrations ran.

Step 6: Open the Firewall

nginx is the only service that listens on the network. Open ports 443 and 80 and nothing else: the SysManage API stays on loopback port 8080 and OpenBAO on loopback port 8200, and PostgreSQL should not be exposed either.

# Ubuntu / Debian (ufw)
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp

# RHEL / openSUSE (firewalld)
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --reload

Step 7: Sign In

Open https://sysmanage.example.com/ and sign in as the admin_userid you set, with the generated recovery password. You can read it with:

sudo grep admin_password /etc/sysmanage.yaml

This recovery account lives only in the configuration file, and the console warns you while it is there. Configure email, create your own administrator user, then remove admin_userid and admin_password from the file and restart the server.

Step 8: Back Up the OpenBAO Unseal Material

The package installs OpenBAO, the secrets broker, on loopback port 8200. On first install it initializes and unseals it, unseals it again at every boot, and writes the token SysManage uses to /etc/sysmanage/openbao-token. The unseal key and root token are in /var/lib/openbao/init.json.

Copy /var/lib/openbao/init.json to safe storage off this machine. Without it, the secrets stored in OpenBAO cannot be recovered if the host is rebuilt.

To have SysManage keep its secrets in OpenBAO, set vault: enabled: true in /etc/sysmanage.yaml. Multi-tenancy requires it. Check its state with systemctl status openbao sysmanage-openbao-init.

Step 9: Connect Agents

Agents need outbound port 443 to the server and nothing else. Point each agent at the same host name the certificate was issued for, and leave certificate verification on:

server:
  url: "https://sysmanage.example.com"
  verify_ssl: true

See Agent Installation for the agent packages.

Optional Features

Telemetry

OpenTelemetry is off by default. To send traces and metrics to your collector, set telemetry: enabled: true and telemetry: otlp_endpoint in /etc/sysmanage.yaml, or the environment variables OTEL_ENABLED=true and OTEL_EXPORTER_OTLP_ENDPOINT. While telemetry is on, Prometheus metrics are served on 127.0.0.1:9090, on loopback only.

telemetry:
  enabled: true
  otlp_endpoint: "http://localhost:4317"

Multi-Tenancy

A server runs as a single tenant unless you turn multi-tenancy on with multitenancy: enabled: true, followed by the database migrations. It needs OpenBAO and a separate database for each tenant; see Deploying Multi-Tenancy.

Troubleshooting

After a Package Install

  • nginx will not start: almost always a missing or unreadable certificate. sudo nginx -t names the file it could not read.
  • The service starts, then exits: check the database settings in the configuration file and confirm the migrations ran.
  • Sign-in is rejected: admin_userid must be a full email address, not a bare name.
  • OpenBAO is sealed or not running: run sudo systemctl restart openbao sysmanage-openbao-init and read systemctl status sysmanage-openbao-init.

Database Connection Issues

  • Verify PostgreSQL is running: sudo systemctl status postgresql
  • Check credentials match configuration file

Port Conflicts

  • In production, ensure 443 is free (and 80, which only redirects to it). The backend listens on 127.0.0.1:8080 behind nginx and is not exposed.
  • Check for an existing listener: ss -tlnp | grep -E ':(80|443|8080)'

Building from Source (Development)

Build from source to work on SysManage itself, or on a platform with no package. A development server runs from the source checkout, with the web interface served by Vite instead of nginx. Do not use it for production.

Prerequisites

  • Python 3.10 through 3.14 with its development headers, Node.js 20 or newer, PostgreSQL 12 or newer, a C compiler, and the libffi, OpenSSL and libpq development packages.
  • On FreeBSD, OpenBSD and NetBSD, use gmake instead of make. On NetBSD, set CFLAGS="-I/usr/pkg/include" and LDFLAGS="-L/usr/pkg/lib -Wl,-R/usr/pkg/lib" before installing, so Python packages with C extensions find their libraries.

On Ubuntu:

sudo apt install python3 python3-venv python3-dev python3-pip \
  build-essential libffi-dev libssl-dev libpq-dev libuv1-dev postgresql
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

Clone and Set Up

Install the development tools once (test runners, linters, Playwright and the telemetry stack):

git clone https://github.com/bceverly/sysmanage.git
cd sysmanage
make install-dev

Create a database and user for development, the same way as in Step 1 above.

Create sysmanage-dev.yaml in the project root from sysmanage-dev.yaml.example; the server reads it when /etc/sysmanage.yaml does not exist. Point SYSMANAGE_CONFIG_PATH at a file to use any other. The settings that matter most for development:

cp sysmanage-dev.yaml.example sysmanage-dev.yaml
# then edit it:
dev_mode: true
registry:            # the database (the older name database: also works)
  user: sysmanage
  password: a-local-password
  host: localhost
  port: 5432
  name: sysmanage
  • dev_mode: true tells the server there is no TLS proxy in front of it: links in emails use http://host:3000 and binding to all interfaces is not warned about. Leave it out on a real deployment; an absent flag means production.
  • PostgreSQL behaves like production and is the better choice. For a quick throwaway server, set the database user to sqlite and name to a file path. SQLite ignores database_pool; on PostgreSQL the pool is sized for your workstation automatically.
  • OpenBAO: make start starts a local development OpenBAO alongside the server. To run without it, set vault: enabled: false and put secrets such as jwt_secret directly in the file (development only).
  • Multi-tenancy stays off unless multitenancy: enabled: true; the environment variable SYSMANAGE_MULTITENANCY=false forces it off for a single run.

Run It

Run the migrations, then start and stop everything with:

make migrate     # create or upgrade the database schema
make start       # API + web UI + local OpenBAO
make stop

The API listens on port 8080 and the Vite web UI on port 3000. The database migrations use the same tool operators run in production.

To create an administrator user and initialize OpenBAO in a source checkout, run scripts/sysmanage_secure_installation; see Secure Installation. It rebuilds the database, so never run it against a server with data you want to keep, and never on a package install.

Need a second, disposable server (for example to test something without touching your own data)? The scale harness starts one with its own PostgreSQL container, configuration and port, and deletes it afterwards:

python tests/load/stack.py up      # its own PostgreSQL + server on port 18080
python tests/load/stack.py down    # remove it

Build Problems

  • Missing libpq-fe.h: Install libpq-dev (Ubuntu) or postgresql-devel (RHEL)
  • httptools build errors: Install libuv1-dev (Ubuntu) or libuv-devel (RHEL)
  • NetBSD, "No space left on device" during pip install: /tmp is a 1 GB tmpfs by default. Enlarge it with mount -t tmpfs -o -s=4g tmpfs /tmp, or set TMPDIR to a directory on disk.
