Agent Capabilities

Not every agent can do everything. SysManage asks each agent what it supports, shows you the answer, and refuses to dispatch work an agent cannot run.

Why this exists

SysManage runs on Linux, Windows, macOS and the BSDs, across several processor architectures. Those platforms are not equivalent. Ubuntu Pro exists only on Ubuntu. bhyve is FreeBSD's hypervisor and vmm is OpenBSD's. WSL is a Windows feature. A dependency may have no build for a given architecture at all.

Without a way to express that, a server has two bad options: assume every agent can do everything and let commands fail at the far end, or hide features from everyone because some hosts lack them. Capability advertisement replaces both with a straight answer from each agent.

How an agent decides what to report

The report is derived from the agent's live command table — the set of operations the running build can actually route — rather than from a list maintained by hand. A hand-maintained list drifts the moment a handler is added or removed; a derived one cannot.

Shipping a handler answers "was this code built?", which is not the same as "will it work here". So the agent additionally probes the host at runtime and removes what it cannot deliver: a command whose required tool is not installed, or one that is meaningless on this operating system. Each removal carries a reason code, which the server renders in your language.

Reason codes

  • A required tool is not installed — the code shipped, but the program it drives is absent. Ubuntu Pro management without the pro CLI, for example.
  • Not applicable to this operating system — bhyve off FreeBSD, WSL off Windows.
  • Not built into this agent — the build does not contain the handler at all.

A probe can only ever remove a capability, never add one. That is deliberate: a mistaken probe tells you a feature is unavailable when it would have worked, which is visible and correctable. The opposite error — claiming a capability the agent does not have — is the failure this feature exists to prevent.

The Hosts list carries a Capabilities column so a mixed fleet is visible at a glance, sortable and filterable like any other column.

Full, Limited and Unknown

Three states, not two. Unknown means the host has not reported a capability set — an agent older than this feature, or one that has not yet checked in. It is deliberately distinct from Full: the server will not claim an agent supports everything merely because it has not said otherwise, and it will not light the whole fleet up as Limited during a rollout.

Commands are refused, not attempted

The advertised set is not only informational. When the server is asked to send a command a host has not advertised, it declines before the command is queued and tells you the agent does not support it — instead of dispatching work that fails minutes later somewhere in a log.

A host in the Unknown state is not gated. Refusing work because an agent has not reported yet would break every existing host the moment the feature shipped.

Asking an agent directly

The capability set travels with registration and with routine system-information reports, but those are snapshots. To ask a running agent what it supports right now — when you are working out why an action is unavailable — the server can issue a capabilities query over the existing connection, and the agent answers from the same command table it advertises from. A live answer and a stored one cannot disagree.

This is a request over the connection the agent already opened outbound to the server. The agent still listens on no ports, on any platform.

Compatibility

The report carries a schema version. A server ignores fields it does not recognise from a newer agent rather than rejecting the report, and an agent newer than its server is logged plainly rather than silently treated as unknown forever. Existing agents that predate the feature keep working and simply show as Unknown until they are upgraded.
