How SysManage Is Tested

The server, the web console and the agent each have their own test suite, and continuous integration fails a change that drops coverage below a floor. This page describes the suites as they are in the source trees in November 2026.

The suites

Suite Tool Size Coverage floor
Serverpytestabout 9,600 test functions (9,068 in tests/, 579 in backend/tests/)83% of lines
Web consoleVitestabout 2,400 tests in 233 files80% of lines (79% statements, 69% functions, 63% branches)
Agentpytestabout 5,900 test functions in 277 files75% of lines

Sizes count test functions as written; a parametrized test counts once, although it runs once per case. The floors are set where coverage was measured and raised as it rises, never lowered: the server measured 85.3% against its floor in September 2026 and the console 82.5% in October 2026. The two server trees run as separate pytest processes that add up to one coverage figure, and the floor applies to the total.

Two ways to build a test database

Server tests run against an in-memory SQLite database. The main fixtures (tests/conftest.py) build its schema from the application's own models, so it always matches them. The API tests (tests/api/conftest.py) build theirs from a small hand-maintained copy of the models, kept SQLite-friendly for speed; a new column used by an API test has to be added there as well, and the file says so at the top. A separate test applies every Alembic chain to a real PostgreSQL database, so production's database is exercised too.

Beyond unit tests

  • Browser tests. Playwright drives the real console against a running server (make test-e2e), including page performance checks. Playwright has no build for the BSDs, so there a Selenium suite (make test-ui) covers sign-in, hosts and updates instead.
  • Security tests. A suite checks the server against the MITRE "unforgivable" vulnerability classes (tests/lucky13), and the security targets run Bandit, Semgrep, dependency audits and secret scanning. SonarCloud and CodeQL analyze the code in CI.
  • Migration tests. Migration tests check that a migration applies, downgrades and re-applies, and a lint check refuses destructive changes in an upgrade. See Database Migrations.
  • Load tests. Artillery exercises the REST API and compares each run with recent ones; the scale harness restarts a real server under thousands of simulated agents. See Performance Testing and Performance and Scale.
  • Every platform. The suites run on Linux, macOS and Windows for every push to the main branches and every pull request, and the agent's integration tests run in FreeBSD, OpenBSD and NetBSD virtual machines for each release. See Multi-OS CI/CD.

Running them

make test              # server: Python, TypeScript, browser and load tests
make test-python       # server: both pytest trees, with the coverage floor
make test-typescript   # web console: Vitest, with its floors
make test-e2e          # Playwright against a running server
make test              # (in the agent tree) agent tests, with its floor
