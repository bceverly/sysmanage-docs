Performance Testing

Two quick checks run with the test suites: an Artillery load test of the REST API and Playwright page-load checks in the browser. They catch a change that makes the server or the console slower than it was; they are not a capacity measurement. How many agents one server carries is measured separately, with the scale harness -- see Performance and Scale.

Artillery: the REST API

make test-performance runs artillery.yml against a running server for one minute in three phases: 10 seconds at 2 new virtual users a second, 30 seconds at 5, and 20 seconds at 10. Each virtual user follows one of four scenarios:

Scenario Share Requests
Health check30%GET /api/health
Sign-in40%POST /api/v1/login
Host list20%POST /api/v1/login, GET /api/v1/hosts
Agent WebSocket reachable10%GET /api/agent/connect

After the run, a regression check compares its latency percentiles, mean, error rate and requests per second with the last ten recorded runs. A metric fails when it is worse than that baseline by more than 15 percent or two standard deviations, whichever is wider (100 percent for the 99th percentile, which one slow request can swing). A run in which many requests timed out is treated as an environment problem rather than a regression.

The history is kept in performance-history.json in the server's source tree. Its 20 runs from 2026-08-31 to 2026-10-16 show how much the numbers depend on the machine that ran them: a 95th-percentile response time between 82 ms and 6.4 seconds, and 5 to 13 requests a second. The recorded error rate, 6 to 10 percent, counts every response that is not 2xx -- including the WebSocket reachability check, about one request in twelve, whose expected answers are not 2xx. Read the figures as a trend for one machine, not as product performance.

Playwright: the console in a browser

The end-to-end suite (make test-e2e) includes performance.spec.ts, which loads the console in Chromium against a running server and checks that the login page, dashboard and hosts page load, that moving between pages works, that no critical request fails, that a page makes a reasonable number of requests, and that JavaScript memory stays bounded across navigation. The limits are loose on purpose -- the login page within 30 seconds, a page change within 15, fewer than 750 requests, under 500 MB of heap -- so the checks catch something broken, such as a request loop, without failing on a slow CI machine.

Where they run

In CI, the UI and performance job of multi-os-ci.yml runs the Playwright suite on Windows and macOS and the Artillery test on macOS, on every push to the main branches and every pull request, and a final job collects the reports. Developers run the same targets locally. See Multi-OS CI/CD.
