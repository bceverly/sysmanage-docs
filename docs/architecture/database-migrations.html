Database Migrations

SysManage changes its database schema with Alembic migrations that ship inside each server release. Installing or upgrading a package never changes the database by itself: the operator applies the migrations with one command, and the package's install message says so.

Three chains

The migrations form three separate chains, each recording its own version in its own table, so that each kind of table can be migrated wherever it lives. Today the registry and shared tables are in the main database, and with multi-tenancy the tenant chain also runs against every tenant's own database:

Chain What it holds Version table
RegistryThe control plane: which tenants exist and where their databases are (tables named registry_*)alembic_version_registry
SharedReference data every tenant reads, such as vulnerability and advisory catalogs (tables named shared_*)alembic_version_shared
TenantEverything else -- hosts, users, the message queue, settings -- applied to the main database and to every tenant databasealembic_version

A server without multi-tenancy has one database, and all three chains apply to it. Tests check that each chain creates only the tables its prefix allows, and that every chain applies to the end on a real PostgreSQL database.

The rules every migration follows

  • One line per chain. Each migration follows the current end of its chain, so a chain always has exactly one head; when two branches meet, a merge migration joins them.
  • Safe to run twice. A migration checks before it acts -- it creates a table, column or index only when it is absent, and its downgrade drops one only when it is present -- so re-running a migration, or running it against a database that already has the change, does no harm.
  • PostgreSQL and SQLite. Production runs on PostgreSQL and the test suites on SQLite, so a migration uses no type or statement that one of them rejects.
  • Expand, then contract. A release only adds: new tables and columns, nullable or with a default, backfilled, with the code reading and writing both shapes. Removing or renaming something happens in a later release, once every database is past the addition.

Expand-contract matters because databases are not migrated all at once. Between installing a release and running the migrations, and while the tenant databases are migrated one after another, the same running server serves databases on both sides of a migration. A check in the server's lint run (make check-migrations, scripts/check_migrations.py) scans every migration's upgrade() and fails on dropping a table, column or constraint, or renaming a table or column. A drop that really is the contract step of an earlier expansion is allowed only with a # expand-contract-ok: comment giving the reason. downgrade() is not checked; dropping things is its job.

Applying migrations

Operators run one command, from the SysManage server: sudo sysmanage-migrate (installed as a command by the Debian and RPM packages; elsewhere, scripts/sysmanage_migrate.py run with the server's own Python environment). It applies, in order:

  1. the registry chain;
  2. the shared chain;
  3. the tenant chain, against the main database;
  4. with multi-tenancy, the tenant chain against every tenant database listed in the registry, one at a time, with a progress count.

For the tenant databases the tool leases each tenant's database credentials from OpenBAO, so OpenBAO must be running. A tenant that fails is reported and the others still migrate; the command then exits with an error. Databases that are already current are skipped, so the command is safe to run again after fixing a failure.

sudo sysmanage-migrate --status     # what is current and what is pending
sudo sysmanage-migrate --dry-run    # what would run, changing nothing
sudo sysmanage-migrate              # apply everything
sudo sysmanage-migrate --no-tenants # the three chains only
sudo sysmanage-migrate --tenants-only

In a development checkout, make migrate runs the same tool, so the path operators use is exercised on every development run. The scale test harness migrates its throwaway databases with it too.

Downgrades

Every migration has a downgrade() that removes what its upgrade() added, and migration tests use it to check that a migration can be applied, removed and applied again. sysmanage-migrate only moves forward; it has no downgrade option. A downgrade changes the schema only: a dropped table or column takes its data with it, and nothing brings that data back. Because releases are expand-contract, rolling the schema back is not needed to keep a server running while its databases catch up.

Professional+ engines and the schema

A licensed Professional+ engine can declare the oldest tenant-chain revision it needs. When the server loads the engine it compares that revision with the database's; if the database is behind, the engine is not loaded and the console shows a banner saying why:

  • Migrations pending -- the revision ships with this server but has not been applied: run sysmanage-migrate.
  • Server too old -- the engine was built for a newer server release; no migration on this server can reach that revision. Upgrade the server.
  • Restart needed -- the migrations have run since the server started. An engine refused at startup stays refused until the server restarts, so restart it after migrating.

This check is a safety net. The normal order is: install the new release, run the migrations, restart the server.
