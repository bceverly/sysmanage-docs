Multi-OS CI/CD Pipeline

The server and the agent are tested on GitHub Actions in two tiers: a fast matrix across Linux, macOS and Windows on every push and pull request, and a wider set of runs -- every supported Python version, the BSDs, security scans and load tests -- when a release is tagged. This page lists what runs, when, and where.

On every push and pull request

The multi-os-ci.yml workflow in each repository runs on pushes to main and develop and on pull requests to them. Its matrix varies the operating system and pins one Python version, so a platform problem shows up on the commit that caused it. A failure on one platform does not cancel the others (fail-fast: false).

Security scanning (the security workflow, and CodeQL on the server) also runs on these pushes and pull requests; SonarCloud analyzes pushes to main.

When a release is tagged

Pushing a version tag (v*.*.* or v*.*.*.*) starts the runs that are too slow or too wide for every commit. The release build waits for the tag's checks before it publishes anything.

  • Server, every Python version. ci.yml runs the backend tests on Python 3.10, 3.11, 3.12, 3.13 and 3.14, with the full lint suite and the coverage floor.
  • Agent, every Python version. The agent's ci.yml runs its tests on Python 3.9 through 3.14.
  • The BSDs. bsd-tests.yml boots FreeBSD 14.3, OpenBSD 7.9 and NetBSD 10.1 virtual machines under QEMU on Linux runners and runs the agent's integration tests in each. GitHub has no BSD runners, so these are slow (each VM takes several minutes to boot) and run per release, or on demand, rather than per commit. OpenBSD agent packages are also built in an OpenBSD virtual machine.
  • Load tests. load-tests.yml runs a cascade of simulated agents -- 100, then 500, then 1,000 -- against a disposable server and records the result.
  • Penetration checks. pen-tests.yml runs Trivy and Gitleaks scans, an OWASP ZAP baseline scan and authentication tests.

Other scheduled and on-demand runs

  • A weekly canary in each repository installs the newest releases of the test toolchain (pytest and its plugins), which every other run pins, so a breaking upstream release is found before the pin is moved.
  • Wheels for the riscv64 architecture are built in their own workflow.
  • The integration, load, BSD and penetration workflows can also be started by hand with a choice of scope.
