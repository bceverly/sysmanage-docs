WebSocket Protocol

Every agent holds one outbound WebSocket to the server, and everything between them rides it in both directions: the agent's reports and the server's commands. The web interface does not use a WebSocket; it calls the REST API. This page describes the agent connection as the code implements it.

Where the connection runs

The agent connects out to the server on port 443 and nothing else. nginx is the only network-facing listener: it terminates TLS on 443 (port 80 only redirects to 443) and passes the WebSocket upgrade for /api/agent/connect to the application, which listens on the loopback address 127.0.0.1:8080. nginx forwards only upgrades to websocket; any other upgrade request, including h2c, is refused with 400.

The agent verifies the server's certificate by default (server.verify_ssl), and a site behind a TLS-inspecting proxy names that proxy's CA in server.ca_bundle rather than turning verification off. The agent also checks the server's key against the identity it pinned when it enrolled. An approved agent presents its own client certificate in the TLS handshake: nginx asks for it on the agent paths, and the server checks that it names the same host as the host token, described below. Whether a certificate is required is set by the mutual TLS mode (see Agent Certificates and TLS).

Opening the connection

  1. Get a connection token. The agent calls POST /api/agent/auth, sending its host id and host token in the x-host-id and x-host-token headers once it has them. The reply names the token, its lifetime and the WebSocket path.
  2. Open the WebSocket. The agent connects to wss://<server>/api/agent/connect?token=<connection_token>. A connection without a token is closed with code 4000, and one with an invalid or expired token with code 4001. Both are recorded in the audit log.
  3. Register. The agent's first message is system_info, and it is what binds the connection to a host. A host is its host token, never its hostname: a message that names a host which has a token, without presenting that token, is refused. The server answers registration_success with the host's id and token. A new host stays pending until an administrator approves it, and is then sent host_approved.
POST /api/agent/auth
x-host-id: <host id>
x-host-token: <host token>

{
  "connection_token": "<token>",
  "expires_in": 3600,
  "websocket_endpoint":
    "/api/agent/connect"
}

The connection token is signed by the server and valid for one hour; it is used only to open the connection (or to authenticate an HTTP poll, below). Token requests are rate-limited over a 15-minute window: a verified host by its host id (30 requests by default) and an agent without an identity yet by its address (600 by default, so an office behind one NAT address is not locked out). Both are set in security.agent_connection_limits. A limited request gets 429 with a Retry-After header, and the wait is jittered so refused agents do not all return together.

After a server restart every agent registers at once, so registrations are admitted at a steady rate -- 100 a second with bursts of 200, per server worker, by default. An agent over the rate is not refused; its registration_success simply arrives later.

More on how hosts prove who they are: Agent Identity.

The message envelope

Every message is a JSON text frame with the same four fields:

{
  "message_type": "heartbeat",
  "message_id": "<uuid>",
  "timestamp": "<ISO 8601, UTC>",
  "data": { ... }
}

The server checks each message before it handles it: the three header fields must be present, message_id must look like a UUID, and timestamp must be within 30 minutes of the server's clock. A message that fails is answered with an error message whose error_type is message_validation_failed; text that is not JSON gets invalid_json. An error message carries error_type, a human-readable message and a data object.

Message types

The full list is the MessageType enumeration in the server's backend/websocket/messages.py. The main groups:

  • Agent to server, connection: system_info, heartbeat, command_acknowledgment, error.
  • Agent to server, inventory and status: reports such as hardware_update, os_version_update, software_inventory_update, package_updates_update, user_access_update, firewall_status_update, antivirus_status_update, time_status_update and host_metrics.
  • Agent to server, results: command_result and the results of specific work, such as update_apply_result, script_execution_result, backup_result and the child host events.
  • Server to agent: command (its data names a command_type, its parameters and a timeout, 300 seconds by default), update_request, ping, shutdown, host_approved, broadcast, config_update and logging_config_update, plus the registration_success and error replies.

Heartbeats and liveness

The agent sends a heartbeat message every websocket.ping_interval seconds -- 30 by default -- with 10% jitter either way, so a fleet that connected together does not heartbeat together. The WebSocket library also sends protocol-level pings at the same interval and drops the connection when a pong takes longer than half of it. The agent answers a server ping message with pong. Heartbeats also carry the timestamps the server uses to measure the host's clock (see Time Sync).

On the server, an approved host that has sent no heartbeat within monitoring.heartbeat_timeout (5 minutes by default) is marked down. Right after the server starts, no host is marked down for that timeout plus 8 minutes, the time agents need to reconnect.

Delivery and acknowledgment

Neither side writes straight to the socket. The agent puts every outgoing message in a local SQLite queue and sends from there, so a report made while the connection is down is sent once it is back; command_acknowledgment goes first. On the server, heartbeat, system_info and command_acknowledgment are handled as soon as they arrive, and every other message is stored in the database queue and processed in the background. Commands for a host are stored in the same queue, so a host that is offline receives them when it reconnects.

The agent acknowledges each command with command_acknowledgment. A command not acknowledged within 60 seconds is sent again, up to its max_retries (3 by default), with a delay that starts at 60 seconds, doubles each time up to an hour, and is jittered by 20%. The agent recognizes a command it has already received by its message_id and does not run it twice. The whole path is described in Message Flow.

Reconnecting

When the connection drops, the agent waits a random time between 1 second and a ceiling that doubles with each failure, up to 300 seconds (full jitter), so a fleet that lost the server in the same second does not come back in the same second. When the server closed the connection on purpose (close code 1001, 1012 or 1013, as in a restart), the first reconnect is spread over 60 seconds. A wait the server asks for with Retry-After is honored, plus up to 20%. Before reconnecting the agent checks that the server is answering at all.

When the network will not carry a WebSocket

Some proxies refuse to tunnel a WebSocket. When the agent sees a failure of that kind -- a structural one, such as a proxy rejecting the tunnel, rather than a server that is down -- it switches to HTTP polling and keeps testing the WebSocket, so a fixed proxy is noticed. A poll is an ordinary POST /api/agent/poll carrying the same connection token as Authorization: Bearer and the host token as x-host-token. Each poll sends the agent's queued messages and returns up to 50 queued for the host; it may wait up to 25 seconds for new ones. Both transports drain the same queues, so a message does not depend on which one carried it.

Server workers

The server can run several worker processes on one machine. Each worker delivers queued messages only to the WebSockets it holds itself, and work that belongs to the whole server (the heartbeat monitor, schedulers and similar ticks) runs in one worker, chosen with a PostgreSQL advisory lock. There is no message bus, load balancer or second server: high availability is planned. Measured limits are in Performance and Scale.
