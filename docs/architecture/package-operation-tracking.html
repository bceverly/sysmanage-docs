Package Operation Tracking

How SysManage records a request to install or uninstall packages on a host, sends it to the agent, and records the result.

Architecture Overview

Each request from the console becomes one row in installation_requests, one row per package in installation_packages, and one queued command to the host's agent. The request ID is a UUID that travels to the agent and back, so the agent's completion report lands on the right row.

Key Features

  • One schema for both directions: operation_type is install or uninstall.
  • One UUID per request: several packages travel in one command and are reported as one result.
  • Store-and-forward delivery: the command goes through the server's message_queue, and the agent's report goes through the agent's own outbound queue, so neither side loses the message if the connection drops.
  • Audit trail: every queued request is written to audit_log with the user, host, and package list.
  • Role checks: installing needs the Add Package role and uninstalling needs the Remove Package role.

Database Schema Design

Installation Requests Table

One row per console request:

CREATE TABLE installation_requests (
    id UUID NOT NULL,                        -- the request ID sent to the agent
    host_id UUID NOT NULL,
    requested_by VARCHAR(100) NOT NULL,
    requested_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    completed_at TIMESTAMP WITHOUT TIME ZONE,
    status VARCHAR(20) DEFAULT 'pending' NOT NULL,
    operation_type VARCHAR(20) DEFAULT 'install' NOT NULL,   -- install | uninstall
    result_log TEXT,                         -- output reported by the agent
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (host_id) REFERENCES host (id) ON DELETE CASCADE
);

Installation Packages Table

One row per package in a request:

CREATE TABLE installation_packages (
    id UUID NOT NULL,
    installation_request_id UUID NOT NULL,
    package_name VARCHAR(255) NOT NULL,
    package_manager VARCHAR(50) NOT NULL,    -- 'auto': the agent picks
    PRIMARY KEY (id),
    FOREIGN KEY (installation_request_id)
        REFERENCES installation_requests (id) ON DELETE CASCADE
);

Index Strategy

CREATE INDEX ix_installation_requests_requested_at ON installation_requests (requested_at);
CREATE INDEX ix_installation_requests_status ON installation_requests (status);
CREATE INDEX ix_installation_requests_operation_type ON installation_requests (operation_type);
CREATE INDEX ix_installation_packages_installation_request_id
    ON installation_packages (installation_request_id);

The history view reads a host's requests newest first by requested_at; the packages of each request are found through installation_request_id.

Software Installation Log Table

software_installation_log tracks single-package installs by an installation_id. When an agent sends package_installation_status for such an install, the server sets the row's status, sets started_at on installing, and on completed or failed records completed_at, success, the installed version, the error message, and the log. Console install and uninstall requests use installation_requests instead.

Operation Lifecycle Management

Status Flow Diagram

pending --> in_progress --+--> completed
                          |
                          +--> failed

Status Definitions

  • pending: The request and package rows are written, before the command is queued.
  • in_progress: The command is in the server's message queue or with the agent.
  • completed: The agent reported success for every package in the request.
  • failed: The agent reported that at least one package failed.

Request Flow

  1. Request: the console calls POST /api/v1/packages/install/{host_id} or POST /api/v1/packages/uninstall/{host_id} with the package names. The server checks the user's role and that the host is active and approved.
  2. Record: the server generates the request UUID, writes the installation_requests row as pending and one installation_packages row per package, and commits.
  3. Queue: the server enqueues one outbound command message for the host, a generic_command that carries install_packages or uninstall_packages with the request ID, the packages, and who asked. It then marks the request in_progress and writes the audit entry.
  4. Run: the agent records the request in its local database, groups the packages by package manager, and installs or removes them.
  5. Report: the agent queues an installation_complete message with the request ID, overall success, and the combined log. The server sets the request to completed or failed, stores completed_at and result_log, and replies with installation_complete_ack.

History Endpoints

  • GET /api/v1/packages/installation-history/{host_id}: a host's requests, newest first, each with its comma-separated package names, status, operation type, and log. Paged with limit (1-100, default 50) and offset.
  • DELETE /api/v1/packages/installation-history/{request_id}: deletes a request and its package rows.
