Performance and Scale

What one SysManage server carries was measured, not estimated. The measurements below were made for the scale-hardening release, v3.10.0.0 (October 2026), with simulated agents against a real server and database. This page says how they were made, what they showed, and what is still unproven. For sizing a server of your own, use the Scaling Guide, which is built from the same runs.

How it was measured

The scale harness lives in the server's source tree under tests/load. stack.py builds a disposable server for each run: PostgreSQL in a throwaway container, a configuration written from scratch, the migrations applied with the same tool operators use, and the server started, stopped and restarted on demand. fleet.py runs the agents. They are simulated agents, not the real agent: each one registers, authenticates, opens a WebSocket and then behaves the way the agent does -- the handshake, the full first report, a heartbeat every 30 seconds, periodic collections, the agent's reconnect backoff and its fallback to HTTP polling -- with generated inventory data. observe.py records the queue, hosts up and down, database connections, the server's CPU and memory, and how long the health check takes to answer.

The agents run on other machines than the server, so the server and its database have their machine to themselves. A run counts only if the server machine was quiet: the harness measures the CPU used by everything outside the run and marks a run untrustworthy above 25 percent.

The scenario is the hardest one a fleet produces: the server restarts while every agent is connected, so the whole fleet reconnects and reports at once. A run passes when every agent reconnects, no queued message expires, no agent is locked out or pushed to HTTP polling, and no host is marked down because of the outage.

10,000 agents, one tenant

Run 2026-10-03, 40 minutes, the server and PostgreSQL on one 8-core laptop and the simulated agents on a second machine.

  • Server restart: the queue peaked at 51,732 messages and was drained by about 16 minutes, then stayed near zero. Reconnect took 195 seconds, heartbeat p95 was 1.2 seconds, health check p95 0.48 seconds, and the server used 199 percent CPU (about two cores).
  • Every agent restarted at once: the queue peaked at 60,337 messages and was drained by about 16 minutes. Reconnect took 159 seconds and heartbeat p95 was 1.3 seconds.
  • Both runs: 10,000 of 10,000 agents connected, and nothing expired, no host was marked down, no agent was refused or fell back to polling.

The capacity curve, 20 tenants

Runs 2026-10-05. The server and PostgreSQL on one desktop (AMD Ryzen 5 7600, 12 threads, 29 GB of memory, wired network); the simulated fleet spread over three other machines on Wi-Fi; 20 tenants, each with its own database; the server-restart storm. Every run was clean, and in every run the queue drained to zero.

Server CPU is the server's processes together, where 100 percent is one core; memory is theirs, without PostgreSQL. At 30,000 agents the six workers each ran at about 85 percent of a core: everything still drained, but reconnects and heartbeats were answered late, so some agents had not reconnected by the end and 550 hosts were marked down. More workers needed more memory than the machine had.

What the numbers say

  • About 2.2 to 2.7 server cores and about 3.5 GB of server memory per 10,000 agents, plus PostgreSQL, which used about 10 GB at 20,000 agents in 20 tenants. The Scaling Guide rounds these up into planning figures.
  • One quiet 12-thread machine carries 20,000 to 25,000 agents across 20 tenants with every criterion met.
  • A server scales up by running more worker processes, one per core. Each worker serves its agents from one event loop, and in these runs the busy event loops, not the queue drain, were what fell behind first.

Fleet-wide pushes

Run 2026-10-06, 2,000 simulated agents, driving the server's real antivirus deployment and package catalog passes every 60 seconds: antivirus went out in 8 waves of 250 and catalog requests in 4 waves of 500, each agent exactly once, with heartbeat p95 at 957 ms and nothing expired.

Not proven yet

  • 50,000 agents. By the curve above it needs about 12 to 14 dedicated server cores, a separate database machine and 48 GB or more. That is an extrapolation; the measurement waits for a larger machine and is planned in ROADMAP Phase 29.
  • Many federated sites under load. There is no many-sites harness yet; it is planned in ROADMAP Phase 29.
  • More than one server. SysManage runs as one server with several worker processes; several servers behind a load balancer, with failover, is planned in ROADMAP Phase 34 and is not available today.
  • The agent's memory. The agent has been observed idling at roughly 75 to 115 MiB resident on Ubuntu; a measurement on every supported operating system, with a budget per platform, is still open (ROADMAP 27.3).
