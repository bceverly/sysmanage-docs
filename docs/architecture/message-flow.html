Message Flow and Queuing

Every message between the server and an agent passes through a queue that survives a restart: a table in the server's database on one side, a small SQLite database on the agent on the other. Nothing is handed straight from a WebSocket to the code that acts on it, so a disconnect, a busy server or a restart delays work instead of losing it.

There is no message broker. The server's queue is an ordinary table in its PostgreSQL database, and the server's worker processes coordinate through that database. With multi-tenancy, each tenant database has its own queue, and the server drains the main database's queue and every tenant's in turn; a failure in one is rolled back and logged without holding up the others.

The server's queue

Each row of the message_queue table is one message, in one direction: inbound (from an agent) or outbound (to an agent). A row records the host, the message type and its JSON payload, a priority (urgent, high, normal or low), how many times it has been tried and may be tried (retry_count, max_retries, 3 by default), a not-before time (scheduled_at), and a correlation ID that ties a reply to its request.

From an agent to the server

A message that arrives on a verified agent session is queued with its host straight away; the WebSocket handler does no other work. A background drain then works through the queue on a thread of its own, so the event loop that serves the agents' connections never waits for it:

  • the host that has waited longest goes first, and each host gets at most 20 messages a round, so one busy host cannot hold up the rest;
  • each drain runs for a time budget of 0.75 seconds and, while work remains, starts again almost at once instead of sleeping for a second;
  • with several worker processes, a worker drains a host only while it holds that host's PostgreSQL advisory lock, so one host's messages are never processed by two workers at once or out of order;
  • a message left in progress by a worker that died is put back to pending after 30 seconds (5 minutes when several workers run).

Heartbeats take a faster path: after a connection's first heartbeat, an unchanged one only records that the host was seen, and each worker writes those in one bulk update every 5 seconds.

From the server to an agent

A command from the UI, the API or a scheduler is written to the queue first. The outbound drain sends it in the same fair order -- the longest-waiting host first, up to 50 hosts a round and 20 messages per host, for half a second at a time. Only the worker process that holds a host's WebSocket sends to that host. A host that has fallen back to HTTP polling collects its messages when it polls.

A command held by a closed maintenance window stays queued with a not-before time and is looked at again every minute, so it goes out when the window opens without blocking anything behind it.

Acknowledgments and retries

When the agent receives a command it stores it in its own queue and answers with a command_acknowledgment. If no acknowledgment (or result) arrives within 60 seconds -- the send worked, but the agent disconnected or crashed before storing the command -- the server schedules the command again. The wait before each retry doubles, starting at 60 seconds and capped at one hour, with 20 percent random jitter either way so messages that failed together do not come back together. After the last retry the message is marked failed.

The sweep that looks for unacknowledged messages takes at most 500 at a time and claims each one with a single conditional update, so two workers never retry the same message. A command that is sent twice is still run once: the agent recognizes the server's message ID, does not run the command again, and acknowledges it again. An acknowledgment or result that arrives late, after a retry was scheduled or the retries ran out, still closes the command instead of being thrown away.

Expiry and cleanup

  • Outbound messages still pending expire by age, 60 minutes by default (message_queue.expiration_timeout_minutes): a reboot or a patch run delivered an hour late is worse than one not delivered. Commands held by a maintenance window are the exception: they wait up to 168 hours (message_queue.held_max_age_hours).
  • Inbound messages never expire just for waiting their turn -- that would turn a backlog into lost agent reports. They expire only when their last processing attempt is older than that timeout, or after a ceiling of 24 hours (message_queue.inbound_max_age_hours), and the server logs a warning when it expires any.
  • Once a day, completed messages older than seven days are deleted in committed chunks; failed messages are kept for diagnosis.

On the agent

The agent keeps its own queue in SQLite, in agent.db (for a system install, /var/lib/sysmanage-agent/agent.db), with the same directions and priorities. Everything the agent sends goes through it. The handshake message (system_info) and errors are urgent; heartbeats, acknowledgments and command results are high; reports are normal. While connected, the agent sends ten messages, waits a second, and repeats. A message is deleted from the queue as soon as it has been sent; a failed send is retried after a random wait of up to 60 seconds, a limit that doubles with each attempt up to an hour; messages whose retries ran out are kept for diagnosis. Messages left in progress by a crash are recovered when the agent reconnects.

Reports are sent only when they change. A snapshot report (software, users, hardware, certificates and the like) is queued only if its content differs from the last one, or if the last one is more than 24 hours old; a newer snapshot replaces an older one of the same type that is still waiting to be sent. Process lists and hardware health are sent when they change in substance and otherwise every 15 minutes; host metrics are sampled every 15 minutes. Anything the server asks for is always sent.

The available-package catalog, the largest thing an agent reports, is sent as a delta -- the packages added, changed and removed since the copy the server already holds. The two sides compare fingerprints first; the agent sends the full catalog instead when they disagree, when more than 30 percent of it changed, or when the last full copy is more than seven days old.

One command at a time, and the express lane

The agent runs the commands it receives one at a time, in priority order, so two package operations never run against each other. A long command -- the first package collection on a large Windows host can take more than ten minutes -- would then hold up everything behind it. A short list of commands that are quick and safe to run beside any other is queued as urgent and also taken by an express lane that runs alongside the main one:

  • resync_clock
  • check_backup_storage

Both lanes claim a command before running it, so each command runs exactly once, whichever lane takes it.

Heartbeats and host status

An agent sends a heartbeat every 30 seconds by default (websocket.ping_interval in the agent's configuration). About once a minute the server marks an approved host down if it has not been heard from within monitoring.heartbeat_timeout (5 minutes by default), and back up when it is. Right after the server starts, every host looks silent because none could reach it while it was down, so for the timeout plus 8 minutes no host is marked down.
