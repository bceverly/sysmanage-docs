Database Schema

The core tables of the SysManage schema, with the columns, indexes, and foreign keys the server's SQLAlchemy models define.

Schema Overview

The models under backend/persistence/models/ define more than 240 tables and are the authoritative schema; Alembic migrations bring a database up to them. This page covers the core tables. The DDL below is what SQLAlchemy emits for PostgreSQL, trimmed where a table has many columns.

Core Tables

Users & Authentication

user

CREATE TABLE "user" (
    id UUID NOT NULL,
    active BOOLEAN,
    userid VARCHAR,                        -- login ID (an email address)
    hashed_password VARCHAR,
    last_access TIMESTAMP WITHOUT TIME ZONE,
    is_locked BOOLEAN NOT NULL,
    failed_login_attempts INTEGER NOT NULL,
    locked_at TIMESTAMP WITHOUT TIME ZONE,
    first_name VARCHAR(100),
    last_name VARCHAR(100),
    profile_image BYTEA,
    profile_image_type VARCHAR(10),
    profile_image_uploaded_at TIMESTAMP WITHOUT TIME ZONE,
    is_admin BOOLEAN NOT NULL,
    last_login_at TIMESTAMP WITHOUT TIME ZONE,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    external_idp_provider_id UUID,
    external_subject VARCHAR(500),
    last_tenant_id UUID,
    PRIMARY KEY (id)
);
CREATE UNIQUE INDEX ix_user_userid ON "user" (userid);
CREATE INDEX ix_user_external_idp_provider_id ON "user" (external_idp_provider_id);

security_role_groups, security_roles, user_security_roles

CREATE TABLE security_role_groups (
    id UUID NOT NULL,
    name VARCHAR(100) NOT NULL,
    description TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    PRIMARY KEY (id)
);
CREATE UNIQUE INDEX ix_security_role_groups_name ON security_role_groups (name);

CREATE TABLE security_roles (
    id UUID NOT NULL,
    name VARCHAR(100) NOT NULL,
    description TEXT,
    group_id UUID NOT NULL,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (group_id) REFERENCES security_role_groups (id) ON DELETE CASCADE
);
CREATE UNIQUE INDEX ix_security_roles_name ON security_roles (name);

CREATE TABLE user_security_roles (
    id UUID NOT NULL,

    granted_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,

    PRIMARY KEY (id),
    FOREIGN KEY (user_id) REFERENCES "user" (id) ON DELETE CASCADE,
    FOREIGN KEY (role_id) REFERENCES security_roles (id) ON DELETE CASCADE,
    FOREIGN KEY (granted_by) REFERENCES "user" (id) ON DELETE SET NULL
);
CREATE INDEX ix_user_security_roles_user_id ON user_security_roles (user_id);
CREATE INDEX ix_user_security_roles_role_id ON user_security_roles (role_id);

Hosts

host

These are certificates the agent finds on the host. The agent's own client certificate is tracked on the host row (client_certificate, certificate_serial, certificate_issued_at).

registry_host_tenant.host_id has no foreign key: the host row lives in the tenant's database, and a foreign key cannot cross databases. See Multi-Tenancy Architecture.

Entity Relationships

Core Entity Relationships

security_role_groups <-- security_roles <-- user_security_roles --> user

tags <-- host_tags --> host <-- software_package
                         ^ ^ ^-- package_update
                         | +---- installation_requests <-- installation_packages
                         +------ alert --> alert_rule
                         +------ host_certificates, network_interface,
                                 storage_device, script_execution_log, ...

registry_tenant <-- registry_tenant_placement
                <-- registry_host_tenant  (host_id: no foreign key)

Foreign Key Constraints

ON DELETE CASCADE

  • Host-scoped tables to host: deleting a host removes its packages, updates, installation requests, certificates, interfaces, storage devices, alerts, tags links, and script runs.
  • user_security_roles to user and security_roles: deleting a user or a role removes the grants.
  • registry_* tables to registry_tenant: deleting a tenant record removes its placement and host bindings.

ON DELETE SET NULL

  • user_security_roles.granted_by, alert.rule_id, and script_execution_log.saved_script_id keep the row when the referenced user, rule, or saved script is deleted.

Data Types & Constraints

JSON columns

Flexible data uses SQLAlchemy's portable JSON type (PostgreSQL json), for example:

  • audit_log.details and alert.details: structured context for an entry
  • alert_rule.condition_params and alert_rule.host_filter: rule thresholds and which hosts a rule covers
  • registry_tenant.settings and registry_tenant.limits: per-tenant settings and limits

Some JSON is stored as text instead, such as message_queue.message_data and host.agent_capabilities.

Temporal Data Management

Timestamps are UTC. Nearly all columns are TIMESTAMP WITHOUT TIME ZONE holding UTC values written by the application; a few, such as custom_metric_sample.collected_at, are time-zone-aware. The application sets created_at and updated_at; there are no database triggers.

Enumerated Values

Status fields are plain strings checked by the application; the schema declares no CHECK constraints. Examples:

  • host.approval_status: pending, approved, rejected, revoked
  • message_queue.status: pending, processing, completed, failed, expired
  • installation_requests.status: pending, in_progress, completed, failed

Indexes

  • Single-column indexes on lookup columns such as host_id, names, statuses, and timestamps.
  • Unique indexes and constraints on natural keys such as user.userid, tags.name, host.host_token, and registry_tenant.slug.
  • Composite indexes where a hot query needs them, such as the three on message_queue (shown on Database Design) and the metric/host/time index on custom_metric_sample.

The schema uses no table partitioning, GIN indexes, or partial indexes.

Database Migrations

Migration Framework

SysManage uses Alembic, in three chains with separate version tables:

Migration Structure

alembic.ini              # one section per chain
alembic/
|-- env.py               # tenant chain    -> alembic_version
|-- versions/            # tenant chain migrations
|-- registry/
|   |-- env.py           # registry chain  -> alembic_version_registry
|   `-- versions/
`-- shared/
    |-- env.py           # shared chain    -> alembic_version_shared
    `-- versions/

How migrations are written and applied in production is on Database Migrations.

Database Maintenance

Automated Cleanup

  • message_queue: completed messages are deleted after 7 days; failed messages are kept.
  • custom_metric_sample: samples older than custom_metrics.retention_days (default 90) are deleted daily from every database.
  • audit_log: retention policies in audit_retention_policy delete old entries or move them to audit_log_archive.

These purges delete in chunks of 5,000 rows, committing after each chunk.
