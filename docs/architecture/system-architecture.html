System Architecture

A SysManage installation is one server machine running a handful of processes, and an agent on every managed host. The agents connect out to the server; the server never connects in to them. This page names each part and what it does.

The components

nginx

The only network-facing listener, on every platform. It terminates TLS on port 443 (port 80 only redirects to it), serves the web console's static files, and passes /api/ -- including the agents' WebSocket upgrade -- to the server on the loopback address. It accepts only WebSocket upgrades and rejects HTTP/2 cleartext upgrade attempts before they reach the server.

The server

A Python application built on FastAPI, SQLAlchemy and Pydantic, run by uvicorn and bound to loopback only. It serves the REST API under /api/v1 (agent communication, multi-factor sign-in, single sign-on callbacks and SCIM keep unversioned /api paths), holds the agents' WebSockets, and runs the background work: draining the message queue, the heartbeat monitor, alerting, schedules, retention and feed refreshes.

Workers and the leader

The server runs several worker processes on its machine -- by default one per CPU less a quarter kept for PostgreSQL and the system, at most one per GB of memory beyond the first 2 GB, and at most 16 (api.workers overrides it). Each worker holds its own agents' connections. Work that belongs to the whole server runs in exactly one of them, the leader, chosen with a PostgreSQL advisory lock; if the leader dies, another worker takes the lock within about 15 seconds. Several workers need PostgreSQL; on SQLite the server runs one.

PostgreSQL

All of the server's state -- hosts, inventories, users, settings, history -- and the queue of messages to and from agents. There is no separate cache or message broker; the workers coordinate through the database. The schema is managed with Alembic migrations that the operator applies.

OpenBAO

The secrets store, listening on 127.0.0.1:8200 with file storage. The secure installation generates the server's own secrets into it -- the token-signing secret, the password salt, database and mail passwords, license keys -- so sysmanage.yaml holds only a pointer. With multi-tenancy, each tenant's database credentials are leased from it.

The web console

A single-page application in React and TypeScript with Material UI, built with Vite into static files that nginx serves. It talks to the server only through the REST API, in any of 14 languages. A licensed engine can add its own pages to it as a plugin bundle.

The agents

A Python agent on each managed host -- Windows, Linux, macOS, FreeBSD, OpenBSD and NetBSD. It dials out to the server over port 443 and keeps a WebSocket open, so managed hosts need no inbound port. If the network will not carry a WebSocket (a proxy that refuses the tunnel, for example), it falls back to HTTP polling and keeps testing the WebSocket. It keeps its own queue and state in a local SQLite database, so it works through a disconnect and catches up afterwards.

Professional+ engines

Licensed features ship as compiled engines (Cython modules) rather than as source. A licensed server downloads the engines its license covers, checks each bundle's signed manifest -- an Ed25519 signature over a list of every file's SHA-256 -- and loads them into the server process at runtime; they are cached locally under /var/lib/sysmanage/modules. Without a license the open-source server runs on its own, and the engines' features are simply absent.

Multi-tenancy (optional)

Off by default. When it is on (a licensed engine), a control-plane registry records the tenants, and each tenant gets a database of its own, which can live on another PostgreSQL server. Reference data that every tenant reads, such as vulnerability catalogs, is kept once in shared tables. An agent joins a tenant with that tenant's enrollment token, and the server drains each tenant's message queue in turn.

How a request travels

  1. An administrator acts in the console; the browser calls the REST API through nginx.
  2. The server checks the caller's token or API key and role, and writes a command to the message queue in the database.
  3. The worker that holds the host's WebSocket sends the command; the agent stores it in its local queue and acknowledges it.
  4. The agent runs the command and queues the result, which the server receives, queues and processes into the database.
  5. The console shows the result the next time it asks the API.

The queues on both sides, the acknowledgments and retries are described in Message Flow and Queuing.

Measured, not estimated

With simulated agents against a real server, the server restarted while every agent was connected:

  • 10,000 agents, one tenant, server and PostgreSQL on one 8-core laptop: every agent reconnected, the queue peak of 51,732 messages drained in about 16 minutes, nothing expired, no host marked down.
  • 20,000 agents across 20 tenants on one 12-thread desktop: 95 percent reconnected in 230 seconds, heartbeat p95 1.6 seconds, everything drained.
  • About 2.2 to 2.7 server cores and 3.5 GB of server memory per 10,000 agents, plus the database. 50,000 agents and more than one server have not been proven yet.

The method, the full results and what is still open are in Performance and Scale; sizing advice is in the Scaling Guide.

What it does not have

No message broker or cache server, no container orchestrator, and no cluster of servers behind a load balancer: one server machine, scaled by its worker processes, with the database as the only shared state. Running several servers with failover is planned and is not available today.
