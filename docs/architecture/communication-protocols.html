Communication Protocols

SysManage has three channels: agents talk to the server over one WebSocket each (or HTTP polling where a WebSocket cannot pass), people and scripts use the REST API, and the server keeps every message for an agent in its database until it is delivered. This page is the overview; each channel has its own page with the details.

One public listener

nginx is the only network-facing listener. It serves TLS on port 443 (TLS 1.2 and 1.3, AEAD cipher suites only), redirects port 80 to 443, serves the web interface's files, and passes /api/ -- including the agents' WebSocket upgrades -- to the application, which listens only on 127.0.0.1:8080. A firewall in front of the server needs only 443 open for SysManage (80 just redirects), and agents need only outbound 443.

                        |
browser --https 443-----+--> nginx
                              |
                  127.0.0.1:8080
                              |

Agents: the WebSocket

Each agent connects out to the server and keeps one WebSocket open at /api/agent/connect. It first asks POST /api/agent/auth for a connection token, valid for an hour, then opens the socket with that token and registers with its system_info message. A host is identified by its host token, never by its hostname. Reports from the agent and commands from the server both ride this one connection as JSON messages, and the agent sends a heartbeat every 30 seconds by default.

The agent verifies the server's certificate. An agent holding a client certificate presents it, but the bundled nginx configuration does not verify client certificates, so the host token is what proves a host. Details -- the envelope, message types, heartbeats, reconnect backoff -- are in WebSocket Protocol.

Agents: HTTP polling fallback

Some proxies refuse to tunnel a WebSocket. When the agent sees that kind of failure -- the network will not carry the protocol, as opposed to a server that is down -- it switches to POST /api/agent/poll, an ordinary HTTPS request that sends its queued messages and collects those waiting for it. It keeps testing the WebSocket and goes back to it when it works. A command reaches a polling agent on its next poll rather than at once.

People and automation: the REST API

The web interface is a single-page application that calls the JSON REST API under /api/v1; it has no WebSocket of its own and refreshes by calling the API again. Scripts use the same API with an API key. Agent traffic, sign-in and SSO callbacks keep their own unversioned paths under /api. See REST API Design and the API reference.

Store and forward

Messages between server and agent are not sent straight to a socket. The server stores a command for a host in its database queue and sends it when the host is connected; a host that is offline gets it when it reconnects. The agent acknowledges each command, and the server sends an unacknowledged one again after 60 seconds, up to three more times by default, with a growing delay. Reports from the agent are stored in the same queue and processed in the background. The agent keeps its own outgoing messages in a local SQLite queue, so reports made while it is disconnected are not lost. Both transports -- WebSocket and polling -- drain the same queues. See Message Flow.

Server discovery

The server also runs a UDP discovery beacon on port 31337 that agents can query to find it. It is bound to 127.0.0.1 unless discovery.bind_address in sysmanage.yaml says otherwise, so by default it is not reachable from the network.

One server

All of this runs on one server machine, optionally with several worker processes that coordinate through PostgreSQL. There is no message bus or load balancer between them; high availability is planned (ROADMAP Phase 34). Measured limits are in Performance and Scale, and the whole picture is in System Architecture.
