Database Design

How the SysManage server stores its data: SQLAlchemy 2.0 models, PostgreSQL in production, three Alembic migration chains, and connection pools sized to the machine.

PostgreSQL in production
The server reaches PostgreSQL through psycopg 3. SQLite works for tests and single-worker installs; running more than one server worker needs PostgreSQL, because the workers elect a leader with PostgreSQL advisory locks.
SQLAlchemy 2.0 models
Every table is a model under backend/persistence/models/. Primary keys are UUIDs: a native UUID column on PostgreSQL, a 36-character string on SQLite.
Sized connection pools
Each server worker keeps its own pool, sized for the machine by backend/persistence/pool_sizing.py and checked against PostgreSQL's max_connections at startup.
Three migration chains
Alembic migrates the tenant, registry, and shared tables as three separate chains, each with its own version table.

How the schema is organized

The server defines more than 240 tables. A table's name prefix says which partition it belongs to:

registry_* -- control plane

Tenants, their database placements, enrollment tokens, and host-to-tenant bindings. Used when multi-tenancy is enabled.

shared_* -- reference data

Data that is the same for every tenant, such as the vulnerability and advisory catalogs, OS lifecycle dates, and content views.

Unprefixed -- host data and identity

Everything about managed hosts -- inventory, packages, scripts, alerts, compliance results, and the message queue -- plus console identity tables such as user and security_roles.

Multi-tenancy is off by default, and then all three partitions live in one database. With it on, host data is served from each tenant's own database, while console identity stays in the main database. See Multi-Tenancy Architecture.

Core Table Relationships

Most host-scoped tables carry a host_id foreign key to host with ON DELETE CASCADE, so deleting a host removes its inventory, history, and queued work with it.

👤
user

Console accounts: login ID, password hash, account lock state and failed-login count, profile image, and an optional link to an external identity provider.

🖥️
host

One row per managed host: FQDN, addresses, approval status, up/down status, platform and OS details, the host token, and certificate details.

📦
software_package

Packages installed on each host, with version, package manager, architecture, size, and install date.

🛒
available_packages

Packages the hosts' package managers offer, grouped by OS name and version.

⬆️
package_update

Updates available on each host: current and available version, update type, and whether a reboot is required.

🔄
installation_requests

One row per install or uninstall request, with its packages in installation_packages. See Package Operation Tracking.

📜
saved_scripts

Stored scripts; each run is recorded in script_execution_log with its output and exit code.

📨
message_queue

The server's store-and-forward queue for messages to and from agents: direction, status, priority, retry count, and expiry.

🏷️
tags / host_tags

Named tags and the many-to-many link between tags and hosts.

🌐
network_interface

Each host's network interfaces, with IPv4 and IPv6 addresses, MAC address, MTU, and link state.

💾
storage_device

Each host's storage devices and mount points, with file system, capacity, and usage.

🔒
security_roles

Console permissions, grouped by security_role_groups and granted to users through user_security_roles.

🧾
audit_log

Who did what and when, with result, details, and an integrity hash per entry. Retention policies in audit_retention_policy can move old entries to audit_log_archive.

Indexing Strategy

Indexes the models declare

🔍
UUID primary keys
🔗
Indexes on host_id and other lookup columns
⚡
Composite indexes for queue processing
🎯
Unique indexes on natural keys
⏰
Timestamp indexes
🏷️
Status indexes

Unique indexes include user.userid, tags.name, and host.host_token. The schema has no full-text search indexes and no JSON path indexes.

Persistence Features

📄
JSON columns

Flexible fields such as audit_log.details, alert.details, and registry_tenant.settings use SQLAlchemy's portable JSON type. Queue payloads are stored as serialized JSON text in message_queue.message_data.

🔗
Cascading foreign keys

Host-scoped rows are removed with their host. Optional references, such as the user who granted a role, use ON DELETE SET NULL instead.

⚡
Connection pooling

Per worker, the pool size is 2 x CPUs + 8 (between 10 and 40), with the same number of overflow connections, capped by the machine's RAM. Every key under database_pool in sysmanage.yaml can override the computed value.

🩺
Failover tolerance

Pooled connections are pinged before use and recycled after 30 minutes. Idempotent work that starts while a new PostgreSQL primary is being promoted is retried with bounded backoff.

🕐
UTC timestamps

Timestamps are UTC. Nearly all are stored in columns without a time zone; a few tables, such as custom_metric_sample and gpg_key, use time-zone-aware columns.

🧹
Chunked deletes

Large purges, such as completed queue messages and expired custom-metric samples, delete 5,000 rows at a time and commit after each chunk, so no single transaction holds millions of row locks.

Message Queue Implementation

CREATE TABLE message_queue (
    id UUID NOT NULL,
    host_id UUID,
    message_id VARCHAR(36) NOT NULL,
    direction VARCHAR(10) NOT NULL,      -- inbound | outbound
    message_type VARCHAR(50) NOT NULL,
    message_data TEXT NOT NULL,          -- serialized JSON
    status VARCHAR(15) NOT NULL,         -- pending, processing, completed, failed, expired
    priority VARCHAR(10) NOT NULL,
    retry_count INTEGER NOT NULL,
    max_retries INTEGER NOT NULL,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    scheduled_at TIMESTAMP WITHOUT TIME ZONE,
    started_at TIMESTAMP WITHOUT TIME ZONE,
    completed_at TIMESTAMP WITHOUT TIME ZONE,
    error_message TEXT,
    last_error_at TIMESTAMP WITHOUT TIME ZONE,
    correlation_id VARCHAR(36),
    reply_to VARCHAR(36),
    expired_at TIMESTAMP WITHOUT TIME ZONE,
    PRIMARY KEY (id)
);

-- Composite indexes for queue processing
CREATE INDEX idx_message_queue_processing
    ON message_queue (direction, status, priority, scheduled_at);
CREATE INDEX ix_message_queue_host_queue
    ON message_queue (host_id, direction, status, created_at);
CREATE INDEX ix_message_queue_drain_order
    ON message_queue (direction, status, created_at);

Package Operation Tracking

CREATE TABLE installation_requests (
    id UUID NOT NULL,
    host_id UUID NOT NULL,
    requested_by VARCHAR(100) NOT NULL,
    requested_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    completed_at TIMESTAMP WITHOUT TIME ZONE,
    status VARCHAR(20) DEFAULT 'pending' NOT NULL,
    operation_type VARCHAR(20) DEFAULT 'install' NOT NULL,
    result_log TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    PRIMARY KEY (id),
    FOREIGN KEY (host_id) REFERENCES host (id) ON DELETE CASCADE
);
CREATE INDEX ix_installation_requests_operation_type ON installation_requests (operation_type);
CREATE INDEX ix_installation_requests_requested_at ON installation_requests (requested_at);
CREATE INDEX ix_installation_requests_status ON installation_requests (status);

Migrations

Three Alembic chains

1
Registry chain
alembic/registry, recorded in alembic_version_registry. Control-plane tables.
2
Shared chain
alembic/shared, recorded in alembic_version_shared. Reference data.
3
Tenant chain
alembic/versions, recorded in alembic_version. Every host-scoped table; applied to the main database and to every tenant database.

In production, sysmanage-migrate (scripts/sysmanage_migrate.py) runs the registry, shared, and tenant chains, then applies the tenant chain to every tenant database listed in the registry, leasing each tenant's credentials from OpenBAO. It is safe to re-run, and --status and --dry-run show pending work without changing anything. See Database Migrations.

At Fleet Scale

  • Agent WebSocket handlers open a short-lived database session per message instead of holding one for the life of the connection, so the number of connections in use tracks work in flight, not connected agents.
  • At startup the server compares every worker's pool, plus the per-tenant pools, with PostgreSQL's max_connections and shrinks the pools with a warning if they would not fit. It never refuses to start over this.
  • Completed queue messages are purged after 7 days; failed messages are kept for troubleshooting.
  • With several workers, server-wide periodic tasks run in one elected leader; each worker still drains its own queue work.

Measured results are on Performance and Scale.
