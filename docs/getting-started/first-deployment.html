First Deployment

Plan and run a production SysManage server from the native package, with a real certificate, a locked-down firewall, monitoring and backups.

Production Deployment Overview

A production server is the same native package as in the Quick Start, installed on a host you plan for and look after. This guide covers the choices to make before you install, and the work that keeps the server healthy afterward. The package itself installs the service, nginx and OpenBAO, so there is no service file or reverse proxy to write by hand.

New to SysManage? Run through the Quick Start Guide first. The Server Installation Guide has the package for every platform.

1. Deployment Planning

Choose a deployment mode

SysManage runs in one of three deployment shapes. Most installations are single-tenant -- choose that unless you are specifically building a hosting service.

  • Homelab / on-prem (default): one server, one implicit tenant. The simplest setup -- everything in this guide applies as-is and nothing about the steps below changes.
  • Federated / air-gapped: multiple cooperating servers, or a fully offline appliance. These are server-role settings configured after install; they are unaffected by multi-tenancy and mutually exclusive with it.
  • SaaS / multi-tenant (opt-in): one control plane that hosts many isolated tenants, each in its own database. An advanced, opt-in mode that is off by default -- see the dedicated Deploying Multi-Tenancy guide.

Multi-tenancy is strictly opt-in: leaving it disabled (the default) preserves the classic single-tenant behavior, and homelab, on-prem, and federated installs are completely unaffected by it.

Infrastructure Requirements

Production Server Specifications

  • Size: about 3 CPU cores and 4 GB of memory per 10,000 agents, plus the database. The Scaling Guide has the measurements.
  • Storage: 100GB minimum (SSD preferred)
  • Network: a DNS name that matches the TLS certificate

Database Requirements

  • PostgreSQL: Version 12 or newer
  • Storage: Fast SSD with adequate IOPS
  • Backup: Automated backup solution
  • High Availability: a PostgreSQL cluster with failover, for critical deployments; see PostgreSQL High Availability

Network Architecture

Plan your network architecture considering these components:

  • Web interface and API: inbound HTTPS on 443, served by nginx. Port 80 only redirects to it.
  • Agents: connect out to the same name on port 443. Nothing needs to reach the agents, and they open no listening port.
  • Database: Internal network only (port 5432)
  • Loopback only: the SysManage API (127.0.0.1:8080) and OpenBAO (127.0.0.1:8200) stay behind nginx and must not be exposed.

2. Install the Server Package

Install the server from the signed package for your platform. On Ubuntu that is the Launchpad PPA; the Server Installation Guide gives the command for Debian, the RHEL family, openSUSE, Arch Linux, Alpine, Snap, macOS, Windows and the BSDs.

sudo add-apt-repository ppa:bceverly/sysmanage
sudo apt update
sudo apt install sysmanage

The package creates the sysmanage service account, the service, /etc/sysmanage.yaml with secrets generated for this host, an nginx site and an unsealed OpenBAO. It leaves the service stopped until the database is ready.

3. Database Setup

PostgreSQL Installation

Ubuntu/Debian

# Install PostgreSQL
sudo apt update
sudo apt install postgresql postgresql-contrib

# Create database and user
sudo -u postgres createuser sysmanage
sudo -u postgres createdb sysmanage -O sysmanage
sudo -u postgres psql -c "ALTER USER sysmanage WITH PASSWORD 'your-secure-password';"

RHEL and compatible distributions

# Install PostgreSQL
sudo dnf install postgresql postgresql-server postgresql-contrib

# Initialize database
sudo postgresql-setup --initdb
sudo systemctl enable --now postgresql

# Create database and user
sudo -u postgres createuser sysmanage
sudo -u postgres createdb sysmanage -O sysmanage
sudo -u postgres psql -c "ALTER USER sysmanage WITH PASSWORD 'your-secure-password';"

Database Security

Configure authentication in /etc/postgresql/*/main/pg_hba.conf:

# Local connections
local   sysmanage    sysmanage                     scram-sha-256
host    sysmanage    sysmanage    127.0.0.1/32     scram-sha-256
host    sysmanage    sysmanage    ::1/128          scram-sha-256

Every server worker keeps its own connection pool, so PostgreSQL's max_connections must hold all of them. The Scaling Guide gives the formula.

4. Configuration and TLS Certificate

Set the database password and your own email address as admin_userid in /etc/sysmanage.yaml, then run the migrations:

sudo vim /etc/sysmanage.yaml
sudo sysmanage-migrate --status
sudo sysmanage-migrate

nginx refuses to start without a certificate, on purpose. By default it reads /etc/sysmanage/tls/server.crt and /etc/sysmanage/tls/server.key. To use Let's Encrypt, follow Step 4 of the installation guide: it covers the HTTP and DNS challenges and the renewal hooks, so renewals reload nginx without your help.

Agents verify the server's certificate by default. A self-signed certificate is only suitable for a test server, because every agent would have to be told to trust it.

sudo nginx -t
sudo systemctl start sysmanage
sudo systemctl restart nginx
sudo systemctl status sysmanage

5. Firewall Configuration

Allow SSH for yourself, HTTPS and the HTTP redirect, and nothing else. Agents need no inbound port on the server beyond 443.

UFW (Ubuntu/Debian)

# Allow SSH (adjust port as needed) before enabling the firewall
sudo ufw allow 22/tcp

# Allow HTTP and HTTPS
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Enable firewall and check status
sudo ufw enable
sudo ufw status verbose

Firewalld (RHEL and compatible)

# Enable firewall
sudo systemctl enable --now firewalld

# Allow services
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https

# Reload configuration and check status
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

6. Monitoring and Logging

Logs

The server writes /var/log/sysmanage/backend.log and rotates it itself: once a day, compressed, keeping 14 days. No logrotate rule is needed. The service's output also goes to the journal: journalctl -u sysmanage.

Health Monitoring

Point your monitoring at the health endpoints. /api/health answers while the server is up, and /api/health/db checks the database connection as well:

#!/bin/sh
# SysManage health check
URL="https://sysmanage.example.com/api/health/db"
RESPONSE=$(curl -s -o /dev/null -w "%{http_code}" "$URL")

if [ "$RESPONSE" = "200" ]; then
    echo "SysManage is healthy"
    exit 0
else
    echo "SysManage health check failed (HTTP $RESPONSE)"
    exit 1
fi

Performance Monitoring

Monitor these key metrics:

  • System Resources: CPU, memory, disk usage
  • Database Performance: Connection count, query performance
  • Application Metrics: Response times, error rates
  • Agent Connectivity: Connected agents, communication errors

With telemetry enabled, the server also exports OpenTelemetry traces and metrics and serves Prometheus metrics on 127.0.0.1:9090; see Optional Features.

7. Backup Strategy

Database Backup

Create automated database backup script:

#!/bin/sh
# Database backup script

BACKUP_DIR="/var/backups/sysmanage"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="sysmanage_backup_$DATE.sql"

mkdir -p "$BACKUP_DIR"
sudo -u postgres pg_dump sysmanage > "$BACKUP_DIR/$BACKUP_FILE"
gzip "$BACKUP_DIR/$BACKUP_FILE"

# Keep only last 30 days of backups
find "$BACKUP_DIR" -name "*.gz" -mtime +30 -delete

Configuration Backup

Back up the configuration file, the certificate directory and the OpenBAO unseal material. Keep /var/lib/openbao/init.json somewhere off this machine: without it, the secrets in OpenBAO cannot be recovered if the host is rebuilt.

sudo tar -czf /var/backups/sysmanage/config_$(date +%Y%m%d).tar.gz \
    /etc/sysmanage.yaml \
    /etc/sysmanage/ \
    /var/lib/openbao/init.json \
    /etc/letsencrypt/

See Backup for restoring a server.

8. High Availability

A single SysManage server is the supported topology today. One server runs several worker processes and scales to tens of thousands of agents; the Scaling Guide has the measurements. Running several SysManage servers behind a load balancer is not supported yet: it is planned.

The database can be highly available now. The server runs against a PostgreSQL cluster and rides through a primary failover on its own; PostgreSQL High Availability describes the connection endpoint, what the server does during a failover, and a local test rig. Common choices:

  • Patroni: Automatic failover and leader election
  • PostgreSQL Streaming Replication: Built-in replication
  • Cloud Solutions: AWS RDS, Azure Database, Google Cloud SQL

For several sites, each with its own server, see Multi-Site Federation (Professional+ Enterprise).

9. Security Hardening

System Security

  • Keep system packages updated
  • Disable unnecessary services
  • Configure fail2ban for SSH protection
  • Use strong passwords and SSH keys
  • Regular security audits

Application Security

  • Install SysManage updates through your package manager
  • Remove the recovery admin account from the configuration file once you have your own administrator
  • Database connection encryption
  • Proper certificate management
  • Network segmentation

10. Troubleshooting

Common Issues

Service Won't Start

  • Check systemd logs: journalctl -u sysmanage
  • Verify configuration file syntax
  • Confirm the database migrations ran
  • Ensure database is accessible

SSL Certificate Issues

  • Run sudo nginx -t: it names the file it could not read
  • Check certificate expiration
  • Ensure proper file permissions
  • Test certificate with openssl

Database Connection Issues

  • Test database connectivity
  • Check PostgreSQL configuration
  • Verify authentication settings
  • Monitor connection pool usage

Performance Issues

  • Monitor system resources
  • Check database query performance
  • Review application logs
  • Optimize configuration settings

See Server Troubleshooting for more.
