Agent Setup and Approval

Learn how to install, configure, and approve SysManage agents on your hosts for comprehensive monitoring.

Agent Overview

SysManage agents are lightweight services that run on your hosts to collect system information, manage packages and carry out administrative tasks. Each agent connects out to the server over HTTPS on port 443 and keeps one secure WebSocket open; the agent itself opens no listening port.

Before you start: your SysManage server must be running and reachable by the name on its TLS certificate. See the First Deployment guide if needed.

Agent Features

  • System Monitoring: Hardware specs, uptime, resource usage
  • Package Management: Inventory, updates, installations
  • Cross-Platform: Linux, BSD, macOS, Windows support
  • Secure Communication: TLS to the server, with a per-host credential issued at approval
  • Privileged Operations: on Linux, an unprivileged service account with a sudo allowlist

1. Agent Installation

Install the agent from the package for your platform, as the Agent Installation Guide describes: the Launchpad PPA on Ubuntu, the package repositories for the other Linux distributions, and the prepackaged installers for macOS, Windows and the BSDs. You do not need to build it from source.

On Ubuntu, for example:

sudo add-apt-repository ppa:bceverly/sysmanage-agent
sudo apt update
sudo apt install sysmanage-agent

2. Agent Configuration

Configuration File Location

The agent configuration file is located at:

  • On Linux, macOS and the BSDs: /etc/sysmanage-agent.yaml
  • On Windows: C:\ProgramData\SysManage\sysmanage-agent.yaml

The package writes this file from its example the first time it installs, and keeps it on upgrade.

Basic Configuration

Set server.url to your server, by the name on its certificate. The API, the web interface and the agent connection share that one origin, so there is no port to add. Leave certificate verification on.

server:
  url: "https://sysmanage.example.com"
  verify_ssl: true
  # Behind a TLS-inspecting proxy, trust its root certificate instead of
  # turning verification off:
  # ca_bundle: "/etc/ssl/certs/corporate-root.pem"
  # An outbound HTTP proxy, if the environment does not already set one:
  # proxy: "http://proxy.example.com:3128"

security:
  # Optional: a registration key that approves this host automatically
  # (see "Automatic approval" below).
  # registration_key: "paste-the-key-here"
  # Multi-tenant servers only: the enrollment token that picks the tenant.
  # enrollment_token: "paste-the-token-here"

logging:
  file: "/var/log/sysmanage-agent/agent.log"

The agent reads its configuration only when it starts, so restart it after every change (see Service Management). The Agent Configuration Guide describes every setting.

3. Approving the Host

A new agent registers and waits. Until a host is approved, the server accepts nothing else from it. When you approve it, the server issues the host its own agent credential, and from then on the server refuses any session for that host that cannot present it.

Web Interface Approval

  1. Log into the SysManage web interface
  2. Open the Hosts page. New hosts are listed as pending approval.
  3. Check that the host name and address are the machine you just installed
  4. Select the host and click Approve

API Approval

Approve agents programmatically via API:

# List hosts (pending registrations appear with an unapproved status)
curl -H "Authorization: Bearer $JWT_TOKEN" \
    https://sysmanage.example.com/api/v1/hosts

# Approve a host by id
curl -X PUT -H "Authorization: Bearer $JWT_TOKEN" \
    https://sysmanage.example.com/api/v1/host/{host_id}/approve

Automatic Approval with a Registration Key

To skip the manual step for hosts you deploy yourself, create a registration key under Settings → Access Groups, with auto-approval turned on. A key can also place the host in an access group. The key is shown once, when you create it; copy it then. Put it in each agent's configuration as security.registration_key before the agent first starts. Registration keys need a Professional+ Enterprise license.

Anyone who holds an auto-approving key can enroll a machine into your fleet, so treat it like a password: deliver it with your configuration management, and delete the key when the rollout is done.

On a multi-tenant server, the agent also needs the tenant's enrollment token as security.enrollment_token. See Deploying Multi-Tenancy.

Re-enrolling a Reinstalled Agent

An approved host has an agent credential, issued once when the host enrolled; the server refuses any session that cannot present it. An agent that was reinstalled, or whose data directory was wiped, has lost that credential, and the server refuses it every time it connects.

To let it back in, open the host's page and click Re-enroll Agent (it needs the Approve Host Registration role). This clears the host's credential and returns the host to pending approval. The next agent that connects as this host gets a new credential; approve the host again, and the agent is back.

The host goes back to pending on purpose: until you approve it again, nothing the new agent sends is accepted, so clearing a credential can never hand an approved host to whoever connects first. Check that the agent waiting for approval is the reinstalled machine (its address, its hostname) before you approve it.

The same action through the API:

# Clear a host's credential and return it to pending approval
curl -X POST -H "Authorization: Bearer $JWT_TOKEN" \
    https://sysmanage.example.com/api/v1/host/{host_id}/reenroll

4. Service Management

The packages install the agent as a service that starts at boot. Restart it after changing the configuration:

sudo systemctl restart sysmanage-agent                     # Linux (systemd)
sudo rc-service sysmanage-agent restart                    # Alpine Linux
sudo launchctl kickstart -k system/com.sysmanage.agent     # macOS
Restart-Service SysManageAgent                              # Windows (administrator PowerShell)
sudo service sysmanage_agent restart                       # FreeBSD, NetBSD
doas rcctl restart sysmanage_agent                         # OpenBSD

To check that it is running:

sudo systemctl status sysmanage-agent                      # Linux (systemd)
sudo launchctl list | grep sysmanage                       # macOS
Get-Service SysManageAgent                                  # Windows

5. Verification

Web Interface Checks

  • Agent appears in the Hosts list
  • Status shows as "Online" or "Connected"
  • System information is populated
  • Package inventory is available
  • Last contact time is recent

Log File Checks

The agent logs to /var/log/sysmanage-agent/agent.log, or C:\ProgramData\SysManage\logs\agent.log on Windows.

# Follow the log while the agent connects
sudo tail -f /var/log/sysmanage-agent/agent.log

# Look for certificate and connection problems
grep -i "certificate\|ssl\|tls" /var/log/sysmanage-agent/agent.log
grep -i "error\|failed\|timeout" /var/log/sysmanage-agent/agent.log

6. Deploying to Many Hosts

To install the agent across a fleet, install the same packages with your configuration management tool and deliver the configuration file with it. Deploying the Agent to Many Hosts has an Ansible example for the Linux package repositories.

7. Troubleshooting

Common Issues

Agent Not Connecting

  • Check network connectivity to server
  • Check server.url: the name must match the server's certificate
  • Allow outbound port 443 from the host to the server
  • Verify SSL certificate configuration

Host Stays Pending

  • Approve it on the Hosts page
  • With a registration key, check that the key still exists, allows auto-approval, and is under security in the file
  • A reinstalled host needs Re-enroll Agent, then approval

Service Start Issues

  • Check configuration file syntax
  • Verify file permissions
  • Review systemd logs

Diagnostic Commands

# Can this host reach the server?
curl -sS https://sysmanage.example.com/api/health

# Which certificate does the server present?
openssl s_client -connect sysmanage.example.com:443 -servername sysmanage.example.com </dev/null

# Agent service log (systemd)
sudo journalctl -u sysmanage-agent -n 100

See Agent Troubleshooting for more.

8. Security Considerations

Network Security

  • Use firewall rules to restrict agent communication
  • Monitor network traffic for anomalies
  • Consider network segmentation
  • Use VPN for remote agents if needed

Privileged Operations

  • Keep the sudo allowlist the package installs; widen it only for commands you need
  • Audit privileged operations
  • Approve only hosts you recognize
