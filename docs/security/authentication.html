Authentication & Authorization

How users sign in to SysManage, how their sessions work, and how access is controlled.

Authentication Overview

Users sign in with their email address and password. Passwords are stored as Argon2 hashes. Everything on this page is part of every edition, including Community, except the external identity providers described at the end, which need Enterprise.

Tokens and Sessions

  • Access token: a successful sign-in returns a JSON Web Token signed with HS256 using the server's security.jwt_secret. It carries the user's id, its expiry and, on a multi-tenant server, the active tenant. Its lifetime is security.jwt_auth_timeout seconds (the example configuration uses 600).
  • Refresh token: set as an HTTP-only cookie (Secure and SameSite=Strict when the site is served over HTTPS). The web interface uses it to obtain a new access token when the current one expires. Its lifetime is security.jwt_refresh_timeout seconds.
  • Signing everyone out: tokens are not stored on the server, so an individual token cannot be revoked before it expires. Changing security.jwt_secret invalidates every token at once.
  • API keys: for automation, a user can create API keys. A key starts with smk_, is sent in the same Authorization: Bearer header as a token, and acts as that user. Only a SHA-256 hash of the key is stored, so it is shown once when created. An API key cannot be used to create further API keys.

Multi-Factor Authentication (MFA)

Users enroll from their profile page. After enrollment, sign-in asks for a second factor, which can be any of the following:

  • Authenticator app (TOTP): works with Google Authenticator, Microsoft Authenticator and other TOTP apps. Codes are 6 digits every 30 seconds by default (configurable to 6-8 digits and 15-120 seconds). The shared secret is stored encrypted in the database, with a key from security.mfa_encryption_key or, if that is not set, derived from the JWT secret.
  • Backup codes: generated when enrollment is confirmed (10 by default), shown once, stored as Argon2 hashes, and each usable once. Users can regenerate them.
  • Email code: a 6-digit code valid for 10 minutes and usable once. Requesting a new code invalidates any earlier unused one. The request endpoint gives the same answer whether or not the account is enrolled, so it cannot be used to discover accounts.

An administrator can require MFA for every user in the MFA settings. A user who has not enrolled by the end of the grace period (14 days after the account was created, by default) can no longer sign in until they enroll.

Password Policies

The password policy is set in the security.password_policy block of sysmanage.yaml; a password_policy setting stored in the database (for the server or for a tenant) overrides it. The available rules and their defaults:

SettingDefault
min_length8
max_length128
require_uppercase, require_lowercase, require_numbers, require_special_charsfalse
min_character_types1
allow_username_in_passwordtrue

Account Lockout and Throttling

An account locks after security.max_failed_logins failed sign-ins (default 5) for security.account_lockout_duration minutes (default 15). The server also throttles repeated failed attempts from one client address. A user with the Unlock User role can unlock an account early. Sign-in attempts, successful or not, are recorded with the client address.

Recovery Administrator

The security.admin_userid and security.admin_password settings define a recovery account for first sign-in or for getting back in when no other administrator can. The password is read from OpenBAO when available. A placeholder password is never accepted. Once real administrator accounts exist, remove these settings; the server shows a security warning while they are present.

Role-Based Access Control (RBAC)

What a signed-in user may do is decided by the security roles assigned to them; the server checks the required role on each protected request and answers HTTP 403 when it is missing. See Role-Based Access Control.

External Identity Providers (Enterprise)

With an Enterprise license, users can sign in through LDAP or Active Directory, OpenID Connect, or SAML, and an identity provider can provision users through SCIM. Without the license these endpoints return HTTP 402. See External Identity Providers.

Troubleshooting Authentication

  • HTTP 422 at sign-in: the user id must be an email address.
  • Frequent "session expired" messages: check the server and browser clocks, and the jwt_auth_timeout and jwt_refresh_timeout values.
  • TOTP codes rejected: the phone's clock is probably off; enable automatic time on the device, or use a backup code.
  • "Account locked": wait for the lockout period, or ask a user with the Unlock User role to unlock the account.
