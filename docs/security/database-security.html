Database Security

UUID primary keys, the secure installation script, and database hardening guidance.

UUID-Based Primary Key Architecture

SysManage uses random UUIDs instead of sequential integers as the primary keys of almost all of its tables (a few small configuration tables still use integers). Resource URLs therefore contain identifiers that cannot be guessed from one another.

Security Benefits

ID Enumeration Attack Prevention

Sequential IDs (1, 2, 3...) allow attackers to easily enumerate resources. UUIDs eliminate this vulnerability by using non-predictable identifiers.

Vulnerable (Sequential):
GET /api/v1/hosts/1, /api/v1/hosts/2, /api/v1/hosts/3...
Secure (UUID):
GET /api/v1/hosts/a1b2c3d4-e5f6-7890-abcd-ef1234567890

Harder Automated Scanning

An attacker cannot list resources by counting upward; they would need to know each identifier.

Information Leakage Prevention

Sequential IDs can reveal business metrics (number of users, hosts, etc.). UUIDs prevent this information disclosure.

No Identifier Conflicts

UUIDs are globally unique, so records can move between databases (for example between tenant databases) without identifier conflicts.

Secure Installation Script

For an installation from source, scripts/sysmanage_secure_installation sets up a new installation; the platform installers do the equivalent. It drops and recreates every database table, so run it only on a new installation.

Script Location

scripts/sysmanage_secure_installation

Security Features Implemented

Initial Admin User Creation

  • Prompts for the first administrator's email address and password (at least 8 characters)
  • Reads the password without echoing it
  • Stores it as an Argon2 hash

JWT Security Token Generation

  • Generates a new JWT secret from 64 random bytes
  • Uses Python's secrets module, a cryptographically secure random source
  • Prevents credential reuse across installations

Password Salt Generation

  • Creates a new password salt from 32 random bytes for each installation

OpenBAO Initialization

  • Initializes and unseals OpenBAO if it is installed
  • Saves the unseal key and root token to a file with mode 0600
  • Writes the OpenBAO connection settings into the configuration file

Security Requirements

  • Mandatory execution: Run the script, or a platform installer, before first use
  • Run once only: Run it once; running it again drops all data
  • Configuration backup: Back up the configuration file and the OpenBAO credentials file afterward
  • No default credentials: The placeholder recovery password in the example configuration never signs in, and the server shows a security warning while a default password salt is in use

Implementation Details

Database Schema Design

Primary keys are random (version 4) UUIDs.

API Security Considerations

UUID Validation

  • Identifier path parameters are validated as UUIDs
  • Pydantic models enforce UUID typing
  • Malformed identifiers are refused with an error instead of reaching the database

Authorization Checks

  • Role-based access control applied to UUID-referenced resources

Database Security Best Practices

Production Deployment

  • Enable database encryption at rest
  • If PostgreSQL is on another machine, require TLS on the PostgreSQL side (hostssl in pg_hba.conf)
  • Keep the database password in OpenBAO or in a configuration file only the server account can read
  • Restrict database network access
  • Implement database activity monitoring

Backup and Recovery

  • Use encrypted database backups
  • Store backups in secure locations
  • Implement backup access controls
  • Regularly test backup restoration
  • Follow data retention policies

Maintenance and Updates

  • Apply security patches promptly
  • Test database migrations in staging
  • Review schema changes for security implications
  • Maintain comprehensive audit logs
  • Monitor database performance and security metrics

Migration from Sequential IDs

Earlier versions of SysManage used sequential integer IDs; they were converted to UUIDs by Alembic migrations.

Migration Process

Step 1: Schema Migration

Alembic migrations converted all primary keys and foreign keys from integers to UUIDs

Step 2: Data Migration

Existing data was migrated with new UUID identifiers while preserving relationships

Step 3: API Updates

All API endpoints updated to handle UUID parameters and responses

Step 4: Frontend Updates

Frontend components updated to work with UUID identifiers

Post-Migration Security Benefits

  • Eliminated ID enumeration vulnerabilities
  • Prevented information disclosure through predictable IDs
