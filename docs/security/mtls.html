Agent Certificates and TLS

How agent-to-server traffic is encrypted, how an agent knows it is talking to its own server, how the server knows which host it is talking to, and how to turn mutual TLS on across a fleet.

Summary

  • Encryption: agents connect outbound to the server over HTTPS and a WebSocket on the same port (normally 443, served by nginx). The agent refuses anything older than TLS 1.2, and the server offers only AEAD cipher suites (AES-GCM and ChaCha20-Poly1305 with forward secrecy).
  • Server authentication: the agent verifies the server's certificate against the system trust store, or against a CA file you name in server.ca_bundle, and then checks it against the server identity it pinned when it enrolled. A proxy or another server presenting a different key is refused, even with a certificate the system trusts.
  • Agent authentication: each host is identified by a secret host token issued when it registers, not by its hostname. See Agent Identity.
  • Approval: a newly registered host is pending until an administrator approves it. The server does not process messages from, or queue commands to, a host that is not approved.
  • Client certificates: once a host is approved, its agent generates a key of its own, which never leaves the host, and the server's CA signs a certificate for it. The agent presents that certificate on every connection, and the server checks that the certificate and the host token name the same host. Whether a certificate is required is set by the mutual TLS mode below.

The Server's Certificate Authority

On first start the server creates a private CA and, from it, a server certificate. They live in the certificate directory: /etc/sysmanage/certs on Linux, macOS and the BSDs, C:\ProgramData\SysManage\certs on Windows, or the path set in certificates.path (or the SYSMANAGE_CERT_PATH environment variable).

Private keys are written with mode 0600; the CA and server certificates are 0644 so that a non-root process can read them to validate the chain.

In most installations nginx terminates TLS on port 443 with the certificate you configure for it (for example one from your corporate CA or a public CA), and agents validate that certificate. If agents should trust the server's own CA instead, download it from /api/certificates/ca-certificate and point server.ca_bundle at it.

The CA is what every host certificate and every agent's pin chains to. Keep it in the server's backup (see Backing Up and Recovering the Server): a server rebuilt with its old CA is recognized by every agent, and one with a new CA is refused by all of them.

Host Certificate Lifecycle

  1. Registration: the agent registers and the host is created with status pending.
  2. Approval: an administrator approves the host in the web interface.
  3. Request: the agent generates an EC P-256 key, writes it with mode 0600, and sends a certificate request to POST /api/agent/certificate with its host credentials. The server answers only for an approved host, signs the certificate with its CA and records its serial number on the host. The private key never leaves the host.
  4. Storage: the agent keeps client.key, client.crt and the CA's ca.crt in its configuration directory (/etc/sysmanage-agent, or C:\ProgramData\SysManage on Windows), replacing the files in one step so a half-written certificate is never used.
  5. Renewal: the agent checks at startup, every 24 hours, on approval and after a refused connection, and requests a new certificate 30 days before the current one expires. For a day after a renewal the server still accepts the previous certificate. An expired certificate is never presented: the host requests a new one on its token, and the Hosts list shows it as Expired until it has one.
  6. Revocation: revoking a host's certificate (POST /api/certificates/revoke/{host_id}) clears it from the host record, sets the host's status to revoked and writes an audit log entry. The server accepts only the serial number it last issued to a host, so a revoked or deleted host's certificate is refused at once, with no revocation list to distribute.

The Hosts list shows each approved host's certificate state: Presented, Renewing, Not presented, Expired or None.

The Agent Pins Its Server

When it enrolls, the agent pins two things in server_pins.json: the SysManage CA, and the public key of the TLS certificate the server presented. On every connection it compares the server's public key with its pins right after the handshake, and refuses a mismatch, saying why in its log. A trusted certificate is not enough: a proxy or another server that presents a different key is refused.

A public certificate that renews every 60 to 90 days, such as one from Let's Encrypt, often comes with a new key. The server publishes the keys it serves in a statement signed with its CA-issued identity, at GET /api/agent/server-identity. The agent pins a new key only when such a statement, chained to the CA it pinned, names exactly the key it saw on that connection, so a proxy can neither forge the statement nor reuse it. The server reads its keys from its own nginx, or from agent_tls_spki in Settings when nginx runs elsewhere.

A different CA is never pinned automatically. After a deliberate change of server or CA, reset the pins on each agent host with the agent's own Python, in its install directory: cd /opt/sysmanage-agent && sudo .venv/bin/python -m src.security.pin_reset (add --certificate to drop the host certificate too and start over). On a network where a TLS-inspecting proxy re-signs all traffic, set server.tls_inspection: true in the agent configuration: pinning is then off, and the agent logs that it is.

Turning On Mutual TLS

The mode is set on Settings -> Configuration, in the Agent certificates (mutual TLS) card, for each tenant when multi-tenancy is on. The card counts how many approved hosts present a valid certificate.

ModeWhat the server accepts
OffClient certificates are ignored. Agents connect with their host token alone.
Optional (the default)A certificate an agent presents must be valid for its host; an agent with none still connects on its host token. Older agents keep working.
EnforcedEvery approved host must present a valid certificate. A host without a current one may still request one, and nothing else.

In every mode but Off, a certificate that is presented and wrong is refused: signed by another CA, expired, issued to another host, or not the host's current one.

  1. Let nginx ask for the certificate. The packages for Ubuntu, Debian, the RHEL family, openSUSE, Alpine, macOS and NetBSD write /etc/sysmanage/nginx/agent-mtls.conf when they install or upgrade and the SysManage CA exists, and keep it only if nginx -t passes. It holds two lines. nginx then asks every client for a certificate, but names only the SysManage CA, so browsers are never prompted.
ssl_verify_client optional_no_ca;
ssl_client_certificate /etc/sysmanage/certs/ca.crt;
  1. Where you edit nginx yourself (FreeBSD, OpenBSD, the snap, Windows, or a site file you changed, which an upgrade leaves alone): add those two lines to the server block, and in the two agent locations (/api/ and /ws) pass the verified certificate to the server. Then run nginx -t and reload nginx.
proxy_set_header X-SSL-Client-Cert $ssl_client_escaped_cert;
  1. Update the agents and leave the mode at Optional. Each agent requests its certificate on its next start and presents it from then on. Watch the Agent certificates card until every approved host presents one.
  2. Set the mode to Enforced. While some approved hosts still present no certificate, the server refuses the change and says how many; Enforce anyway confirms it.

nginx sets X-SSL-Client-Cert from its own variable, so a header sent by a client is discarded. nginx proves the agent holds the key; the server checks the rest: the CA's signature, the dates, the host and the serial number. Air-gapped servers work the same way, with nothing to fetch from outside.

Troubleshooting TLS Connections

Certificate Validation Failures

  • Symptoms: Agents cannot connect, TLS handshake failures
  • Causes: The server's certificate is expired, or its issuer is not in the agent's trust store or server.ca_bundle; a TLS-inspecting proxy re-signs traffic with its own CA
  • Solutions: Renew the server certificate, or set server.ca_bundle to the CA that signs it. verify_ssl: false turns verification off entirely and is meant only for labs.

The Agent Refuses the Server

  • Symptoms: the agent logs that the server's key does not match its pins, and does not connect
  • Causes: a proxy between the agent and the server presents its own certificate; the server was rebuilt with a new CA; the agent was pointed at a different server
  • Solutions: find out which first. For a deliberate change, reset the pins on the agent host with pin_reset, as described above. For a TLS-inspecting proxy, set server.tls_inspection: true. For a rebuilt server, restore its old CA from the backup instead.

A Host Shows Not Presented

  • Symptoms: the Hosts list shows Not presented for a host that has a certificate
  • Solutions: nginx is not asking for it. Check that /etc/sysmanage/nginx/agent-mtls.conf exists and that both agent locations set X-SSL-Client-Cert, then run nginx -t and reload nginx.

Clock Synchronization

  • Symptoms: "Certificate not yet valid" or "expired" errors
  • Causes: System clock drift, timezone issues
  • Solutions: Configure NTP, check timezone settings

Host Stays Pending

  • Symptoms: the Hosts list shows the host's certificate as None
  • Solutions: approve the host on the Hosts page; the agent requests its certificate as soon as it learns it is approved

Diagnostic Commands

# Show the certificate the server presents, and whether it validates
openssl s_client -connect sysmanage.company.com:443 \
    -servername sysmanage.company.com -verify_return_error </dev/null

# Check the expiry of the server's own certificate (on the server)
openssl x509 -in /etc/sysmanage/certs/server.crt -noout -subject -dates

# Check a host's client certificate (on the agent host)
openssl x509 -in /etc/sysmanage-agent/client.crt -noout -subject -dates

# Check that nginx asks agents for a certificate (on the server)
sudo nginx -T 2>/dev/null | grep -E 'ssl_verify_client|X-SSL-Client-Cert'
