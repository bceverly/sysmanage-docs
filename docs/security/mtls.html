Agent Certificates and TLS

How agent-to-server traffic is encrypted, how the server knows which host it is talking to, and what the per-host certificates SysManage issues are for.

Summary

  • Encryption: agents connect outbound to the server over HTTPS and a WebSocket on the same port (normally 443, served by nginx). The agent refuses anything older than TLS 1.2, and the server offers only AEAD cipher suites (AES-GCM and ChaCha20-Poly1305 with forward secrecy).
  • Server authentication: the agent verifies the server's certificate against the system trust store, or against a CA file you name in server.ca_bundle in the agent configuration.
  • Agent authentication: each host is identified by a secret host token issued when it registers, not by its hostname. See Agent Identity.
  • Approval: a newly registered host is pending until an administrator approves it. The server does not process messages from, or queue commands to, a host that is not approved.
  • Client certificates: when a host is approved, the server issues it a client certificate signed by the server's own CA, and the agent downloads and stores it. The current agent does not present this certificate during the TLS handshake, and the server does not request one, so connections are not mutually authenticated at the TLS layer today; agent authentication relies on the host token above.

The Server's Certificate Authority

On first start the server creates a private CA and, from it, a server certificate. They live in the certificate directory: /etc/sysmanage/certs on Linux, macOS and the BSDs, C:\ProgramData\SysManage\certs on Windows, or the path set in certificates.path (or the SYSMANAGE_CERT_PATH environment variable).

Private keys are written with mode 0600; the CA and server certificates are 0644 so that a non-root process can read them to validate the chain.

In most installations nginx terminates TLS on port 443 with the certificate you configure for it (for example one from your corporate CA or a public CA), and agents validate that certificate. If agents should trust the server's own CA instead, download it from /api/certificates/ca-certificate and point server.ca_bundle at it.

There is no automatic renewal of these certificates, no certificate revocation list and no OCSP responder. Plan to replace the server certificate before it expires.

Host Certificate Lifecycle

  1. Registration: the agent registers and the host is created with status pending.
  2. Approval: an administrator approves the host in the web interface. The server generates the host's key pair and client certificate, signs it with its CA and records the serial number on the host.
  3. Delivery: the agent requests /api/certificates/client/{host_id} with its bearer token. The server answers only for an approved host (HTTP 403 otherwise) and returns the client certificate, its key, the CA certificate and the server certificate's SHA-256 fingerprint.
  4. Storage: the agent writes them to its configuration directory (/etc/sysmanage-agent, or C:\ProgramData\SysManage on Windows), which it restricts to its own user; the private key file is mode 0600.
  5. Revocation: revoking a host's certificate (POST /api/certificates/revoke/{host_id}) clears the certificate from the host record, sets the host's status to revoked and writes an audit log entry. A revoked host is treated like an unapproved one until it is approved again.

The agent stores the server fingerprint it receives, but the current agent does not compare it with the server's certificate when it connects; server authentication relies on normal certificate validation.

Troubleshooting TLS Connections

Certificate Validation Failures

  • Symptoms: Agents cannot connect, TLS handshake failures
  • Causes: The server's certificate is expired, or its issuer is not in the agent's trust store or server.ca_bundle; a TLS-inspecting proxy re-signs traffic with its own CA
  • Solutions: Renew the server certificate, or set server.ca_bundle to the CA that signs it. verify_ssl: false turns verification off entirely and is meant only for labs.

Clock Synchronization

  • Symptoms: "Certificate not yet valid" or "expired" errors
  • Causes: System clock drift, timezone issues
  • Solutions: Configure NTP, check timezone settings

Host Stays Pending

  • Symptoms: The agent logs "Host not yet approved for certificate retrieval"
  • Solutions: Approve the host on the Hosts page; the agent fetches its certificate on its next attempt

Diagnostic Commands

# Show the certificate the server presents, and whether it validates
openssl s_client -connect sysmanage.company.com:443 \
    -servername sysmanage.company.com -verify_return_error </dev/null

# Check the expiry of the server's own certificate (on the server)
openssl x509 -in /etc/sysmanage/certs/server.crt -noout -subject -dates

# Check a host's stored client certificate (on the agent host)
openssl x509 -in /etc/sysmanage-agent/client.crt -noout -subject -dates
