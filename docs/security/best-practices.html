Security Best Practices

A checklist for running SysManage in production, tied to the settings and features that exist in the product.

Secrets and Credentials

  • Install with the platform installer or run sysmanage_secure_installation. They generate a random JWT secret, password salt and recovery administrator password for each installation. The server refuses to sign anyone in with a placeholder password.
  • Run OpenBAO and keep the server's sensitive settings there. The server reads the recovery administrator password, the license key and the MaxMind license key from OpenBAO first, and falls back to sysmanage.yaml only when OpenBAO is unavailable.
  • Once real administrator accounts exist, remove admin_userid and admin_password from the configuration file and restart. The server shows a security warning while they are present.
  • Keep /etc/sysmanage.yaml readable only by the account the server runs as.

TLS and Network Exposure

  • Give nginx a certificate from a CA your agents trust. On agents, leave verify_ssl on; if you use an internal or TLS-inspecting CA, set server.ca_bundle to it instead of turning verification off.
  • Use the nginx configuration shipped by the installer. It accepts TLS 1.2 and 1.3 with AEAD cipher suites only, redirects port 80 to 443, and sends HSTS and other security headers.
  • Keep nginx the only network listener. The backend listens on loopback port 8080, and the installers bind OpenBAO to 127.0.0.1:8200. Keep PostgreSQL on the same host or on a private network that only the server can reach.
  • Open only 443 (and 80, for the redirect) to the networks your administrators and agents come from. Agents connect outbound to the server; they need no inbound ports.
  • If a load balancer or reverse proxy sits in front of nginx, list it in security.trusted_proxies so the server logs and throttles the real client address. API rate limiting (api.rate_limit) is off by default; enable and tune it for your deployment if you need it.

See Network Security for the full port list.

User Accounts and Access

  • Turn on multi-factor authentication (TOTP, email codes and backup codes) and consider requiring it for every user; the MFA settings include a grace period for enrollment.
  • Set the password policy to your organization's standard. Accounts lock after repeated failed sign-ins (by default 5 failures, for 15 minutes; security.max_failed_logins and security.account_lockout_duration).
  • Grant each user only the security roles they need. See Role-Based Access Control.
  • Keep access tokens short-lived (security.jwt_auth_timeout, in seconds).
  • On Enterprise, connect your directory or identity provider (LDAP/Active Directory, OIDC or SAML) so that leavers lose access when their directory account is disabled.

Managed Hosts

  • Approve only hosts you recognize. A newly registered host is pending until an administrator approves it, and the server does not exchange data with it until then.
  • Revoke the certificate of a host you decommission or no longer trust; its status becomes revoked and it is treated as unapproved until approved again.
  • Keep agents and the server on current releases, and apply operating-system security updates to managed hosts through SysManage.

Auditing and Evidence

  • Review the audit log regularly. It records sign-ins, user and role changes, host approvals and certificate revocations, among other security-relevant actions.
  • Forward logs to your central log system. The server can also write to journald, syslog or the Windows Event Log (logging.native).
  • If you need configuration evidence for an audit, the commercial editions run compliance checks (about 50 checks from the CIS Benchmarks and DISA STIGs, focused on Linux) and, on Enterprise, FIPS mode management. These produce evidence you can give an auditor; SysManage itself is not certified or attested against SOC 2, ISO 27001, FedRAMP, PCI DSS or any other framework.

Backups

  • Back up the PostgreSQL database on a schedule and test restores.
  • Back up the certificate directory (/etc/sysmanage/certs). It holds the server's CA private key; protect the backup accordingly.
  • Back up OpenBAO's storage and keep its unseal key and root token somewhere safe and separate. Without them, the secrets stored in OpenBAO cannot be recovered.
  • For database availability, run PostgreSQL as a high-availability cluster; see PostgreSQL High Availability. Running more than one SysManage server for failover is not supported yet.

If You Suspect a Compromise

  1. A managed host: revoke its certificate so the server stops working with it, then investigate the host itself.
  2. A user account: deactivate or delete the account, and review its recent actions in the audit log.
  3. The server: change the JWT secret (this signs every user out), the password salt and the database and OpenBAO credentials, then review the audit log.
  4. A vulnerability in SysManage itself: report it as described in Vulnerability Reporting.
