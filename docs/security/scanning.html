Security Scanning

How the SysManage source code is checked for security problems before it is released.

Security Scanning Overview

This page is about the project's own development process: the scanners that run against the SysManage server, agent and documentation code in GitHub Actions and on developers' machines. It does not describe scanning your managed hosts. For that, see Vulnerability Scanning and Compliance.

Scanners in CI (Server Repository)

The Security Scanning workflow runs on every push and pull request to main and develop, weekly on Sundays at 02:00 UTC, and on demand. Results in SARIF format are uploaded to the repository's GitHub code-scanning view.

ToolWhat it checksEffect on the build
BanditPython static security analysis of the backend, at medium severity and aboveFails the build
SemgrepMulti-language static analysis rulesAdvisory in CI (reported to code scanning); make security-semgrep runs the local scan, which fails on a new finding
SafetyKnown vulnerabilities in Python dependenciesFails the build on a new vulnerability that is not covered by a reviewed ignore entry
pip-auditPython dependencies against the PyPI advisory databaseAdvisory (reported, does not fail the build)
npm auditKnown vulnerabilities in frontend dependencies, moderate severity and aboveAdvisory (reported, does not fail the build)
SnykFrontend dependencies, high severity and aboveReported to code scanning
ESLint security pluginsUnsafe patterns in the frontend sourceAdvisory (reported, does not fail the build)
TruffleHogVerified secrets committed to the repositoryReported in the workflow run

CodeQL analyzes the Python and JavaScript/TypeScript code on every push and pull request to main and develop and weekly on Mondays. SonarQube Cloud analyzes code quality, security hotspots and test coverage on every push to main.

The agent repository runs its own Security Scanning workflow with CodeQL, Semgrep, Safety, Bandit, Snyk and TruffleHog, plus SonarQube Cloud.

Release-Tag Penetration-Test Workflow

Each release tag in the server repository, and any on-demand run, starts an automated penetration-test workflow:

  • Trivy scans the repository filesystem for known CVEs in dependencies.
  • gitleaks searches the full Git history for committed secrets.
  • OWASP ZAP runs a baseline scan against a running server started from the release code.
  • The authentication and authorization test suite (tests marked security) runs against a real database.

This is an automated subset. An external penetration test performed by people is a separate engagement and is not part of CI.

Unforgivable-Vulnerability Tests

The server and agent CI workflows also run the "Lucky 13" test suite, which checks for each of the thirteen vulnerability classes in MITRE's Unforgivable Vulnerabilities paper. See the list of classes and how each is checked.

Running the Scans Locally

From a server checkout:

# Lucky 13 tests, Bandit, Safety, frontend security lint, secret patterns
make security

# Semgrep, matching what the pre-push hook runs
make security-semgrep

# Versions of security-critical packages, and which are outdated
make security-upgrades

A finding is fixed, or suppressed on the line where it occurs with a comment that gives the reason. The server repository lists its suppressions and their reasons in docs/security-suppressions.md.

Scanning Your Managed Hosts

The scanners above check SysManage's own code. For your fleet, the commercial editions provide:

  • Vulnerability scanning: installed packages on each host compared with CVE data.
  • Compliance checks: about 50 configuration checks drawn from the CIS Benchmarks and DISA STIGs, focused on Linux hosts. Their results are evidence you can use in an audit; running them does not certify a system against any standard.
