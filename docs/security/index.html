Security Documentation

Security features, configuration, and recommended practices for SysManage deployments.

Security Overview

This section describes how SysManage authenticates users and agents, protects traffic and stored secrets, and how the code itself is tested and scanned. Each page states which edition a feature needs.

Core Security Features

Authentication & Authorization

JWT-based authentication with short-lived access tokens, multi-factor authentication, role-based access control (RBAC), and configurable password policies.

Agent Transport Security

TLS 1.2 or later with AEAD cipher suites, server certificate validation by the agent, per-host tokens, and administrator approval of new hosts.

Security Scanning

The SysManage source code is scanned in CI with Bandit, Semgrep, Safety, pip-audit, npm audit, Snyk, CodeQL, and TruffleHog.

Network Security

TLS 1.2+ encryption, secure WebSocket communication, CORS protection, login throttling, and optional API rate limiting.

Multi-Tenant Isolation

Physical per-tenant database isolation for the Multi-Tenant SaaS edition -- no shared schema, no tenant_id column to forget.

  • A separate, physically isolated database for every tenant
  • OpenBAO-brokered, short-lived, per-tenant database credentials
  • Least-privilege provisioning -- the server holds no cluster superuser
  • Fail-loud routing that never guesses a tenant
  • Server-global identity with per-tenant data -- the identity boundary

Tested for MITRE's "Lucky 13" Unforgivable Vulnerabilities

In 2007 Steve Christey of MITRE presented Unforgivable Vulnerabilities at Black Hat USA: thirteen classes of weakness so well documented, so obvious and so cheap to find that shipping one is unforgivable. SysManage tests for every one of them explicitly.

The server, agent and documentation repositories run these checks in CI as a named step on every push; Professional+ runs them on every release build. Each repository runs them locally with make test-lucky13 and checks the classes that apply to it. A finding is fixed, or recorded on a reviewed allow-list together with the reason it is safe.

#Vulnerability classHow SysManage checks it
1Buffer overflow (CWE-120)Oversized values, such as 100 KB strings, in every sign-in and enrollment field and every path parameter must be refused cleanly and never crash the server.
2Cross-site scripting (CWE-79)No unreviewed raw-HTML output in the web interface or on this site; machine translations are sanitized before they are rendered.
3Directory traversal (CWE-23)../.. and absolute paths in every path parameter are refused.
4Remote file inclusion (CWE-98)No code is ever loaded from request data; Professional+ engines are loaded only after their signature is verified.
5SQL injection (CWE-89)' OR 1=1 in the login and in every id parameter neither signs anyone in nor reaches the database as SQL.
6World-writable files (CWE-276, CWE-279)Installers, scripts and code never give other users write access to files or directories.
7Direct request (CWE-425)Every API route requires a login or is on a reviewed public list with its reason; anonymous calls to every other route are refused.
8Authentication bypass with authenticated=1 (CWE-472)Forged cookies, headers and form fields that claim the caller is signed in or an administrator are ignored on every protected route.
9Grow-your-own cryptography (CWE-327)Only standard, reviewed libraries: no MD5 or SHA-1 for security, no DES, RC4, ECB mode or home-made ciphers.
10Privilege escalation through Help (CWE-271)Privileged code (the server, and the agent running as root or SYSTEM) never launches a browser, a help viewer or any other interface.
11Symlink following (CWE-61)No predictable temporary file names.
12Hard-coded or default passwords (CWE-259)No credentials in source code, tooling or workflows. The example configuration ships only placeholders; the installers generate each installation's JWT secret, password salt and recovery password, and a placeholder or well-known password is never accepted at sign-in.
13Integer overflow (CWE-190)0xffffffff, values beyond 64 bits and negative numbers in every numeric parameter are refused cleanly.

Agent Approval System

A newly registered host must be approved by an administrator before the server works with it:

Approval Workflow

  1. Agent Registration: A new agent registers and its host is created with "pending" status
  2. Messages Refused: The server does not process messages from, or send commands to, a host whose status is not "approved"
  3. Administrator Approval: Administrators review and approve agents through the web interface
  4. Certificate Generation: The server issues a client certificate to each approved host
  5. Full Operation: The approved agent's messages are processed and it receives commands over its TLS-protected WebSocket

Security Benefits

  • Authorized Hosts Only: A host that has not been approved cannot report data or receive commands
  • Manual Review: Administrators can verify each host before approval
  • Audit Trail: All approvals and rejections are logged

Vulnerability Reporting

We take security seriously and appreciate responsible disclosure of security vulnerabilities.

For Security Issues (DO NOT create public issues)

  1. Email: Send details to security@sysmanage.org
  2. Include:
    • Description of the vulnerability
    • Steps to reproduce
    • Potential impact assessment
    • Suggested fix (if available)
  3. Response Time: We will acknowledge receipt within 48 hours
  4. Updates: You'll receive updates every 7 days until resolution

Responsible Disclosure Process

  1. Initial Report: Security researcher reports issue privately
  2. Acknowledgment: We confirm receipt and begin investigation
  3. Investigation: We assess impact and develop fixes
  4. Fix Development: Patches are developed and tested
  5. Coordinated Release: Fix is released with security advisory
  6. Public Disclosure: Details shared after fix is available
