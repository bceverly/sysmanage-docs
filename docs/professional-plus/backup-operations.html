Backup Operations (Enterprise)

The Enterprise backup_ops_engine module runs backups across a fleet and across sites. It builds on the fleet backups every edition has and on Fleet Backups (Professional+): whether each host could be restored in time, a second person's approval before a restore overwrites a host's files, snapshots kept on legal hold, several backup targets, off-site copies another site cannot delete, moving a host to another target with its backups, and backup policies set once for every site.

Restore readiness

The Restore readiness card on the Backups page answers three questions for every host with a backup policy, worst first:

  • Recovery point (RPO): is the last good backup younger than the most data you can afford to lose? By default that is twice the policy's interval, so one missed night counts. Change it for a host from the card.
  • Recovery time (RTO): how long getting the latest snapshot back would take, from the best speed the host has shown: a real restore of 100 MB or more, else a full-read verification, else how fast its backups read, which the card labels an estimate.
  • Proof: has the repository been proven readable recently? A passing full-read verification within its schedule counts. A host without fresh proof shows Unproven however recent its backups are.

Each host is Never backed up, Recovery point missed, Unproven or Ready. Under federation, each site's counts appear with its backup status on the controller's page for that site.

Four-eyes approval of restores

With four-eyes approval on, a restore over a host's own files waits until someone else with the Restore Files role approves it. A restore into the agent's staging directory and every preview never wait. Turn it on with the switch on the Restores awaiting approval card, which needs the Manage Backups role. It is off until you turn it on, so a site with one administrator is never locked out of its own restores.

A held restore shows on the card with what was asked for, from which snapshot and by whom. Another person approves or rejects it; the person who asked can only withdraw it. Approving sends exactly the restore that was asked for, after checking that the host can still take it. A request nobody approves expires after 24 hours. Every request, approval, rejection and withdrawal is audited.

If the license lapses, nothing is held and restores run as they do without the module.

Legal hold

A snapshot on legal hold is kept by every prune of its repository until the hold is released, whatever the retention settings say. Use Legal hold on a host's Backup card: choose the snapshot, say whose hold it is (a case, a matter or a person) and why. The Legal holds card on the Backups page lists the holds in force and those recently released, and releases a hold. Placing and releasing are audited with the owner and the reason.

The storage host's restate must be 3.4.0.0 or later, which keeps named snapshots through a prune. SysManage refuses a hold on a storage host whose restate cannot honor it, rather than accept a hold that would be ignored.

If the license lapses, existing holds keep protecting their snapshots: every prune still keeps them. Placing and releasing a hold wait for a license.

Fleet restores

A fleet restore puts the same paths back on many hosts at once -- after an incident that touched a whole group of servers, for example. On the Backups page, Fleet restores > New fleet restore: name it, choose the hosts, list the paths (and any to leave out), and say where they go: a staging folder on each host, or over each host's own files, which you confirm. Preview only lists what would be restored and changes nothing.

Each host restores from its own snapshot: its newest, or, when you give a time, its newest taken before that time -- the last good one before the incident. A host with no snapshot that old is skipped and says so.

Hosts restore a few at a time (Hosts at a time, 5 unless you change it, at most 50), so the storage host is never overwhelmed; as each finishes, the next starts. Each host's restore is the same as one started from its own Backup card: the same checks, the same audit entry. A host that cannot take it -- not set up for backups, its storage unreachable -- is recorded with the reason and the others go on. Hosts on a job shows each host's state, the snapshot it restored from and any note. Cancel stops the hosts still waiting; restores already running finish.

With four-eyes approval on, a fleet restore over the hosts' own files waits as one request on the Restores awaiting approval card, naming the job and how many hosts it covers. Nothing is restored until someone else approves it, and a rejected, withdrawn or expired request never runs.

Several backup targets

Every edition has one backup target. With the module, Add another target on the Backups page adds more, each with its own storage host, capacity and health, and an optional location such as a site, room or building. Each target has its own card, and its storage host seals, prunes and checks only that target's repositories.

One target is Default for new hosts; Make default on another card changes it. A host's backup policy, a bulk setup and a backup policy by tag can each name another target; the target picker appears in those dialogs once there is more than one target. A target cannot share another's name, storage path on the same storage host (or a path inside it) or mount point. A target in use by a host or a policy by tag, or the default while others remain, cannot be deleted.

To move a host, choose another target in its backup policy. A host with no backups yet simply switches. A host with backups is copied to the new target first; see Moving a host with its backups.

With snapshot signing, each target's storage host signs with its own key. A break-glass key export names each host's own target and storage path and carries every target's public signing key; each host's entry in manifest.json says which file is its signing key.

If the license lapses, every target keeps backing up and restoring. No target can be added, no host can move between targets and the default does not change until the license is renewed.

Off-site copies

A target can copy every repository it holds to another target at another site. On the target's card, choose Off-site copy, then Change, and pick the target that keeps the copy. That target must be reached through restate-proxy and live on a different storage host.

After each host's nightly backup, its storage host copies every snapshot the off-site copy lacks, oldest first, through the off-site target's restate-proxy. It sends only the packs the copy does not have, and an encrypted snapshot is copied as it is, never decrypted. The copy keeps the same snapshots as the source policy, including any on legal hold. The off-site storage host protects, checks, prunes and seals its copy itself, and needs no key to do so.

The source storage host's token for the copy is granted append and nothing more, so the source site can add to the off-site copy but never delete or prune it. A site whose storage is compromised cannot reach back and destroy its copy.

Give the off-site target seals as well: ZFS or btrfs snapshots that its storage host takes after each copy and keeps for the target's seal retention. Nothing that reaches the storage host through restate-proxy or from a backed-up host can change a seal; only an administrator on that storage host can remove one. The source target's card says whether its off-site copy is immutable: append-only for the source, sealed, and how long seals are kept. It warns when the off-site target does not seal.

The source target's card names its off-site copy, and the off-site target's card lists whose copies it holds. Each host's Backup card shows how many snapshots are still to copy and how old the newest copied one is. The storage host's own server backup is copied too. To stop, set the off-site copy to None; the copies already made stay where they are.

If the license lapses, copying goes on as it was set up. Starting or changing an off-site copy waits for a license.

Restoring from the off-site copy

When a host's own site cannot serve its backups, because its storage host is down or lost, restore from the off-site copy instead. In the restore dialog, set Restore from to Off-site copy at the off-site target. The host reads the copy through that target's restate-proxy with a token of its own that may only read, so this site's backup storage is not used or mounted at all.

Practice it before you need it: stop the site's backup storage, restore a few files on one host from the off-site copy, check them against the live files, then start the storage again. A normal restore fails while the storage is down; the one from the off-site copy does not.

Moving a host with its backups

A host's backups always live on one storage host, so a host with backups moves by copy, then switch. Choose the new target in the host's backup policy and save; the dialog says the backups are copied first. Then:

  1. Copy. The current storage host copies every snapshot into the new target through its restate-proxy, as an off-site copy is made. The host keeps backing up to its current target meanwhile, and a snapshot made during the move is copied too. Its Backup card shows how many snapshots have been copied.
  2. Check. Once every snapshot is in, the new storage host protects, checks and lists the copy. If the check fails, the move stops, the card says why, and the host stays where it is.
  3. Switch. When the copy holds every snapshot and nothing of the host's is running, its policy names the new target and the host and both storage hosts are told at once. The next backup goes to the new target and adds only what changed since the last one.

Until the switch, Cancel move on the host's card stops it and the host stays on its target. Saving the policy for any other reason leaves a move alone.

After the switch the old repository is left as it is, with nothing backing up to it or pruning it. It is kept for 14 days, or for the old target's seal retention if that is longer, and then the old storage host removes it. Remove now on the host's card removes it sooner, though never before the old target's seals of it expire; Keep keeps it until someone removes it. The storage host removes only a repository it kept for that host itself, and leaves alone anything that is not a restate repository.

A move is refused, with the reason, when the new target is not reached through restate-proxy, when the current storage host's agent cannot copy yet, when the new target holds this host's off-site copy, when the host still has snapshots from before its backups were encrypted, when it is already moving to another target, or when its old repository from an earlier move is still kept on the new target.

If the license lapses, a move under way carries on and can still be canceled, and an old repository can still be kept or removed. Starting a move waits for a license.

Backup policies for every site

Under federation each site runs its own SysManage server and keeps its own backup targets, so backups never cross the network to the controller. The controller can still set a backup policy once for every site: on its Policies page, create a policy of type backup_tag_policy, assign it to sites and push it.

{
  "name": "Web servers",
  "tag": "web",
  "priority": 50,
  "enabled": true,
  "settings": {"interval_hours": 24, "window_start_hour": 2, "keep_last": 30},
  "target": {"name": "Offsite"}
}

Each site makes it one of its own backup policies by tag and picks the target there: its target with that name, else the one at that location ({"location": "DC2"}), else its default. The site creates the tag if it does not have it, checks the settings as it would a local change, and gives every host carrying the tag its policy. A site needs the Professional+ backup engine to apply it, and the Enterprise module to use a target other than its default.

On the site's Backups page the policy shows From the federation controller and cannot be changed or removed there; change it on the controller and push it again. A site's own policy with the same name is never overwritten. To pause a policy, push it again with "enabled": false.

The controller's page for each site lists that site's backup targets: name, location, which is the default, how many hosts use each, how full it is and whether it needs attention. Paths and storage hosts stay at the site.

Requirements

  • An Enterprise license that includes the backup_ops_engine module.
  • The Professional+ backup_engine module for backup policies by tag, including those the federation controller pushes.
  • restate 3.4.0.0 or later on a storage host before snapshots there can be placed on legal hold.
  • restate-proxy on the storage host of a target that keeps off-site copies or that a host with backups moves to.
