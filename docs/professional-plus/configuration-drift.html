Configuration Drift

Which hosts have diverged from their assigned profiles, what diverged, and -- the part a run history cannot answer -- how long it has been that way.

Overview

Drift detection reuses the machinery that already exists rather than adding a second collection path. A check-mode run is a drift report. A dry run of an assigned profile answers "what would change on this host", which is the definition of drift against that profile. So a scheduled check-mode assignment IS the comparison, and each result is reconciled into findings as it lands.

Why findings exist as well as runs

A check-mode run says what would change. What it cannot say is since when -- each run only knows about itself, so "this host has been drifting for nine days" is unanswerable from run rows without scanning the whole history on every page load. A drift finding stores exactly that lifespan and nothing else; the runs remain the record of what happened.

A finding is identified by (host, profile, task name). That is the only identity the generic result shape carries: the agent reports a task name, and nothing more stable travels with it. The accepted cost is that renaming a task in a profile restarts its drift age, because the new name is a different row. That is the right trade against matching on task order, which would silently re-attribute one task's history to another the moment somebody inserted a step -- a wrong date is worse than a reset one, because a reset is visibly a reset.

The reconciliation rules

Three rules govern how a landing run changes the finding set, and each exists to prevent a specific wrong answer:

  • Only check-mode runs open findings. A live run that changed something is not drift, it is a change we just made; counting it would report the system's own remediation as a new problem.
  • Only a successful run may resolve a finding. A check run that failed does not know the host's state, so treating its silence as "the drift is gone" would close findings on the strength of an error. A failed check may still open findings for whatever it did observe.
  • Only tasks reported as changed count. A failed task is an error to investigate, not a divergence to remediate.

A finding that had been resolved and reappears is a regression: the resolution is cleared and the clock restarts, so "drifting since" always describes the current episode rather than claiming continuous drift across a period when the host was compliant.

Dashboard and API

  • GET /api/v1/config-management/drift -- fleet view: one row per host with its open-finding count, the profiles involved, and how long it has been drifting
  • GET /api/v1/hosts/{host_id}/config-management/drift -- the individual findings for one host
  • POST /api/v1/config-management/drift/remediate -- re-apply the profile live

Findings are ordered oldest-first, because drift that has persisted is the interesting kind: a divergence seen once may be a race with a deploy, one standing for weeks is a configuration nobody is managing.

One-click remediation

Remediation re-applies the profile in live mode through the same dispatch builder as a manual apply and as the scheduled tick, so a remediation cannot diverge from a normal apply. It therefore inherits agent capability gating and maintenance windows for free rather than re-checking either.

Queuing a remediation does not mark the finding fixed. Findings resolve when the next successful check run stops reporting the task -- claiming success at dispatch time would be a dashboard that lies about the fleet.

Alerting on drift

The alerting engine gains a config_drift condition. It reads findings rather than runs, because only findings know since when:

POST /api/v1/alerting/rules
{
  "name": "Standing drift on production",
  "condition_type": "config_drift",
  "condition_params": {
    "min_findings": 1,
    "min_hours": 24,
    "profile_name": "production-baseline"
  },
  "severity": "medium"
}
  • min_findings -- how many qualifying findings before the rule fires
  • min_hours -- ignore drift younger than this. This is the parameter that matters: a check run moments after a deploy will legitimately report a divergence that the next run resolves by itself, and paging someone for that teaches them to ignore the channel. The UI defaults it to 24.
  • profile_name -- optional; scope the rule to a single profile

Resolved findings never re-alert, so remediation does not read as a new failure. The alert names the profiles involved and how long the oldest finding has stood, because an alert saying only "3 findings" sends the operator hunting.

Setting it up

  1. Create a configuration profile describing the desired state (see the Configuration Management guide)
  2. Assign it to a host, tag or site with a cron schedule and check mode enabled -- this is the comparison
  3. Watch the drift dashboard, or add a config_drift alert rule with a min_hours that matches how quickly your environment self-heals
  4. Remediate from the dashboard when a divergence is real, and let the next check run close the finding

A profile may be assigned twice to the same target -- once on a frequent check-mode schedule to detect drift, and once live on a slower schedule to correct it -- if you want detection and enforcement on different cadences.

Golden-host baseline comparison

The other kind of drift. Profile drift answers "does this host match the profile we assigned it". Baseline drift answers "does this host match that host" -- which is what an operator reaches for when there is no profile yet and staging works while production does not.

GET /api/v1/hosts/{host_id}/config-management/baseline-diff
      ?reference_host_id=..uuid..
      &categories=packages,repositories,users

Nine categories are compared, each matched on the identity that makes two rows "the same thing" across hosts and compared on the fields that make them differ:

  • packages -- matched by name, compared on version
  • repositories -- matched by name, compared on URL and enabled state
  • users -- matched by username, compared on shell and home directory
  • groups -- matched by group name
  • interfaces -- matched by interface name, compared on type
  • storage -- matched by mount point, compared on filesystem
  • certificates -- matched by certificate name, compared on issuer
  • firewall -- matched by firewall name, compared on enabled state
  • files -- matched by path, compared on checksum, permissions and ownership -- see Watched files below

Each category returns three buckets, named from the target host's point of view because that is the host being fixed: missing is on the reference but not the target, extra is on the target but not the reference, and different is present on both with a compared field disagreeing. "You don't have it" and "you have the wrong one" are different fixes, so they are never merged.

Per-item lists are capped so one call cannot return a megabyte of JSON, but the counts stay exact and a truncated flag says when a list was shortened -- a summary never under-reports the size of a divergence.

This comparison stores nothing. It is a pure function of two hosts' current inventory, and unlike a profile finding there is no lifespan to track: a category either differs right now or it does not. GET /api/v1/config-management/baseline-categories reports the supported categories, so the UI cannot offer one the server would refuse.

Watched files

The eight inventory categories compare facts the agent already reports. Watched files compares things nothing collected before: a list of paths you nominate, hashed on every collection, so two hosts can be compared on their actual configuration files rather than on the packages that installed them.

Contents are never collected

Only a SHA-256 checksum and the stat metadata -- size, mode, owner, group, modification time -- ever leave the host. No file content is transmitted, stored, returned by the API, written to logs, or included in backups. That is a deliberate design constraint rather than a limitation waiting to be lifted: it is what makes it safe to watch /etc/shadow, a private key or a license file.

The cost is real and worth stating plainly. Drift reports the fact of a change, and that a file's mode went from 0440 to 0644. It cannot report which line changed inside the file.

Every watched path reports an outcome

A watched path always produces a result, including when there is no file there. This is the difference that makes the feature trustworthy: a tool that simply omits missing files makes a deleted configuration file indistinguishable from one nobody was watching, so deleting it silently stops being drift.

  • present -- read and hashed. The only state that carries a checksum.
  • absent -- the path does not exist. Real drift, if the reference host has it.
  • unreadable -- it exists and the agent was not permitted to read it. A fixable gap, and emphatically not "unchanged" -- an agent that loses permission would otherwise report a file as stable forever.
  • not_a_file -- a directory, socket or device. Metadata is reported; there is nothing to hash.
  • too_large -- above the hash limit, so it was skipped deliberately. A separate state from "could not", because those send you to different places.

A symlink is reported as one, with its target, and the content at the end of it is hashed as well -- a configuration file replaced by a link to /dev/null is exactly the drift worth catching. A dangling link reads as absent but keeps its target, so "deleted" and "points at nothing" stay different repairs.

Not compared is not a match

When either host did not measure a path, that path is a blind spot: it is reported separately and counted separately, never as a difference and never as agreement. Both would be wrong. An unreadable file has no checksum, so comparing it against a real one would invent a divergence out of a permission error -- and comparing it against another unreadable file would report two hosts as matching when they agree only in having been unable to look.

A path on the reference host's list but not the target's is also a blind spot, not a deletion. Nobody asked the target about it.

Two hosts with no watch list assigned are reported as not compared rather than identical. Zero differences between two empty sets is arithmetically true and operationally a lie.

Setting up a watch list

  1. Create a list under Configuration Drift → Watched files, one absolute path per line. Relative paths are refused: they resolve against the agent's working directory, so the same list would watch a different file on each host.
  2. Assign it to a host, a tag or a site, with a collection interval (minimum five minutes, default sixty).
  3. Compare two hosts as usual; the files category appears once both have reported.

A path may declare which platforms it applies to. This matters more than it looks: a path sent to a host it does not apply to comes back absent, and absent means "this should be here and is not" -- so a list naming /etc/ssh/sshd_config without a platform restriction would report every Windows host as having deleted it.

  • GET|POST /api/v1/file-watches -- the watch lists this tenant has authored
  • POST /api/v1/file-watches/assignments -- bind a list to a host, tag or site
  • GET /api/v1/file-watches/hosts/{host_id}/state -- every watched path on one host with its outcome, including the absent and unreadable ones, plus a count per state

Watched files need an agent speaking version 2 of the fact contract. A host running an older agent is reported as not compared with a reason saying so, rather than being compared against nothing and declared identical.

Remediation playbooks

One-click remediation re-applies the whole profile a host drifted from. That is right when the profile is small and wrong when it is a four-hundred-task baseline and the divergence is a single file mode: you wanted a permission fixed and got an hour of unrelated convergence, inside a maintenance window budgeted for one change.

A remediation playbook is the narrow alternative. It is an ordinary configuration profile -- authored, versioned and dispatched exactly like any other -- bound to the findings it repairs by a rule. Only the binding is new, which is why there is no second authoring surface: validation, version history, the engine spec builders and run history are all reused rather than re-grown.

A rule carries four things that decide whether and when it fires:

  • Task pattern -- a shell-style glob matched case-insensitively against the drifting task's name, for example ensure nginx*. Globs rather than regular expressions, because the same string as a regex means something subtly different and would quietly match a task it should not. A bare * is refused outright: with automatic repair it would fire one profile at every divergence in the fleet, and it would look like the system working.
  • Scope -- optionally narrow the rule to drift from one profile. Left open, a rule repairs that task wherever it drifts, which is what makes a rule library worth having across profiles.
  • Priority -- lowest number wins. At equal priority the profile-scoped rule beats the global one, because the narrower claim is the one whose author knew more about the situation, and any remaining tie breaks by name so the winner is the same on every server and after every restart. An operator who cannot predict which repair fires will never switch an automatic one on.
  • Automatic -- off by default. When on, the repair is queued the moment the drift is first detected.

An automatic repair fires once per episode, not once per check. Only a finding that has just opened is eligible; a finding that is merely still open is not a new event, so a divergence the playbook cannot fix shows up as persistent drift rather than an endless loop of attempts. A finding that had resolved and comes back is a new episode and does earn a fresh attempt.

Automatic repairs inherit the same two guards as everything else queued the normal way and re-implement neither: a host that has not advertised config-management support is refused at the queue, and delivery is held for any host inside a maintenance window. A rule whose repair profile has been retired is reported loudly in the log and applies nothing -- silent breakage of a repair somebody wrote down is exactly what makes unattended remediation dangerous.

  • GET|POST /api/v1/config-management/remediation-rules -- the rule library, returned in precedence order
  • GET /api/v1/config-management/drift/findings/{id}/remediation -- what would repair this finding, without doing it. Three distinguishable answers: nothing matched, a rule matched but its profile is retired, or here is what will run
  • POST /api/v1/config-management/drift/findings/{id}/remediate -- apply the matched playbook to this host

As with re-applying a baseline, queuing a targeted repair does not mark the finding fixed. It clears when the next successful check run stops reporting the task.

What this does and does not cover

Drift here is measured against a profile: the engine itself reports what would change, so nothing extra has to be collected. Drift measured against a reference host covers two kinds of fact. The eight inventory categories -- packages, users and groups, network interfaces, storage, repositories, firewall state and certificates -- come from what the agent already reports. Arbitrary files and configuration state come from a watch list you nominate, collected as checksums over the fact substrate.

Architecture

Reconciliation runs inside the result handler, before the run is committed, so a run and its findings land together -- a run recorded without its findings would leave drift looking resolved until the next check. Reconciliation never raises: a bookkeeping problem must not fail the queue processor and cost the run record, which is the more valuable of the two. The config_drift_finding table lives in the open-source schema; the rules that populate it are gated on the licensed config_management_engine, so an unlicensed install has a coherent schema and simply no findings.
