Advisor

Recommendations over the evidence your fleet already reports -- and an honest account of everything the advisor could not check, so an empty list never reads as a healthy fleet.

Overview

The advisor evaluates rules against what each host has reported -- its facts, its vulnerability and compliance scans, its pending updates, its configuration drift -- and turns what it finds into recommendations across four lenses: security, performance, availability and stability. Each finding carries a risk score, a remediation, and for some rules a fix it can propose.

The feature is built around one property. An advisor's output is a list, and an empty list reads as "your fleet is in good shape". So a rule that could not be evaluated on a host is never reported the same way as a rule that found nothing. It is its own outcome, with the reason, everywhere the advisor shows results.

Four outcomes

Every rule, on every host, ends in exactly one of these:

  • Finding -- the rule matched. It carries a risk score and a remediation.
  • Clean -- the rule was evaluated on current evidence and matched nothing.
  • Not assessable -- the evidence the rule needs is missing, too old, or was never collected. This is not clean: it is unmeasured.
  • Not applicable -- the rule cannot apply to this platform. A filesystem-capacity rule does not apply to a Windows host that has no mounts table; that is neither a gap nor a finding.

Rules declare the evidence they need

A rule does not simply run and see what comes back. It declares the fact tables and columns it reads and the evidence domains it depends on, and the advisor checks every one of them before any query runs. A host that cannot supply the evidence is reported not assessable with the specific reason, rather than evaluated against nothing.

Coverage is checked per column, not per table. A host can serve the mounts table while its agent leaves the capacity columns empty; a disk-usage rule evaluated against those empty columns would report every filesystem as fine.

Evidence also has an age, and each kind of evidence is read from its own timestamp: a heartbeat proves an agent is alive, not that its list of pending updates is current. Evidence older than its limit makes a rule too old to trust rather than letting it pass on stale data:

Evidence Trusted for
Facts collected from the host1 day
Pending updates, reboot status, software inventory, firewall status2 days
Vulnerability scan, configuration drift check7 days
Compliance scan30 days

Fact rows are collected by the advisor itself: it asks each host for exactly the tables and columns its enabled rules read, through the ordinary query-pack path, and asks again before the evidence goes stale -- or immediately, when a rule starts reading a column that was not collected before.

Risk scores that are withheld

A finding's risk is its rule's impact × likelihood, each from 1 to 5. A host scores its worst finding on a 0 to 100 scale, so twenty trivial findings cannot outrank one critical exposure.

  • A host is graded No findings only when every rule that applies to it was assessed and none fired.
  • If any rule could not be assessed and nothing fired, the host gets no score and no grade -- shown as Not assessed, never as a low score or a clean one.
  • A host with findings is scored, but when some rules could not be assessed the score is marked as a minimum: the host is at least that risky.
  • The fleet's average covers assessed hosts only, and the unassessed ones are counted beside it. Averaging them in as zero would make adding blind spots improve the fleet's score.

Curated rule packs

The advisor ships with a curated SysManage baseline pack, on by default: an advisor with no rules would show an empty feed, and that is exactly the impression it exists to prevent. Curated packs are shared reference data -- one copy for every tenant -- and each tenant can switch a pack off or opt out of individual rules without copying it. Switching a rule off clears its findings and proposed fixes at once.

Curated rules are delivered inside the licensed engine, so a new version of a pack arrives with an engine update -- including on air-gapped installations, which receive engine updates the same way.

The baseline pack checks for:

  • Critical and high-severity vulnerabilities that have a fix available
  • Accounts other than root with user ID 0
  • Services listening on all interfaces while the host firewall is off
  • Certificates expiring within 30 days
  • Filesystems more than 90% full, ignoring snap images and other pseudo-filesystems
  • Pending security updates, with a proposed fix
  • Hosts that need a reboot
  • Configuration drift unresolved for more than 7 days
  • Failed high or critical compliance checks
  • OpenSSL versions that differ from the version their peers run, compared only among hosts on the same operating system release

Proposed fixes

A rule can say how its finding is fixed, either by naming a configuration profile you already have, or by having the advisor generate a package upgrade for the packages it matched. The advisor only ever proposes the fix. Nothing is applied until an operator reviews it and approves it.

  • Review shows exactly what would run: the packages, anything that was left out, and the playbook itself.
  • An approved fix is applied through the same path as any other configuration profile, so it waits for the host's maintenance window and shows as queued, not applied, until its run comes back.
  • A generated fix only upgrades packages from the operating system's package manager. Firmware updates, snaps and anything whose name is not a well-formed package name are left out and counted, never passed through.
  • You are asked once per fix, not on every evaluation: a rejected fix is not proposed again until it changes, and a proposal is withdrawn when its finding goes away.

Writing your own rules

Rules are data: a rule names what it requires, a single read-only SQL query in the same dialect as query packs, and its impact, likelihood and remediation. The facts your hosts report are available as tables by their osquery names, and server-side records as sm_* views such as sm_pending_update, sm_vuln_finding and sm_host.

{
  "id": "OPS-001",
  "version": 1,
  "contract": 1,
  "title": "Security updates pending",
  "lens": "availability",
  "requires": {"domains": ["updates"]},
  "when": "SELECT package_name, package_manager FROM sm_pending_update WHERE update_type = 'security'",
  "impact": 3,
  "likelihood": 3,
  "remediation": "Apply the pending security update for {package_name}",
  "fix": {"generate": "package_upgrade", "column": "package_name"}
}

A rule that is not valid is refused with every problem at once, as codes the interface explains. A rule that needs nothing is refused too: it would "pass" on a host that has told the advisor nothing.

  • GET /api/v1/advisor/feed -- the fleet's recommendations, one entry per rule
  • GET /api/v1/advisor/hosts/{id} -- one host's score and outcomes
  • GET|POST /api/v1/advisor/rules -- curated and tenant rules; add your own
  • GET /api/v1/advisor/proposals -- proposed fixes, with approve and reject actions
  • GET /api/v1/advisor/packs -- curated packs and this tenant's choices
  • POST /api/v1/advisor/evaluate -- evaluate this tenant now

Getting started

  1. Open Insights > Advisor. The baseline pack is already on; the advisor evaluates every fifteen minutes, or press Evaluate now.
  2. Read the Not assessable column first. Its reasons tell you what to fix to see more of your fleet: upgrade an old agent, run a scan that has gone stale, or wait for a first collection.
  3. Review the Proposed fixes tab, and approve the ones you want applied at each host's next maintenance window.
  4. Under Rule packs, switch off any rule that does not fit your environment.
