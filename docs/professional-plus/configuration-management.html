Configuration Management

Desired-state configuration: stored, versioned profiles applied to hosts, tags or sites on a schedule or on demand. Puppet, Salt and Chef sit behind one profile abstraction; ansible-core and Windows DSC stay open source.

Overview

A configuration profile is a named, versioned body of desired state -- a Puppet manifest, a Salt state, a Chef recipe, an Ansible playbook or a DSC resource set -- plus the engine that interprets it. Profiles are stored server-side, assigned to hosts, tags or sites, and applied either on request or on a cron schedule. Every application is recorded as a run, including the runs that changed nothing.

Pull-style execution, not push

Configuration management is conventionally push-based: a control node opens SSH to each target. SysManage does the opposite. The server ships the profile down the existing agent WebSocket and the agent runs it locally against localhost, exactly as script execution already works.

  • No new inbound port and no SSH reachability: the agent needs 443 outbound and nothing else
  • No credential distribution: there is no control node holding keys to every host
  • The executor is an agent-side dependency, so a host that cannot run one simply does not advertise the capability
  • Results flow back over the same connection as every other command result -- no new ingress path

Engines

Five engine identities are supported. Which are free and which are licensed follows the value they add, not the effort of supporting them:

  • ansible-core -- Community Edition. Someone with three hosts already has ansible-playbook; single-host apply is the direct analogue of script execution, which is free.
  • dsc -- Community Edition. Vendored with the Windows agent, so it is the default single-host path there. Reported as "included with the agent" rather than as something to install.
  • puppet -- Professional+
  • salt -- Professional+
  • chef -- Professional+

Only DSC is platform-bound, and only because it is what we vendor on Windows. Puppet, Salt and Chef all ship Windows agents and run there. requires_license() in backend/services/config_mgmt_engines.py is the single source of truth consulted by the apply endpoint, the install endpoint and the UI, so the rule cannot drift between the place that offers a button and the place that refuses the request.

How one abstraction drives four engines

The open-source agent knows how to run ansible-playbook and DSC. It knows nothing about Puppet, Salt or Chef. Instead of teaching it, the licensed engine builds an execution spec and the agent executes it generically:

{
  "engine": "puppet",
  "argv":   ["puppet", "apply", "--noop", "--color=false", "--vardir", "{workdir}/var", "site.pp"],
  "profile": {"name": "site.pp", "content": "file { '/etc/motd': ... }"},
  "files":  [{"name": "client.rb", "content": "..."}],
  "env":    {"CHEF_LICENSE": "accept"},
  "result": {"format": "yaml_file", "report_glob": "last_run_report.yaml",
             "entries_path": "resource_statuses",
             "changed_key": "out_of_sync", "name_key": "title"}
}

The result block names one of five generic shapes the agent can read, and supplies the rules for reading it. Which flags produced that output, and what the fields mean, is the licensed engine's business:

  • json_lines -- one JSON object per line (ansible-core, via our callback plugin)
  • json_stdout -- one document on stdout (Salt, DSC)
  • json_file -- the newest matching report file in the run directory (Chef)
  • yaml_file -- the same, for a YAML report (Puppet's last_run_report.yaml, which is Ruby-tagged and read with a tag-tolerant safe loader)
  • exit_code -- meaning carried in the exit bits, with the bit values supplied by the spec

This is why adding an engine is a licensed-side change with no agent release: a new engine ships new argv and new result rules, not new agent code.

Profiles and versioning

Every change to a profile's engine or content bumps its version and snapshots the previous body into config_profile_version. Editing only the description does not burn a version. Config-as-code without history is just config: the value of a stored profile is being able to answer "what changed, and when" once a run starts behaving differently.

  • GET /api/v1/config-management/profiles -- list
  • POST /api/v1/config-management/profiles -- create
  • GET /api/v1/config-management/profiles/{id}/versions -- version history
  • POST /api/v1/config-management/profiles/{id}/restore/{version} -- restore a prior body

Assignments and scheduling

An assignment binds a profile to exactly one target -- a host, a tag or a site -- with an optional cron schedule and an optional check-mode flag. Three nullable target columns are used rather than a (target_type, target_id) pair, because that pair cannot be a foreign key: it would let an assignment outlive the host it names, and the first symptom would be a scheduled run against a machine that no longer exists.

Due-ness is anchored on last_applied_at rather than a stored next_run column, so changing a schedule takes effect immediately and a missed tick cannot strand an assignment. A scheduled assignment with check_mode set only ever reports drift and never changes the host -- see the Configuration Drift guide.

Applying a profile

An apply queues a command for the host through the normal outbound queue, so it inherits agent capability gating and maintenance windows rather than re-checking either:

POST /api/v1/hosts/{host_id}/config-management/apply
{
  "profile_id": "..uuid..",
  "check_mode": true
}
  • Check mode runs the engine's dry-run flag (--check, --noop, test=True, --why-run) and reports what would change
  • GET /api/v1/hosts/{host_id}/config-management/runs -- run history for a host
  • GET /api/v1/config-management/runs/{run_id} -- per-task detail for one run

Runs that changed nothing are recorded too. Idempotency reporting is the point of desired-state management and it is a claim about history: "the last three applications of this profile changed nothing" cannot be answered from a current-state column.

Executor readiness

Before offering to run a profile, the server reports whether the host actually has the executor, and distinguishes three situations that must not be described identically:

  • Installed -- with the detected version, so a profile can declare a minimum
  • Not installed, but installable from this host's package manager
  • Not required -- DSC ships with the agent
  • Not available here -- either the distro is measured not to carry the package, or Windows inventory cannot report it (a detection limit, not a platform limit)

Feature Codes

Profile storage, assignment, scheduling and the Puppet/Salt/Chef adapters are provided by the config_management_engine module. Without it the open-source server still stores runs and drives ansible-core and dsc on a single host; licensed engines are refused before anything is queued.

Architecture

The schema lives in the open-source tree because the OSS server owns the database; the behavior -- validating a profile, versioning it, resolving an assignment, deciding when a schedule is due, building an execution spec -- lives in the Cython-compiled config_management_engine. That is the same split Vulnerability and ComplianceProfile use, and it means an unlicensed install keeps a coherent schema and its existing run history.
