Container Image Content Lifecycle

Bring OCI / Docker container images into the same content-distribution pipeline as packages and snaps. Capture images, digest-pin them, snapshot them into content-view versions, promote them through lifecycle environments, and serve them to hosts offline — including fully air-gapped.

Overview

Container Image Content Lifecycle is an Enterprise feature, delivered by the compiled oci_proxy_engine. It reaches parity with a Satellite-style container-image content view: your OCI / Docker container images flow through the very same capture → version → promote → serve pipeline as mirrored packages and snaps.

As with the other engines, the feature is Enterprise-gated — the OSS server owns the API, the schema, and the license gate, while the compiled engine performs the capture and content work. With it loaded, container images become curated, versioned, offline content: capture them once, pin them by digest, snapshot them into an immutable content-view version, promote them through your lifecycle environments, and serve them to hosts with no live registry required.

Track Images

On a mirror (Settings → Repository Mirroring) you track the container images you want by registry / repository / tag — for example docker.io / library/nginx / 1.27. Each tracked image is one row that rides the mirror it belongs to, so images are curated in exactly the place you already manage upstream content.

A tracked image shows a capture status as it moves through the pipeline — TRACKED → DISPATCHED → CAPTURED (or FAILED). Once it has been captured, the row also carries the pinned digest — the immutable manifest identity of exactly which bytes were fetched.

Capture

The Capture images action uses skopeo to copy each tracked image into a self-contained, digest-pinned OCI layout under the mirror. Because skopeo is daemonless, no dockerd or podman daemon is required on the mirror host — the capture is a plain, offline-friendly copy of the image's manifests and layers.

The image's manifest digest is recorded as the immutable pin. This makes every captured image tamper-evident and offline-verifiable: the digest identifies the exact content, so a captured image can be validated at any later point without contacting the origin registry.

Promote Through Content Views

Captured images materialize into an immutable content-view version — landing as an images/ sibling of the package and snap content within the same frozen version store. From there they promote through Lifecycle Environments (Library → Dev → Test → Prod) alongside everything else in the view — one promotion moves packages, snaps, and images together.

Because captured images live inside the content-view version store, they ride the air-gap export ISO with no extra steps — exporting a version carries its container images into the air-gapped environment automatically.

Serve & Repoint Hosts

A consuming host is repointed to load an environment's served images into its local container storage offline. The host pulls the served OCI tree from the environment and then runs skopeo copy oci:… containers-storage:… to load it into local storage — no live registry is required, so this works fully air-gapped.

This is the Repoint images action on the content view's promotion lane. Once loaded, the image is a first-class local image — runnable immediately with podman run on the host, with no dependency on an external registry.

Requirements

  • Enterprise license — the oci_proxy_engine must be loaded; without it the container-image endpoints are gated off.
  • Mirror host — needs skopeo installed to capture images into the digest-pinned OCI layout.
  • Consuming hosts — need skopeo to load the served OCI tree and podman to run the resulting local image.
