Fleet Configuration Jobs

One configuration profile across thousands of hosts, worked through in bounded waves, with a row per host so “which twelve of the four thousand failed” is a question you can answer.

Overview

A profile assignment is standing intent -- “this profile applies here, forever, on this schedule”. A job is one bounded execution with a beginning, an end, and a result you can point at afterwards. The two are deliberately separate: collapsing them would mean either giving standing intent a completion state it can never reach, or giving a finished run a cron expression.

Assignments already fan out to every matched host, and that is correct for tens of hosts and wrong for thousands in two distinct ways: one database transaction holding the whole fleet, and a burst of messages that arrives all at once regardless of what the queue, the network and the agents can absorb. A job fixes both by never having more than its concurrency in flight.

Inventories

An inventory is a named, reusable set of hosts built from the same three selectors assignments use -- a host, a tag, or a site -- or the flag that means every active host. Members union rather than intersect: an inventory of “tag=web” plus “site=eu-west” is every host in either.

An inventory resolves at launch; it never stores a host list. A copied list would be wrong the moment a host joined the tag -- and wrong silently, because a job that simply misses machines looks exactly like a job that succeeded. For the same reason the host count on the page is computed on every read rather than cached, and the Preview button answers “who am I about to change?” at the moment you ask it.

An inventory that resolves to nothing is refused rather than allowed, and a job launched against one that has since emptied completes immediately saying so. A job reporting a clean success over zero hosts reads as “the fleet is converged”, which is the most expensive way this feature could be wrong.

Job templates

A template names a profile, an inventory and how hard to run it. Its value is that the three decisions you would otherwise re-make every time are made once and named, so the run that happens at 3am under a schedule is provably the run somebody reviewed.

  • Dry run is the default for a new template. The first thing to do with one is find out what it would change; a live fleet-wide run is the one mistake here that cannot be undone.
  • Concurrency is clamped rather than rejected. Somebody typing 10,000 means “as fast as possible”, so the server stores its ceiling and the page tells you what you got -- refusing the whole template over it would turn a clear intention into an error message.
  • A cron schedule makes the template a standing fleet job. Due-ness is derived from the last launch, so a server that was down overnight launches once on the next tick rather than replaying every occurrence it slept through.

How a job runs

Launching materializes one target per selected host, all pending, and immediately releases the first wave. Targets are created up front rather than discovered as the job goes, which costs one insert per host and buys the thing the feature exists for: from the first second the job can say how many hosts it will touch and which ones.

From then on the job is paced by results, not by a clock. Each arriving result closes its target and immediately releases the next one, so a fleet is worked through as fast as it answers. A background tick every 60 seconds is only a safety net for jobs whose results are slow or absent.

A target dispatched but never answered ages out after six hours and is recorded as failed. Something must: a job stuck at “running” holding slots forever, with an outstanding count that never moves, reads as a broken feature rather than a failed host.

Dispatch goes through the same builder as a manual apply and as the assignment tick, so a fleet job cannot diverge from what a normal apply would have done -- and it inherits both existing guards without re-checking either: a host that has not advertised config-management support is refused at the queue, and delivery is held for any host inside a maintenance window.

Reading a job's status

A job's status answers “did this job do its work?” -- not “is every host happy?”, which is what the counts answer. So a job where a handful of hosts failed is completed, deliberately.

The temptation is to mark a job failed the moment any target fails, and it is wrong for a reason that only shows up at scale: on a fleet of four thousand, a handful of machines are always offline, mid-reboot or newly rebuilt. A status that goes red every single time is ignored within a week, and then it is worth nothing on the day it means something.

  • pending -- created, nothing dispatched yet
  • running -- targets are in flight or still waiting for a wave
  • completed -- every target reached a terminal state and at least one succeeded, or every host declined
  • failed -- the job achieved nothing: something failed and nothing succeeded. This is also what an undispatchable profile produces
  • canceled -- an operator stopped it

A host that cannot take the command is skipped, never failed, and the reason is written to its row. That distinction matters on a mixed fleet: “this agent does not advertise config-management support” is a true and useful answer that must not be filed alongside “the playbook blew up”.

Canceling stops further dispatch and marks the untouched targets skipped. Targets already in flight are left alone -- the command is with the agent and the server cannot recall it, so claiming otherwise would be a status that lies. Their results still land and still close their targets, which is why a canceled job's counts keep moving for a while.

API

  • GET|POST /api/v1/config-management/inventories -- list and create inventories
  • GET|POST /api/v1/config-management/inventories/{id}/members -- the host, tag and site selectors an inventory is built from
  • GET /api/v1/config-management/inventories/{id}/hosts -- what it resolves to right now
  • GET|POST /api/v1/config-management/job-templates -- list and create templates
  • POST /api/v1/config-management/job-templates/{id}/launch -- launch now; the first wave is dispatched before the response returns
  • GET /api/v1/config-management/jobs -- recent jobs with their counts
  • GET /api/v1/config-management/jobs/{id}/targets -- the per-host rows, failures first
  • POST /api/v1/config-management/jobs/{id}/cancel -- stop dispatching

Authoring an inventory or a template needs the Add Script / Edit Script entitlement. Launching one needs Run Script -- the same permission as applying a profile to a single host, because it is that operation with a larger blast radius rather than a different one.

History outlives its parents

Deleting a template does not erase the record that it changed four thousand hosts last Tuesday. The job keeps the template's name, the profile's name and the inventory's name alongside foreign keys that soften to null, and every target keeps its host's fully-qualified name. A job is an audit artifact; decommissioning a host or tidying up a template must leave it readable.

Architecture

The tables live in the open-source schema, because the open-source server owns the database. What is licensed is the behavior: how wide a wave may be, what a job's status means when some hosts failed, what an inventory selects, and when a scheduled template is due. Those rules live in the config_management_engine module, and without it an unlicensed install has a coherent schema, no jobs, and a runner that releases nothing rather than falling back to the unbounded behavior jobs exist to replace.

A job's state lives entirely in its rows. There is no per-job task and nothing sleeps on a result, so a server restarted in the middle of a four-thousand-host run resumes by reading the rows rather than losing the loop.
