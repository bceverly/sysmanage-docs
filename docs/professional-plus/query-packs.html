Query Packs

Ask the same question of every machine you manage — on a schedule, or right now — and get an answer that distinguishes "nothing found" from "this host could not be asked".

Overview

Every agent exposes its facts as a set of SQL-queryable tables using osquery's schema — the same table and column names, so a query written against osquery means the same thing here. A query pack is a named, versioned set of those queries, assigned to hosts, tags or sites as policy and collected on an interval.

The fact substrate itself is open source and present on every edition, because better inventory helps everyone. What Professional+ adds is the management plane: authoring packs, distributing them as multi-tenant policy, pacing collection and reading results.

The substrate works where osquery does not

osquery has no port for OpenBSD or NetBSD, and no package table on any BSD. If facts came only from osquery, those hosts would report nothing — and nothing reads as "no findings", which reads as healthy.

So every agent ships a native provider that materializes the contract tables from the inventory it already collects, using nothing but the Python standard library. Where osquery is present it is used instead, per table, because it is more faithful. The native provider is the floor everywhere; osquery is an accelerator where it exists.

Two tables are ours rather than osquery's, and deliberately so. sysmanage_packages is one installed-package table that every platform populates, so package queries are portable to the BSDs where osquery has no package table at all. sysmanage_available_updates covers pending updates, which osquery does not model.

A host says what it cannot answer

This is the property the whole feature is built around. Each agent advertises, per table, whether it serves it — and if not, why not. Four answers, because they call for four different responses:

  • Served — ask it; the data is real.
  • Not applicable — a Windows host has no mounts. Not a gap, not a defect, and not something to show an operator as a finding.
  • Unsupported — the host could serve it and cannot right now, typically an unprivileged agent. This one is worth showing precisely because it is fixable.
  • Unknown — the agent predates the substrate and has not advertised anything.

A query is only dispatched to hosts that can answer it, and a host that cannot is recorded as not covered rather than returning an empty result. The distinction is the point: a table that was never measured, reported as zero rows, becomes "no findings" — which an operator reads as compliant. Unmeasured and measured-empty must never share a value.

A run where some queries could not be answered grades partial, never success. A partial security fact is worse than a missing one: "nothing is listening on port 22" reads as safe, and a pack cannot tell a true negative from a blind spot.

Packs, assignment and collection

A pack carries its queries, each declaring the contract tables it reads and optionally the platforms it applies to. Curated packs shipped with the product are global reference data — one copy for every tenant, offline-updatable — while the assignment of a pack to hosts, and any packs you write yourself, are your own tenant's data. Distributing packs as multi-tenant policy means one shared catalog plus per-tenant assignment, never per-tenant copies.

Each query declares which tables it needs, rather than leaving them to be guessed from its SQL. Parsing would be wrong in exactly the cases that matter — a join, a subquery, a CTE — and a wrong answer here means a host is sent a question it cannot answer, which comes back as an error rather than as honest non-coverage.

  • GET|POST /api/v1/query-packs — packs this tenant has authored
  • GET /api/v1/query-packs/catalog — the curated catalog
  • POST /api/v1/query-packs/assignments — bind a pack to a host, tag or site with an interval
  • GET /api/v1/query-packs/runs/recent — what came back, and how each run graded

Results are stored as rows, not as one document per run, because every consumer wants "which hosts returned a row matching this" — a query over rows, not a scan of documents. A query that was asked and not answered still leaves a row recording that it was asked.

Live queries

A scheduled pack answers questions you knew to ask. A live query is for the ones you did not: one statement, typed at a console, fanned out across the fleet, with answers arriving as hosts respond.

A live query is dispatched as a one-query pack, so the agent command and the result path are the ones scheduled collection already uses. What it adds is bounds: a concurrency limit and a per-host timeout, stored with the request so that what a run actually did stays answerable afterwards rather than depending on whatever the server policy happened to be at the time. Waves are released as answers land rather than on a timer, so a four-hundred-host query is paced by how fast hosts actually reply.

Completed, failed and not-covered are counted separately. A host that does not serve the tables has not failed, and merging the two would make a Windows box look broken for lacking mounts.

What reads the substrate

The fact tables are not only for packs you write. The compliance, vulnerability and fleet engines, and the golden-host differ, all read the same coverage advertisement — and all of them degrade honestly rather than silently when a host cannot answer:

  • Compliance returns not_assessable rather than a pass or a fail when a host never reported its package inventory. A "must not be installed" rule would otherwise succeed on a host that reported nothing.
  • Vulnerability scanning gives an unmeasured host no score and no grade, instead of the perfect one that zero known vulnerabilities would otherwise produce. At fleet level such hosts are counted separately from clean ones and excluded from the risk average, so blind spots cannot make an estate look safer.
  • Fleet operations mark a host unresolvable when a selector tests a property it never reported — neither targeting it nor silently excluding it, and reporting the count alongside the job.
  • Golden-host drift reports a category as not compared rather than as matching when either host cannot report it. See the Configuration Drift guide.

Setting it up

  1. Review the curated catalog under Query Packs, or write a pack of your own, declaring the tables each query reads.
  2. Assign it to a host, tag or site with a collection interval.
  3. Read results per run, and check the not-covered count — it tells you how much of the fleet the answer actually covers.
  4. If a table reports unsupported for insufficient privilege, granting the agent that privilege converts a blind spot into data. Listening ports is the common one.
