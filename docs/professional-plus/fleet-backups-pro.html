Fleet Backups (Professional+)

The backup_engine module builds on the fleet backups every edition has: encrypted repositories whose keys never live on a backed-up host, keys that rotate on their own, a sealed key export for a restore with SysManage down, grandfather-father-son retention, and backup alerts.

Encrypted backups

In a host's Backup tab, the Encryption panel has Encrypt this host's backups. SysManage makes an OpenPGP key pair for the host, keeps the secret key in OpenBAO and gives the host only the public key, so a host that is broken into cannot read its own backups. restate cannot encrypt an existing repository, so the next backup starts a new, encrypted repository; the backups taken so far stay where they are and can still be restored.

To restore, browse or see what changed in an encrypted repository, the host's agent fetches the keys over HTTPS for that one job, keeps them only in memory-backed storage readable by root, and deletes them when the job ends. The keys never travel through the command queue or the database. The host needs a restate that can take a key for one job (decrypt_with); until it has one, SysManage says so instead of restoring.

Keys are RSA-3072. libgcrypt 1.12.0, which Ubuntu 26.04 ships, cannot reliably use an imported Curve25519 secret key (GnuPG bug T8094, fixed in 1.12.1), and restores depend on exactly that.

Key rotation

Rotating a host's key makes a new, independent key pair: new backups are encrypted only to it, and every earlier key stays in OpenBAO, because a backup taken after a rotation still reuses data written before it. A restore is given every key the host has held. Use Rotate key now in the Encryption panel, or let SysManage rotate on its own: every 365 days by default, set from the same panel for every host (0 turns it off; otherwise 30 to 3650 days). Every rotation is audited, and a scheduled one that fails is tried again an hour later.

A host can hold up to 16 keys, the most a restore can take. After that a rotation is refused, with the reason, until old keys can be retired, which comes with a restate that reports which keys its remaining data still needs.

Snapshot signing

With Sign every snapshot in the Encryption panel, SysManage makes one signing key for the backup target and keeps it in OpenBAO. The storage host signs each new snapshot right after it is taken, before it is protected, with the key released to it for that one job. No backed-up host ever holds the key, so a host cannot vouch for a snapshot it altered. Signing is turned on once and stays on; it needs the Manage Backups role, and turning it on is audited.

Every backed-up host gets the signer's public key, and restate checks every restore against it. A signed snapshot restores with no extra step; a snapshot whose signature is wrong, or made with another key, is refused. Snapshots taken before signing was turned on stay unsigned, and restoring one still asks you to confirm that it is not signed. The snapshot list in Restore files shows which snapshots are signed, and the backup target card shows the signing key.

Signing needs restate 2.2.0.16 or later on the storage host and GnuPG on the SysManage server. If the storage host cannot sign, or a signing job fails, the snapshot is still protected, sealed and pruned as usual and stays unsigned.

Break-glass key export

A lost key is lost backups, and the SysManage server, with OpenBAO behind it, may be exactly what is gone when the backups are needed. Break-glass key export in the Encryption panel exports one host's keys, or every encrypted host's, sealed to an OpenPGP public key you paste: an offline key, a smartcard or a key held in escrow. You give a reason, and the browser downloads one file, sysmanage-backup-keys-<time>.tar.asc. It needs both the Manage Backups and Restore Files roles, it is never stored on the server, and every export is audited for each host with your key's fingerprint and the reason.

Opened with your private key (gpg --decrypt, then tar -xf), it holds README.txt with the restore procedure, manifest.json naming each host's repository, where it lives on the storage host and its keys (no secrets), one secret key file per key under keys/<host>/, and, when snapshot signing is on, the signer's public key as keys/signing.pub.asc. If OpenBAO lacks any key, nothing is exported, since a partial export would only be found out in a disaster.

To restore with SysManage down, on the storage host (or a machine that can read the repository) with restate 2.2 or later, give restate every key of the host: restate restore --plan --trusted-key keys/signing.pub.asc --decrypt-with keys/<host>/1-<fingerprint>.asc ... <repository>::<snapshot> to see what would come back, then the same with --check-first --root /restore/<host> to restore. --trusted-key refuses a snapshot signed by any other key or tampered with. A snapshot taken before signing was turned on, or any snapshot when the export has no keys/signing.pub.asc, is unsigned: give --allow-unverified in place of --trusted-key for it, never both. The procedure below says who does what.

The break-glass procedure

Write this down for your own organization and keep a printed copy with the escrow key, since the server it describes may be the thing that is gone.

  1. Prepare once. Make an escrow OpenPGP key pair that never lives on a SysManage server or a backed-up host, such as a smartcard or an offline machine. Decide who holds it; two people who must both be present is a common choice. Export every encrypted host's keys sealed to it, and store the export file and the escrow key in different places.
  2. Export again after every key rotation and every newly encrypted host. An export holds the keys that existed when it was made: a host's snapshots after a rotation need the new key, which an older export does not have. Replace the old file, and destroy it.
  3. Open it only for a restore. When SysManage or OpenBAO is unavailable and a backup is needed, the escrow key holders decrypt the export (gpg --decrypt, then tar -xf) on a trusted machine and read README.txt and manifest.json, which name each host's repository on the storage host.
  4. Find the snapshot. On the storage host, list the host's snapshots with all of its keys: sudo restate snapshots --decrypt-with keys/<host>/1-<fingerprint>.asc --decrypt-with keys/<host>/2-<fingerprint>.asc /srv/backups/restate/<repository>. Without the keys, restate lists only the names.
  5. Plan, then restore. Run restate restore --plan --trusted-key keys/signing.pub.asc with every key and the snapshot, check the list, then restore with --check-first --trusted-key keys/signing.pub.asc --root /restore/<host> into an empty directory, or a new machine's root. For an unsigned snapshot, use --allow-unverified in place of --trusted-key. Restored onto another operating system, owners and groups are matched by name, and a group that system lacks keeps its number.
  6. Destroy the opened keys. Delete the decrypted archive and every key file when the restore is done (shred -u on Linux, rm -P on FreeBSD, where the disk allows it). The sealed export stays in escrow.
  7. Rehearse it. At least once a year and after changing the escrow key: export, then restore one file from an encrypted repository using only the export and restate, with SysManage left out. A drill on 2026-11-02 restored a file from snapshots written under an old and a new key, and found two errors in the instructions, since fixed.

Escrow status. The Encryption panel shows when the last break-glass export was made, by whom, the key it was sealed to and how many encrypted hosts it covers. When an encrypted host, a key rotation or snapshot signing comes after it, the Backups page shows a warning with a link to the export, the dashboard's backups card says the export is out of date, and the advisor's PM-BACKUP-KEY-ESCROW check fails. Right after you turn encryption on, rotate a key or turn signing on, the panel offers to export at once; after a scheduled rotation, users with Manage Backups get an email when email is configured.

A remembered escrow key. An export can remember the public key you paste, and later exports start from it. Only the public half is stored, and a pasted private key is refused. Replace the escrow key changes it.

Making an escrow key

Make the key on your own machine or a hardware token, never on a SysManage server or a backed-up host. Use RSA 3072: libgcrypt 1.12.0 cannot decrypt with cv25519 keys (GnuPG T8094).

On Linux or macOS with GnuPG: gpg --quick-gen-key "Backup escrow <you@example.com>" rsa3072 sign,cert never, then gpg --quick-add-key <fingerprint> rsa3072 encr never, and gpg --armor --export <fingerprint> > escrow-public.asc for the public half.

On Windows, in Gpg4win's Kleopatra: File, New OpenPGP Key Pair, choose RSA 3072 under Advanced Settings, then Export the public key.

Paste only the public key into SysManage. Keep the private key offline, on a hardware token or an encrypted drive in a safe, with a backup copy somewhere else. Never upload it to SysManage: whoever holds it can read every exported backup key.

Grandfather-father-son retention

Beside Snapshots to keep, a host's backup policy can keep the newest snapshot of each of the last N days, weeks and months that have one: Days to keep, Weeks to keep and Months to keep (0 means not used). The storage host's prune applies them, as restate's --keep-daily, --keep-weekly and --keep-monthly; weeks are ISO weeks, and dates come from the snapshot names, in UTC.

Preview the next prune shows how many snapshots the next prune would keep and which it would remove, choosing exactly as restate does, before anything is deleted. Changing these settings needs Professional+, but once set they are always honored: a lapsed license never makes a prune delete history you chose to keep. Yearly retention comes with a restate that has --keep-yearly.

Years to keep is always shown beside them, as restate's --keep-yearly (restate 2.2.0.12 or later on the storage host). A yearly count is refused, with the reason, only when the storage host has reported that its restate cannot keep yearly snapshots, so a prune never runs without a rule you set; a policy that already keeps years always keeps them.

A new policy, from its dialog or from Set up backups for selected, starts with the newest 7 snapshots plus the newest of each of the last 14 days, 8 weeks, 12 months and 3 years. restate stores only what changed, so the extra snapshots cost little.

Scheduled verification

Read the whole repository back every (days) in a host's backup policy runs restate's check --read-all on that cadence: a test restore that writes nothing. It runs on the backed-up host, which receives the policy's keys for that one job when the repository is encrypted, so the storage host still never holds a key. It never starts while a capture of the host is queued or running, it waits for the host's maintenance window like a capture, a failed pass is retried a day later, and one refused because the storage host was pruning or checking the repository is retried after 30 minutes.

Each pass reads every pack of the repository through the host's mount, so it costs the repository's full size in network traffic: choose weeks rather than days (30 is a good start; 0 turns it off). The host's Backup card shows the last passed verification, and the Backups page marks a host whose last pass failed or that has not passed one within its cadence. Setting the cadence needs Professional+; without the engine nothing new is scheduled, and an old pass ages into "not verified".

Backup alerts

With the alerting engine, a Backup health rule raises one alert per host when its backups need attention: the last backup failed or is overdue, the last repository check failed, or its write cache is over the target's budget. On the storage host it also covers the target's storage problems: a failed drive, critically full storage, or a seal, prune or check that has not run in time. A failed backup, a failed drive or critically full storage is critical; anything else is a warning. The alert is escalated in place, resolved, with a notice, when everything is healthy again, and repeated daily until someone acknowledges it. A host without a backup policy is never alerted on.

The rule's parameters: statuses (default ["failed", "overdue"]; add "incomplete" for backups that skipped unreadable files), max_age_hours (also alert when there has been no good backup in that many hours), check_failed, write_cache and storage (each on by default), and renotify_minutes (1440).

Scheduled verification feeds the same rule: a failed full-read pass is critical, and a host that has not passed one within its cadence is a warning. Turn both off with verification set to false in the rule's parameters.

Reports, compliance and forecasting

The Backup SLA report (Reports, with the reporting engine) lists every backed-up host: its backup interval, last good backup, whether its recovery point objective is met now (the RPO is twice the backup interval, the same line at which a host is called overdue), on how many of the last 30 days it was met, its failed backups in that time, its last full-read verification and its repository size.

With the compliance engine, the rule SYSMANAGE-BACKUP-1 (benchmark SYSMANAGE, scanned with ALL) passes when the host's backups passed a full-read verification within 30 days. A host without a backup policy is not applicable, so hosts you do not back up do not lower their score.

With the advisor engine, the Posture punch list carries four backup checks: every host restate can back up has a policy, no host's backups failed or fell behind, every host passed a full-read verification in the last 30 days, and every encrypted host's keys were exported for break-glass after its newest key was made. Each counts hosts as passing, failing or not yet known, and its fix opens the Backups page.

The target card forecasts how fast the backup storage is filling: the bytes the last 30 days of captures added, less what that period's prunes freed, per day, and the days until the storage path's filesystem reaches its warning and critical marks (85% and 95% unless the target sets its own).

Package-level restore

A restore can put the snapshot's packages back before its files: its repositories and their keys, each apt package at the version recorded, what was installed by hand and what as a dependency, and its snaps and flatpaks. Then apt removes the packages the snapshot did not have, so the host's packages match the snapshot. In the Restore files dialog, tick Put the snapshot's packages back first; it restores into place, because the packages go onto the host itself.

Preview first. The preview is planned from the snapshot's index in seconds and shows what will happen: the apt packages and their versions, the snaps, how many repository keys, and a warning that unlisted packages are removed, with the whole generated script one click away. The real restore needs its own confirmation, and both are audited. Anything installed since the backup can be removed, the SysManage agent included if it was installed later, so on a running host name the paths to put back and read the preview; the natural use is a fresh machine being rebuilt into an old one.

Package-level restore needs the Professional+ backup engine and a restate on the host that takes packages in a restore job (2.2.0.16 or later).

Drift timeline

After every good backup the host compares the new snapshot with the one before it, by package: which packages were installed, removed or upgraded, and the file changes no package accounts for, such as an edited configuration file. The host's Backup tab shows these comparisons newest first as the Drift timeline. An encrypted repository's keys are released for each comparison only, as for a restore.

Expected churn is hidden and counted: logs, caches, temporary files, package lists and SysManage's own job files and agent state, plus the host's own patterns under Also hide on this host, written like the backup's leave-out patterns. Show everything brings them back. A pair of backups that was never compared can be compared from the timeline.

What changed between backups opens the timeline from a host's configuration-drift differences and from its Software Changes tab, so a drifted file or an unexpected package can be traced to the backup it first appeared in.

The drift timeline needs the Professional+ backup engine and a restate on the host that runs diff as a job (2.2.0.16 or later).

Backup policies by tag

A tag policy gives every host carrying a tag the same backup settings: schedule and start hour, retention (including days, weeks, months and years), the services to pause, the paths to leave out or also back up, and the full-read check cadence. Add one under Policies by tag on the Backups page: name it, pick the tag, set a priority, and set the settings. Tag a new host and it gets them on the scheduler's next pass, or at once with Apply now; remove the tag and the policy that tag gave it is removed (its repository and snapshots are left alone).

Where several tag policies cover one host, the lowest priority number wins. A host's own policy, saved with Configure, always beats every tag policy; the host's Backup card says which applies ("From tag policy Servers nightly (priority 10)" or "This host's own policy"). To return a host to its tag policy, remove its own policy. Switching a tag policy off pauses it: its hosts keep what it last gave them.

Creating, changing and removing a tag policy, and each host it sets or removes, are audited. Tag policies need the Professional+ backup engine; without it the policies they set keep running, but nothing new is applied.

Requirements

  • A Professional+ license with the backup_engine module, and the alerting_engine module for backup alerts.
  • GnuPG (gpg) installed on the SysManage server, which makes and seals the keys, and OpenBAO, which holds them.
  • restate on each host and the storage host, as for every edition; restoring encrypted backups needs a restate that takes decrypt_with.
