Automatic Updates

An update profile can apply updates on its own schedule. The server runs each due profile, works out exactly which pending updates each host may take, sends them, records what happened, and reboots only when you have said it may. Everything it does can be stopped at once, and every step is in the audit log.

Overview

Turn on Apply automatically on this schedule in an update profile (Settings, Update Profiles) and the profile becomes a policy. Its cron schedule says when; its tag, or the hosts it lists by name, say where; security-only and the package-manager list say what. Profiles without the option still run only when someone presses Trigger Now.

What a Run Applies

Each run sends a host exactly the pending updates shown for it at that moment, named one by one, so a run never installs something nobody could see beforehand. Some updates are never applied automatically, whatever the policy says:

  • Held packages -- a package pinned on the host (apt-mark hold, pkg lock) is left alone and shown as held. A version locked with dnf's versionlock never appears as an update at all.
  • Excluded packages -- names the policy excludes, with * matching anything (linux-image-*, postgresql*).
  • Operating system upgrades -- moving to a new release is always a person's decision.
  • Firmware -- only when the policy's package managers include fwupd.
  • The SysManage agent itself -- the agent updates through Update Agent, which is built for the agent restarting under it.

A host with nothing eligible is recorded as having nothing to do, which is neither a success nor a failure. The profile's staggered window spreads the hosts' start times so a whole fleet does not update at the same second.

Which Policy a Host Follows

A host covered by several policies follows one: the most specific (hosts listed by name, then a tag, then every host). Between equally specific policies the more conservative wins -- security-only before everything, no reboot before reboot. The host's Software Changes tab names the policy it follows and why.

Staying in Control

  • Never update a host automatically -- a switch on the host's Software Changes tab, with a reason. It beats every policy.
  • Hold -- pause one policy from its row, or every policy at once with Hold every policy, each with a reason. Nothing starts while a hold is on.
  • After a failure -- a host whose last run failed, partly failed or never reported is not tried again until someone acknowledges the run, or until the retry hours (24 by default) have passed.
  • A broken package manager -- a host whose package manager needs repair is skipped, and says so, instead of failing every night.
  • Backups first -- with Only after a good backup within set, a host without a good backup that recent is skipped.

Inside Maintenance Windows

A host that maintenance windows apply to is updated only inside one. When its policy fires while the window is closed, the run waits and says when the window opens; when it opens, the run is planned again, so it applies what is pending and eligible then. A run starts only if it is expected to finish before the window closes, judged from how long the host's earlier runs took. A run that fits no window in the coming week is skipped and says so. A host with no window is updated on its policy's schedule.

  • Blackouts win -- nothing is applied or rebooted automatically during a blackout, even a run that was already waiting to go out.
  • No override -- an emergency override lets a person's change through a closed window, never an automatic run or reboot.

Waiting Periods

A policy can hold updates back for a number of days before applying them, with two separate counts: one for regular patches and one, usually much shorter and often 0, for patches that fix a critical CVE. The days count from when the host first saw the update, or from the vendor's release date if that was earlier, so a host that came online late does not wait twice. With both counts at 0 every eligible update is applied on the next run.

  • What counts as critical -- the update reaches the fixed version of a CVE that the host's vulnerability scan rates critical, or of a vendor advisory marked critical. The policy chooses which of the two it trusts, or either; the Update Profiles page sets whether high counts as critical too.
  • Without that data -- a host with no vulnerability scan or vendor advisories never has a critical patch, so everything on it waits the regular count, and its Software Changes tab says so.
  • Shown, not guessed -- the host's Software Changes tab lists each pending update and when it becomes eligible: "critical CVE-2026-1234: eligible now", "regular: eligible on" a date, or why it is never applied automatically.
  • Dependencies come along -- when an eligible update needs a newer version of a package that is still waiting, the package manager installs that version with it. Applying the eligible update, often a critical fix, matters more than holding its dependency back, so the waiting package is upgraded early on that run.

Rolling Out Fleet by Fleet

A policy can roll out across fleets instead of patching every host it covers at once. Each fleet is the hosts carrying a tag, and the fleets go one at a time in the order you set; the first is the canary, a small group you trust to show problems first. A fleet finishes, then soaks for its soak time, and only a healthy fleet lets the next one start.

  • Healthy -- no more of the fleet's runs failed than the policy allows (0% by default: any failure), every host that rebooted came back, every host that was patched is still reporting, and no critical alert was raised on the fleet's hosts since it started. The checks keep running through the soak.
  • Halted -- otherwise the rollout stops at that fleet, says why and names the hosts that caused it, and nothing more is patched until someone resumes it (with a reason) or cancels it. While a rollout is running or halted, the policy does not start another.
  • Each host once -- a host in several fleets is patched with the first one that contains it, and hosts in no fleet go last, as the remaining hosts.
  • Windows and waiting periods still apply -- each host applies only inside its own maintenance windows and only updates past their waiting period, so a fleet is done when every host that could apply did; the rollout lists the rest with the reason.

Reboots

By default a policy never reboots: a host that needs one shows "reboot required", as it does today. With Reboot when the update needs it, the server sends one reboot after a run that needs it -- including when the host only reports the need a little later -- and records it in the audit log. It then watches for the host to come back: a host that has not started up again within the reboot timeout (30 minutes by default) is flagged on its run and counted on the dashboard.

With Reboot when needed, only inside a maintenance window, the reboot happens only while the host is inside a window with time left for it. Otherwise the host stays "reboot required", the run says it waits for the next window, and the reboot is sent when that window opens. A run under this option counts the reboot's time when deciding whether it fits the window.

Results

Every run is kept: the packages it applied, the ones that failed with the package manager's own message, the ones it left out and why, and the reboot. A host's runs are on its Software Changes tab beside the updates applied by hand. The Update Profiles settings page lists the runs that need someone to look, and the home dashboard counts them.

The audit log records every policy change, hold, opt-out, run and automatic reboot, with the policy and the packages named.

Alerts, Report and Dashboard

  • Alerts -- an alert rule on the Automatic Updates Need Attention condition raises one alert per host when its last automatic run failed, it did not come back from an automatic reboot, a rollout halted because of it, a patch for a critical CVE is still not applied a set number of hours after its waiting period (24 by default), or its policy has been on hold longer than a set number of days (7 by default). The alert updates as problems come and go, and is resolved when they are gone.
  • Report -- the Automatic Updates report shows, per policy and fleet over the last 30 days, the runs, hosts patched, failed runs, reboots, and the median time from a patch for a critical CVE appearing on a host to its being applied there.
  • Dashboard -- the home page counts automatic update problems, automatic reboots waiting for a maintenance window, and rollouts in progress or halted.

Requirements

  • Enterprise license with the automation engine. Without it nothing is applied automatically, and updates are applied by hand as before.
  • The Apply Software Update role to turn automatic application on, change a policy's automatic settings, hold, opt a host out or run a profile now.
  • A current agent, so that held packages and the time the host started are reported.
  • For a shorter wait on critical patches: vulnerability scanning or vendor advisories for the host. Without either, every patch waits the regular count.
