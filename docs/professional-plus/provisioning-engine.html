Provisioning Engine

Stand up brand-new hosts that auto-enroll into the fleet on first boot. A pluggable compute-provider model drives remote libvirt and Proxmox VE; reusable provisioning templates render the first-boot artifacts; and a paste-and-go credential flow stores provider secrets in OpenBAO so an operator never hand-manages a vault path.

Overview

Every other deployment path in SysManage assumes a host is already running an agent. The Provisioning Engine closes that gap: it actuates a compute provider (server → hypervisor API) to clone a base image, attaches a first-boot cloud-init seed carrying the tenant enrollment token, and the new host installs the agent and self-registers into the correct tenant and site. Adding a provider is incremental — every backend implements one create / status / destroy / console contract behind a capability descriptor.

Community Edition vs Professional+

  • Community Edition: deploy plans require a host that already runs an agent — there is no net-new provisioning.
  • Professional+: author reusable, versioned provisioning templates (cloud-init / kickstart / preseed / autoinstall).
  • Enterprise: configure compute resources, provision hosts on remote libvirt / Proxmox, and drive first-boot auto-enrollment.

Compute Providers

A compute resource points the engine at a provider endpoint. The list view shows each resource's name, kind, connection, and credential reference; the secret it points at is never displayed. Two providers ship today:

  • Remote libvirt — connect over qemu+ssh://user@host/system. The engine stages an overlay disk plus a NoCloud seed ISO into the pool, then defines and starts the domain. Local and remote differ only by the connection URI.
  • Proxmox VE — connect over the HTTP API with an API token. The engine clones a cloud-init-ready template, applies size and cloud-init settings, and boots it.

Paste-and-Go Credentials (OpenBAO)

Adding a resource is a paste-the-secret-and-go experience — the operator never touches OpenBAO directly. The form is provider-aware: a Proxmox resource takes a host, port, and API token; a libvirt resource takes a connection URI and an SSH private key. On save, the backend writes the pasted secret to a tenant-namespaced OpenBAO path and stores only that path (credential_ref) on the row. The secret itself never lands in the database, and it is never returned by the API. An Advanced toggle still lets an operator reference an existing OpenBAO path instead of pasting a secret.

  • Proxmox API token → stored in OpenBAO, used as the provider's bearer token.
  • libvirt SSH key → stored in OpenBAO, written to a transient 0600 keyfile at provision time.
  • Proxmox node SSH key → stored in OpenBAO, used to place the auto-enroll snippet on the node (see below).
  • Non-secret provider settings (e.g. the node SSH user) live in a dedicated config column, never in the vault.

First-Boot Auto-Enrollment

When a provision request carries a server host and an enrollment token, the engine renders a cloud-init user-data that writes /etc/sysmanage-agent.yaml (with the tenant enrollment token) and installs plus starts the agent on first boot. Delivery is provider-specific: libvirt attaches a NoCloud seed ISO, while Proxmox drops the user-data as a cicustom snippet on the node over SSH (the HTTP API cannot upload snippets). The enrollment token can also carry a site and access group, so the host lands in the right tenant, site, and group with no manual step.

server:
  url: "https://sysmanage.example"
security:
  enrollment_token: "sme_..."
  registration_key: "rk_..."

Bare-Metal Provisioning (PXE)

Compute providers cover machines a hypervisor can create. Bare metal is the case where nothing exists yet: a physical server arrives with an empty disk and no operating system. SysManage drives it over PXE — the machine network-boots, asks who it is, and is handed an installer that lays down its assigned OS and enrolls it into the fleet unattended. The operator supplies a MAC address and an OS choice; everything after that is automatic.

The full path is: machine network-boots → the per-MAC boot endpoint resolves its assignment → an answer file is generated for that machine → the OS installs unattended → a first-boot script installs the agent with a single-use enrollment token → the host appears in the correct tenant → netboot is disarmed so the machine boots from its own disk from then on.

Readiness Preflight and the Config Advisor

PXE needs DHCP, TFTP, and HTTP on a designated provisioning-server host. Rather than assume they exist, SysManage probes for them and refuses to arm a machine until the roles it needs are present. The probe is read-only; nothing is installed without an explicit action.

Once the tooling is present, the config advisor renders a ready-to-apply dnsmasq configuration for the segment. It has two modes, and choosing correctly matters more than it appears:

  • own-DHCP — SysManage is the DHCP server for the provisioning segment, handing out both addresses and the boot file. Use this on an isolated build network. Two authoritative DHCP servers on one segment will fight, so this mode must not be pointed at a network that already has one.
  • proxyDHCP — the existing corporate DHCP server keeps handing out addresses, untouched, and SysManage answers only the PXE part. Use this when you cannot change the incumbent DHCP server, which is the common case in a real datacenter.

The advisor also emits the firewall rules the chosen mode needs (UDP 67 for DHCP, 69 for TFTP, 4011 for PXE boot-server discovery, plus the server's HTTP port), detected per platform rather than assumed.

Install-Source Catalog

An install source is one bootable OS install tree: an OS family and version, an architecture, the kernel and initrd paths within the tree, and the tree URL itself — which can point at a public mirror, a mirror maintained by repository mirroring, or an air-gapped install tree.

The answer-file dialect is derived from the OS family rather than being a free-text field, because getting it wrong is the single easiest way to end up with a machine that boots correctly and then waits forever at an interactive prompt. Each family maps to the unattended-install format its installer actually speaks:

  • Debian → preseed; Ubuntu → autoinstall (Subiquity)
  • RHEL / Rocky / Alma → kickstart; SUSE → autoyast
  • FreeBSD → bsdinstall — note that FreeBSD netboots via pxeboot plus an mfsroot, not the Linux kernel-and-initrd shape, so its install source is described differently

A source that is still referenced by an assignment cannot be deleted — removing it would leave a machine booting toward a tree that no longer exists.

Per-MAC Assignment and Netboot Arming

An assignment pins one MAC address to one install source, optionally with a hostname, site, and access group. When that machine network-boots, the per-MAC boot endpoint resolves the assignment and serves the matching installer — which is what makes “Ubuntu on this box, Rocky on that one, FreeBSD on a third” a deliberate choice rather than an accident of boot order.

Netboot armed is the safety-critical field on this page. While a machine is armed it will reinstall itself — erasing its disk — every time it network-boots.

Arming is derived from install state rather than being a free-standing switch. A machine is armed while it is assigned, building, or failed, and is disarmed once it reports installed or agent_missing. That is what stops a finished server from reinstalling itself on every reboot.

Re-arming an already-installed machine is deliberately a confirmed action, because it is destructive: the next network boot wipes the disk and reinstalls from scratch. Use it to rebuild a machine in place.

Why an Install Ended That Way

A machine reports its own outcome when the install finishes, and that report is kept on the assignment. This matters because the failure that costs the most time is not a machine that fails loudly — it is one that installs perfectly and then never appears in the fleet. Before the machine reported anything, the reason for that lived only in bootstrap output on a console nobody was watching.

Two outcomes are therefore recorded separately, and the difference is not cosmetic. installed means the agent is up. agent_missing means the operating system installed and the agent did not — the machine is usable but will never enrol until someone looks at it. A third state, failed, means the install itself did not complete.

Both installed and agent_missing disarm netboot; only failed stays armed for another attempt. That asymmetry is deliberate: an install that did not complete should be retried, but a machine whose OS is fine and whose agent is broken must never be reinstalled — that would erase a working system to fix a package.

The report holds a one-line reason and the tail of the bootstrap log, so a row reads agent install failed: Unable to locate package sysmanage-agent rather than simply installed. Reporting is best-effort and never blocks the disarm: a machine that cannot reach the server at all still stops netbooting, because a machine stuck reinstalling itself is a worse outcome than one with a missing agent.

The answer file a machine fetches is guarded by a single-use, expiring boot token rather than by credentials — a machine partway through a network boot has no identity to authenticate with. The token is minted per boot, and the plaintext is never returned by the API.

Host Discovery

Racking a new machine usually means nobody has written its MAC address down. Discovery removes that step: hardware that network-boots without an assignment is booted into an ephemeral RAM probe — nothing is written to disk — which reports what the machine is and parks it in a discovered-hosts list.

Each entry carries manufacturer and model, CPU and core count, memory, disk count and primary disk, and serial number — enough to tell a 256 GB compute node from a 64 GB edge box without walking to the rack. Assigning an OS from here is the fast path: the MAC is already known, so the operator only chooses an install source. A machine that should not be provisioned can be ignored instead.

Boot Media for Networks Without PXE

Not every network can PXE boot — a segment may have no DHCP you are allowed to touch, or the machine may sit somewhere PXE traffic does not reach. For those cases an assignment can be turned into boot media directly, and the rest of the flow is identical once the machine starts.

  • iPXE script — a few hundred bytes, for a machine that already network-boots but is pointed elsewhere.
  • Bootable ISO — write it to a USB stick or attach it to a remote console. Building an ISO needs xorriso or genisoimage on the server; when neither is present the option is disabled and says so rather than failing at download time.

Endpoints

  • GET/POST/DELETE /api/v1/provisioning/compute-resources — manage provider endpoints (Enterprise)
  • GET/POST/PUT/DELETE /api/v1/provisioning/templates — author provisioning templates (Professional+)
  • POST /api/v1/provisioning/provision — provision a host; poll /jobs/{id} for progress
  • GET /api/v1/provisioning/providers — capability descriptors for every registered provider
  • GET/POST/DELETE /api/v1/provisioning/install-sources — the bootable OS install-tree catalog (Enterprise)
  • GET/POST/DELETE /api/v1/provisioning/install-assignments — pin a MAC to an install source; POST .../{id}/rearm re-arms netboot (Enterprise)
  • GET /api/v1/provisioning/discovered-hosts — the discovery parking lot; POST .../{id}/assign and .../{id}/ignore act on an entry (Enterprise)
  • GET /api/v1/provisioning/bootdisk/status and POST /api/v1/provisioning/bootdisk/{id}.ipxe|.iso — boot media for networks without PXE (Enterprise)
  • GET /api/v1/provisioning/readiness/{host_id} plus /advice, /apply, /install and /refresh — the preflight probe and config advisor (Enterprise)
  • GET /api/v1/provisioning/boot.ipxe and /answer/{token} — consumed by the booting machine itself. Deliberately unauthenticated: a machine partway through a network boot has no credentials, so these are guarded by a single-use, expiring boot token instead.

Feature Codes

Endpoints are gated by these feature codes (the open-source server returns 402 when the module isn't loaded):

  • provisioning_templates_manage — template authoring (Professional+)
  • provisioning_manage — compute resources, provisioning, bare metal, and discovery (Enterprise)

Architecture

The engine is a Cython-compiled binary (provisioning_engine.so) loaded by the open-source server's module_loader at startup. It exports the standard get_module_info() + get_provisioning_router() contract, so mount_provisioning_routes() mounts it alongside the 402 stubs. Compute resources, templates, and jobs are per-tenant operational data read from the active tenant database; provider secrets are brokered from OpenBAO by reference and are never stored in a row.
