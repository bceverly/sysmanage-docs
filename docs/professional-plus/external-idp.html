External Identity Providers

Sign in to SysManage using your existing LDAP/Active Directory or OIDC identity provider. External group membership maps to sysmanage roles automatically; a break-glass local-password fallback keeps you in the door if the directory is unreachable.

Overview

The external_idp_engine Pro+ module performs the actual authentication -- an LDAP bind+search for AD/LDAP providers, or an OIDC authorization-code exchange. The OSS server holds the configuration tables, the Settings UI, and the routes that 402 without the engine loaded; the engine is stateless and never touches the database directly.

LDAP / Active Directory

For each LDAP provider, configure:

  • ldap_server_url -- typically ldaps://ad.example.com:636. Plain ldap:// is supported but logged as a warning.
  • ldap_bind_dn + ldap_bind_password_secret_id -- service account used for the user-search bind. The plaintext password lives only in Vault; the server unseals it before passing to the engine.
  • ldap_user_search_base + ldap_user_search_filter -- where to look up the user. The filter must contain %s for the username, e.g. (sAMAccountName=%s) for AD or (uid=%s) for OpenLDAP.
  • ldap_group_search_base + ldap_group_search_filter -- optional. When set, the engine queries the user's group memberships after a successful bind; matched cn values are passed to the role-mapping step.
  • ldap_tls_ca_bundle_path + ldap_connection_timeout -- TLS verification bundle and connection timeout (default 10 s).

Authentication flow: the engine binds as the service account, searches for the user, then binds as the user with the supplied password to verify it. RFC 4515 filter-injection escapes are applied to every interpolated value.

OIDC

For each OIDC provider, configure:

  • oidc_issuer_url -- the IdP's HTTPS root, e.g. https://login.example.com.
  • oidc_client_id + oidc_client_secret_secret_id -- the application registered with the IdP. The client secret is Vault-stored.
  • oidc_redirect_uri -- the URL the IdP bounces the browser to after the user signs in. Typically https://your-sysmanage.example.com/api/auth/oidc/{provider_id}/callback.
  • oidc_scopes -- space-separated, default openid profile email. Add groups (or your IdP's group claim scope) when you want role mapping.
  • oidc_discovery_url -- optional override for the well-known discovery doc. Defaults to {issuer}/.well-known/openid-configuration.
  • oidc_group_claim -- name of the ID-token claim that lists the user's groups (default groups; some IdPs use roles or a custom name).

After the email step, the login page shows a Sign in with button for each provider the address may use. It sends the browser to /api/auth/oidc/{provider_id}/start, which 302s to the IdP's authorization endpoint with a CSRF-protecting state token. After the user signs in, the IdP returns to /api/auth/oidc/{provider_id}/callback?code=…&state=… and the engine exchanges the code for an ID token. The sub claim is matched against the user's external_subject column to locate the local account.

SAML 2.0

For each SAML provider, configure:

  • saml_idp_entity_id, saml_idp_sso_url and saml_idp_x509_cert -- the IdP's entity ID, its sign-on URL, and the certificate that verifies its signatures.
  • saml_sp_entity_id and saml_sp_acs_url -- this server's identity at the IdP. The ACS URL is typically https://your-sysmanage.example.com/api/auth/saml/{provider_id}/acs; the IdP can import both from /api/auth/saml/{provider_id}/metadata.
  • saml_email_attribute and saml_group_attribute -- the assertion attributes that carry the user's email (the NameID is used when empty) and group memberships (default groups).
  • saml_want_assertions_signed -- require the IdP to sign its assertions. On by default; leave it on.

Requiring Multi-Factor Sign-In

Single sign-on leaves multi-factor authentication to the identity provider, and SysManage accepts the token the IdP returns. Turn on Require multi-factor sign-in on an OIDC or SAML provider and SysManage refuses a sign-in whose token does not say the user signed in with more than one factor, so a misconfigured or bypassed IdP policy no longer goes unnoticed. It is off by default; turn it on for any console reachable from the internet.

  • OIDC: the ID token's amr claim must contain mfa (RFC 8176). Microsoft Entra ID sets it in v1.0 tokens only; its v2.0 tokens carry no amr at all, so use the v1.0 endpoints (see the Microsoft 365 walkthrough below). For an IdP that expresses assurance through acr instead, list the accepted values in oidc_acr_values; they are also requested at sign-in.
  • SAML: the assertion's AuthnContextClassRef must be one of saml_mfa_authn_contexts, one per line; empty means Microsoft Entra ID's http://schemas.microsoft.com/claims/multipleauthn. The AuthnRequest asks the IdP for that context.

A refused sign-in lands on the login page with "Your identity provider did not confirm multi-factor sign-in", and the server log records the provider and what the token said instead.

Walkthrough: Microsoft 365 / Entra ID

Verified against a real Entra ID tenant: sign-in, group-to-role mapping, just-in-time accounts and required multi-factor sign-in. You need rights to register applications in the tenant.

  1. Register the app. In the Entra admin center, under App registrations, choose New registration: single tenant, platform Web. For the redirect URI, save the provider in SysManage with its Redirect URI left blank: SysManage fills it in (https://CONSOLE/api/auth/oidc/PROVIDER_ID/callback), and the field's copy button gives you the exact value to paste. Entra accepts plain http:// only for localhost. Note the Application (client) ID and the Directory (tenant) ID.
  2. Create a client secret under Certificates and secrets, and give SysManage a reference to it in the client-secret field: a vault path, or literal: followed by the secret for a test.
  3. Token configuration: add a groups claim (Security groups, emitted as Group ID) and the optional ID-token claim email, which just-in-time accounts need.
  4. Groups: under Groups, create security groups (for example SysManage Admins) and add the users; map each group's Object ID to a SysManage role on the provider.
  5. The SysManage provider: issuer https://sts.windows.net/TENANT_ID/, discovery URL https://login.microsoftonline.com/TENANT_ID/.well-known/openid-configuration, scopes openid profile email, group claim groups. These are Microsoft's v1.0 endpoints, which Require multi-factor sign-in needs: Entra's v2.0 ID tokens carry no amr claim, so with MFA required every v2.0 sign-in is refused.
  6. Just-in-time accounts: set the provider's Tenant ID and add the users' email domain to that tenant's email domains. The login page then offers this provider to every address in that domain.
  7. Multi-factor sign-in: enforce it in Entra (security defaults or a Conditional Access policy) and turn on Require multi-factor sign-in, so SysManage also refuses any token that does not show it.
  8. The console's address: set webui.public_url to the address users sign in from. If the redirect URI's host differs from it, the sign-in hand-off never reaches the console and users see "The single sign-on session has expired" right after signing in; the server log names both hosts.

Signing In from the Login Page

The login page asks for the email address first. The next step offers the password and a Sign in with button for each enabled OIDC or SAML provider that address may use: the server-wide providers, plus those of the tenants that list the address's domain among their email domains. The answer depends only on the domain, never on whether an account exists, so the page cannot be used to probe for accounts. On a server with no such provider, the second step shows only the password.

When the IdP returns the browser, sysmanage signs the user in and redirects to the console's /login/sso page. The session travels in a two-minute HttpOnly cookie that the page exchanges once -- never in the URL, where it would end up in browser history and server logs.

The console's address comes from webui.public_url in sysmanage.yaml. Set it, and register the redirect and ACS URLs on that same host name: the browser only returns the hand-off cookie to the host that set it.

If the sign-in does not complete, the user lands on the same page with the reason (for example, an identity with no active sysmanage account) and a way back to the password form. The details are in the server log.

External Group → sysmanage Role Mapping

Each provider has a per-row mapping table that translates external group identifiers into sysmanage SecurityRole names. Rules:

  • If any of the user's external groups matches an entry's external_group, the entry contributes its role_name. Multiple matches are unioned.
  • If no entries match AND a mapping has default_for_unmapped=true, that entry's role is granted as a catch-all (e.g. read-only viewer for anyone who authenticates successfully but isn't in a privileged group).
  • The result is deduped before being applied to the user's role set. Roles already granted locally aren't touched -- only the names that overlap with the mapping output get reconciled.

Linking sysmanage Accounts to External Identities

Existing sysmanage user rows pick up two new columns that link them to a directory:

  • external_idp_provider_id -- FK to the provider row. NULL for local-only accounts (the default).
  • external_subject -- IdP-side stable identifier. For LDAP this is the user's full DN; for OIDC it's the sub claim. Used to re-link if the userid changes.

OIDC and SAML users need a sysmanage account linked to their identity before their first sign-in, unless the provider has JIT provisioning enabled; without one, the sign-in lands back on the login page saying so. LDAP users authenticate via the password form and follow the existing user-creation flow.

Local-Account Fallback

When the singleton external_idp_settings row has local_account_fallback=true and the engine declines (LDAP server unreachable, password rejected, etc.), the login flow falls through to local Argon2 verification. This is the break-glass admin path -- the local password row stays usable even after a user is linked to an external IdP. Setting it to false hard-locks accounts to their external directory.

API Reference

Every route below returns 402 without external_idp_engine loaded.

  • GET /api/idp-providers -- list providers
  • POST /api/idp-providers -- create a provider
  • GET /api/idp-providers/{id} / PUT / DELETE -- CRUD on a single provider
  • GET / POST /api/idp-providers/{id}/role-mappings -- role mappings for the provider
  • DELETE /api/idp-providers/{id}/role-mappings/{mapping_id} -- remove a mapping
  • GET / PUT /api/settings/idp -- cross-provider settings
  • GET /api/auth/oidc/{provider_id}/start -- anonymous; redirects browser to IdP
  • GET /api/auth/oidc/{provider_id}/callback -- anonymous; exchanges the code, lands the browser on the console signed in
  • GET /api/auth/saml/{provider_id}/start -- anonymous; redirects browser to IdP
  • POST /api/auth/saml/{provider_id}/acs -- anonymous; verifies the assertion, lands the browser on the console signed in
  • GET /api/auth/saml/{provider_id}/metadata -- anonymous; this server's SP metadata, for the IdP
  • GET /api/auth/sso/providers -- anonymous; the server-wide providers (empty without the engine)
  • POST /api/auth/login/discover -- anonymous; step one of the login page: the password and the providers an email address may use, decided by its domain alone
  • POST /api/auth/sso/session -- exchanges the one-shot hand-off cookie for the session
