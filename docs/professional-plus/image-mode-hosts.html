Image-Mode Host Management

Manage hosts that boot from an atomic OS image — Fedora/RHEL bootc, or rpm-ostree / OSTree systems like Fedora CoreOS — instead of a mutable package set. Detection is automatic and always visible; the Enterprise image_mode_engine adds first-class Stage, Apply, and Rollback actions on the whole image. This is Satellite image-mode parity.

Overview

An image-mode host boots its entire operating system from a single, versioned, digest-identified image rather than from a mutable set of installed packages. You don’t dnf install into it — instead you swap the image and reboot. The whole OS is an atomic artifact you can advance forward or roll back as a unit. SysManage manages these hosts through the compiled Enterprise image_mode_engine.

Two backends are supported: Fedora/RHEL bootc (container-native image mode), and rpm-ostree / OSTree systems such as Fedora CoreOS. SysManage detects which one a host uses and drives the right commands underneath a single, uniform set of actions.

Detection Is Automatic (and Free to See)

Every agent reports whether its host is image-mode as part of its normal check-in. When a host is image-mode, that report also includes:

  • the backend — bootc or rpm-ostree;
  • the booted image reference and its digest;
  • any staged (pending, next-boot) deployment;
  • whether a rollback deployment is available.

This detection rides the standard host check-in, and the display of this state is always visible — you can see whether a host is image-mode, and its booted/staged/rollback state, without an Enterprise license. Only the actions that change the image (Stage, Apply, Rollback) are gated on the image_mode_engine.

The Image Mode Tab

An Image Mode tab appears on the host detail page — but only for hosts that are actually image-mode. It surfaces the booted, staged, and rollback image state reported at check-in, and provides three first-class actions for advancing or reverting the OS image.

Stage, Apply & Rollback

These are the Enterprise actions the image_mode_engine adds. Each operates on the whole OS image and maps to the native command for the host’s backend:

  • Stage — fetch and stage the newest image (or rebase to a chosen image reference) without rebooting (bootc upgrade / rpm-ostree upgrade). The staged deployment becomes the next-boot image.
  • Apply — boot into the staged image (bootc upgrade --apply, or stage + reboot for rpm-ostree).
  • Rollback — return to the previous deployment and reboot into it (bootc rollback / rpm-ostree rollback).

Apply and Rollback reboot the host, so the UI confirms before it proceeds. These actions are distinct from package updates — they operate on the whole OS image, not on individual installed packages.

Package-Update UI Is Gated Off

Because you don’t apply package updates to an image-mode host, the Updates and Request Available Packages actions are hidden for these hosts. You manage the operating system through Stage / Apply / Rollback on the Image Mode tab instead — advancing or reverting the whole image rather than patching packages inside it.

Requirements

  • An Enterprise license with the image_mode_engine loaded (required for the Stage, Apply, and Rollback actions; detection and display are always available).
  • The host must be a bootc or rpm-ostree / OSTree system, with the bootc or rpm-ostree tool present.
