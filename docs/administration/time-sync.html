Time Sync

A clock that is off breaks what security rests on: certificate validity, Kerberos (which allows five minutes), one-time MFA codes, token expiry, and the order of events in the audit log. SysManage measures every host's clock itself -- it does not take the host's word for it -- and shows each one against the bounds you set.

How a clock is measured

The server and the agent timestamp the messages they already exchange, the way NTP does: the server notes when a message leaves and when the reply arrives, and the agent notes when it received the message and when it sent the reply. The time the reply waited in a queue cancels out, so the offset is accurate to a few milliseconds even over a busy connection -- within 2 ms of a reference clock on every platform tested. Each host's offset is the median of its last nine measurements, so one slow round trip is not mistaken for a clock that is off.

Because the measurement does not depend on the host's own time service, a host whose time service is broken -- or reports that it is synchronized when it is not -- is still measured. A host so far off that the server refuses its messages (more than 30 minutes) is measured from those messages' timestamps instead, to the second rather than the millisecond, so the hosts that need attention most are never left out.

The server's own clock

Every offset is relative to the server, so the server checks its own clock first, against the NTP server named by time_sync.reference in sysmanage.yaml (pool.ntp.org by default). An air-gapped site names its internal NTP server there. When the server's own clock is more than 100 ms off its reference, host clocks are not judged -- the Time Sync page says why -- rather than blaming the hosts for the server's error. When the reference cannot be reached or none is set, hosts are still judged against the server's clock, and the page says that clock could not be checked.

What each status means

  • In bounds The offset is below the warning bound.
  • Warning The offset is at or beyond the warning bound.
  • Critical The offset is at or beyond the critical bound.
  • Not measured The host has not been measured yet -- its agent is too old, or it has not connected.
  • No recent measurement The last measurement is more than 30 minutes old; the host is probably not connected.
  • Server clock off The server's own clock is off its reference, so no host is judged.

A host that has not been measured is never shown as in bounds.

A host's clock

The Clock card on a host's overview shows the measured offset and round trip beside what the host's own time service says about itself -- which service it runs (chrony, ntpd, systemd-timesyncd, OpenNTPD, Windows Time or macOS), whether it is running and synchronized, its source and stratum, and its own estimate of the offset -- so a service that claims to be synchronized on a clock measured seconds off stands out. A stopped or unsynchronized time service is called out, and the chart shows the measured offset over the last seven days.

Bounds

A warning and a critical bound -- 1 second and 5 seconds unless you change them -- are set for the whole server under Settings > Time Sync, and can be overridden for a tenant, a site or a tag: tighter for domain controllers and signing hosts, looser for lab machines. The most specific bounds apply: a tag's, then a site's, then the tenant's, then the server's. A host with several tags that have bounds is held to the tightest of them.

Resynchronizing a clock

Resynchronize now on a host's Clock card sets its clock at once through the time service it runs -- chronyc makestep; a restart of systemd-timesyncd; ntpdate or a restart of ntpd; rdate on OpenBSD; starting a stopped Windows Time service and w32tm /resync; sntp on macOS -- and reports the service's state afterwards. The host is pulled to the server's own verified reference, so it ends up on the clock it is judged against. Setting the clock needs an agent running with administrator rights; an agent without them says so instead of trying.

Resynchronize clocks out of bounds on the Time Sync page does the same for every host at warning or critical, sent in waves rather than all at once. It is not offered while the server's own clock is off. Every resynchronization is recorded in the audit log.

The fleet NTP policy

An NTP policy names the NTP servers hosts should use -- for the whole fleet, a site (an air-gapped site's internal pair) or a tag. A tag's policy wins over a site's and a site's over the fleet's; a host with two tag policies that name different servers is reported as a conflict and neither is applied. In report only mode, each host's configured servers, whether its time service is enabled at boot, and whether it is running are compared with the policy, and the differences are shown. Applied, SysManage also writes the configuration of whichever time service the host runs and enables it at boot, retrying with a growing delay when that fails.

The configuration written is minimal and marked as managed, and the previous file is kept as a backup. systemd-timesyncd gets a drop-in with no fallback servers, so a host on an isolated network never reaches out to a public one. OpenNTPD's HTTPS constraints are not written, because an air-gapped site can never satisfy them and OpenNTPD would then refuse to set the clock. macOS accepts a single network time server, so it gets the policy's first.

With automatic resynchronization switched on, a clock that reaches its warning or critical bound is resynchronized without anyone clicking, at most once an hour per host.

Alerts

Two alert conditions watch clocks: Clock Offset, raised when a host's measured offset reaches its warning or critical bound, and Time Sync Lost, raised when a host's time service stops or loses synchronization. Each host has one open alert while the problem lasts -- not a new one every cooldown. An alert that worsens from warning to critical is raised in place and notified again, and an alert is resolved automatically when the clock recovers, with a notification saying so. A clock must come back well inside its bounds (below 80% of the warning bound by default) before its alert clears, so a clock hovering at the bound does not flap. A host that cannot be measured raises nothing and clears nothing.

When many hosts at one site go out together -- five or more, and at least half of the site, by default -- one notification names them all: a failed NTP server at a site is one alert, not a thousand. Each host still has its own alert on its page, and the site's alert is resolved once, when its last host recovers.

Posture

The security posture punch list includes a check that every host's clock is within its bounds. A host that has not been measured keeps the check open rather than passing it.

Permissions

Changing bounds and the NTP policy needs the Manage Time Sync role; resynchronizing a clock needs Resync Host Clock. Anyone signed in can see clocks and bounds. On a server upgraded to this release, administrators receive both roles automatically.

Edition Requirements

Clock measurement, the server's own clock check, statuses, bounds, the Clock card, the dashboard tile and resynchronization are available in all editions, including the Community Edition. The fleet NTP policy, the clock alerts and the posture check are part of Enterprise.
