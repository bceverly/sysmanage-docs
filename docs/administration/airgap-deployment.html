Air-Gapped Deployment

Dual-server architecture for managing hosts on isolated networks that have no internet access. One server (Collector) lives on the public side, mirrors upstream package and CVE feeds, and burns the result to optical media. A second server (Repository) lives on the air-gapped side, ingests the media, serves it as a local mirror, and lets managed agents update normally without ever touching the internet.

Architecture

Two servers, both running the same SysManage binary. The role: key in sysmanage.yaml picks which half of the air-gap pair this server runs as. License is the same Enterprise SKU on both -- one license includes both engines.

  • Collector -- public-side. Loads airgap_collector_engine. Captures package mirrors (apt-mirror, dnf reposync, pkg fetch), CVE / NVD snapshots, and CIS / STIG compliance feeds. Bundles the result into one or more ISO images, signs the manifest with ed25519, optionally burns to physical media.
  • Repository -- private-side. Loads airgap_repository_engine. Ingests optical media, verifies the signature against the configured public key, verifies per-file SHA-256 hashes, copies the payload into a local mirror tree, and generates native repo metadata so each managed agent's package manager can consume it. Also rewrites each agent's APT / DNF / pkg config to point at the local mirror.
  • Standard -- the default. No air-gap; manages hosts directly online. This is what every deployment before v2.3.0.0 was, and what new deployments default to when role: is omitted from sysmanage.yaml.

The two halves never share a database. Collector and Repository communicate exclusively through the disc -- there is no network connection between them by design. The Repository records the manifest's signer_fingerprint + collector_iso_label so audit trails can correlate runs across the gap by inspecting both halves' databases after the fact.

Setting the server role

Set the role from the web UI -- no config-file editing required. Go to Settings → Server Role and pick one of three options, each shown with an explanation of what it means and how it's used:

  • Standard (no air gap) -- the default; manages hosts directly over the network. Leave every ordinary server here.
  • Air-Gap Collector (online side) -- the internet-connected half that mirrors upstream repos and builds the signed ISO media.
  • Air-Gap Repository (disconnected side) -- the isolated half that ingests the media and serves packages to hosts on the private network.

The choice is stored in the server's database (the server_configuration singleton), not in sysmanage.yaml. Earlier releases used a top-level role: key in the YAML; that key is now ignored, so you can remove it. Restart the SysManage server after changing the role for it to take full effect.

The role is also exposed via the unauthenticated GET /api/v1/server-info endpoint, which the web UI uses to render a chip in the header bar so operators can see at a glance which half of an air-gap pair they're looking at. The authenticated GET/PUT /api/v1/server-role endpoints back the Settings screen.

If the role is set to Collector or Repository but the corresponding Pro+ engine isn't loaded (typically a license problem), the chip turns red and a tooltip explains what's missing. The server keeps running in degraded mode so you can fix the license without losing access to the rest of the UI.

Collection cycle (Collector side)

Triggered by an operator (UI, API, or cron) on the public-side server. The bundle is built from snapshots of configured mirror_repository trees rather than running a second upstream fetch per run -- one download from upstream (via the repository_mirroring engine's normal sync) is reused for both the LAN mirror and the air-gap bundle. The engine emits a deployment plan that runs locally on the collector itself; it does not dispatch to managed agents.

A scheduled collection runs up to 30 minutes after its cron time, at a fixed point for each schedule, so repositories that share the default schedule do not all pull from the upstream mirrors at the same moment. The schedule's next run shows the actual time.

  1. Request -- POST /api/v1/airgap/collector/runs with a body listing each target as a {mirror_id} picked from /api/mirror-repositories, plus iso_label, media_size_bytes, include_cve, include_compliance, and optional burn_device. Distro / version / repos are derived server-side from each mirror's known_version catalog entry.
  2. Validation -- each picked mirror must exist, be enabled, have a known_version_id, and share a host_id with the other picks (the collection plan dispatches to one agent, so cross-host targets aren't supported in v1). Version strings are constrained to a tight regex so they cannot smuggle shell metacharacters into the dispatch templates; iso_label is constrained the same way.
  3. Auto-snapshot -- at run creation, one snapshot is dispatched per target mirror. Each AirgapCollectionTarget row pins its source_snapshot_id to the placeholder snapshot row so the orchestrator knows which snapshot to bundle once the agent reports completion. Snapshots run in parallel; the run sits at QUEUED until every target's last_snapshot_message_id clears.
  4. Mirror (snapshot-sourced) -- once all snapshots are ready, the orchestrator builds build_snapshot_collection_run_plan with a source_snapshots map of "<distro>:<version>" → snapshot directory path. The plan rsyncs each snapshot tree into per-target staging directories. No upstream apt-mirror / reposync / pkg fetch runs at collection time -- the bundle is provably byte-for-byte identical to the snapshot. Each rsync has a 4-hour timeout ceiling; the agent's in-flight journal covers the multi-hour run across WebSocket reconnects.
  5. CVE / compliance snapshot -- if requested, the collector exports its whole security catalog -- every CVE it holds with its package mappings, and every vendor advisory with its packages -- into one file on the media, named with its SHA-256 in the signed manifest, so the media set carries a coherent point-in-time view of public vulnerability data.
  6. ISO build -- xorriso -as mkisofs bundles the staging tree into one ISO at /var/lib/sysmanage/airgap-iso/<run_id>.iso with the manifest embedded at /manifest.json. The post-build step computes the ISO's SHA-256 for the transfer log.
  7. Sign -- the manifest is canonicalized (sorted keys, no whitespace) and signed with the operator's ed25519 private key. The envelope carries the signature, the SHA-256 of the public key as a fingerprint, the algorithm identifier, and the manifest format version.
  8. Burn (optional) -- if burn_device is set on the run row, the orchestrator advances ISO_BUILT → BURNING by dispatching build_burn_plan at that device path (typically /dev/sr0). The burn-step timeout ceiling is 4 hours so slow drives don't trip a watchdog mid-write. When burn_device is NULL the run goes ISO_BUILT → COMPLETE directly -- the "build a downloadable ISO and stop" flow that doesn't touch optical media.
  9. Download -- GET /api/v1/airgap/collector/runs/{id}/iso streams the ISO file. For multi-disc runs, GET /runs/{id}/discs lists the disc files and /iso?disc=N picks a specific one. The Air-Gap Collections UI auto-detects multi-disc runs and pops a picker dialog when the operator clicks Download.

Lifecycle states the airgap_run_tick orchestrator drives: QUEUED (waiting on per-target snapshots) → MIRRORING (rsync from snapshot trees into staging) → STAGING_COMPLETE (single-disc only; multi-disc skips this) → BUILDING_ISO (xorriso) → ISO_BUILT → BURNING (only when burn_device set) → COMPLETE. Any failure transitions the run to FAILED with the surfaced error message visible in the UI status column.

Multi-disc spanning. When sum(target.source_snapshot.size_bytes) > run.media_size_bytes the orchestrator routes to build_snapshot_multidisc_collection_plan, which first-fit-decreasing bin-packs whole target trees onto discs. Each disc gets its own staging dir + rsync + xorriso + sha256 in one inline plan; output is <run_id>-disc-<N>.iso. The orchestrator surfaces a clear error if any single target's tree exceeds the disc size -- file-level splitting (chopping one mirror tree across discs) is deferred; the operator picks larger media (BD-25 → BD-50) or splits into separate runs.

A run is split into discs only when it has a burn device: with the burn device left blank it builds one ISO of any size, since a file has no disc to fit. Every disc of a set carries the signed manifest, which says which disc of how many it is, and its volume label is the run's ISO label followed by -d<N>. The SysManage tools ride on disc 1.

Burning a set. One build_burn_plan burns one disc and ejects it, so a set is burned disc by disc: each <run_id>-disc-<N>.iso in turn, while a single disc burns <run_id>.iso. After each disc but the last, the run moves from BURNING to AWAITING_MEDIA, which the orchestrator never dispatches from. POST /api/v1/airgap/collector/runs/{run_id}/next-disc (the Next disc loaded action in the UI) puts the run back at ISO_BUILT and the next disc burns; it answers 409 when the run is not waiting for media. The run's disc_count and burned_disc_count show the progress. A failed burn sets FAILED with the disc number in the error message.

Ingestion cycle (Repository side)

Operator inserts the optical media into the air-gapped server, then triggers ingestion via the UI or API. The repository engine refuses to serve any byte until the signature and file hashes have verified.

  1. Mount -- the engine emits a deployment plan that mounts the ISO read-only at /mnt/sysmanage-airgap-ingest.
  2. Verify signature -- the manifest envelope is decoded; the engine refuses to ingest a manifest whose format_version is newer than its own software version (forward-compat fail-safe). The signature is verified against the keys in the repository's trusted-collector keyring, which the Trusted Collector Keys card under Settings → Server Role manages. Strict mode (the default) rejects the HMAC-SHA-256 fallback envelope that the collector produces only when cryptography isn't installed.
  3. What the signature covers -- the signed manifest proves the disc came from a collector you trust. The mirrored packages are not hashed again on import: each host's package manager checks them against the mirrors' own signed indexes, which are carried across unchanged. The SysManage tools on the disc are checked file by file against the SHA-256 hashes in the signed manifest (see The SysManage tools repository).
  4. Copy -- once verification passes, rsync copies the payload from the mount point to the local repository root: /var/lib/sysmanage/airgap-repo on Linux, /var/db/sysmanage/airgap-repo on FreeBSD and OpenBSD. A disc that belongs to a multi-disc set leaves alone the distribution trees it does not carry, so the discs of a set can be imported one after another.
  5. Build the tools repository -- the mirrors are served as they came, with their own signed indexes. From the SysManage tools on the disc, the server builds a separate repository for each distribution and release, signed with the site's own key.
  6. Unmount -- the ISO is unmounted; the operator can eject the disc.
  7. Repoint hosts -- SysManage points each host's package manager at the mirror for that host's own distribution and release, adds the tools repository beside it, and switches the upstream sources off, with signature checks left on: /etc/apt/sources.list.d/sysmanage-airgap.list on Debian and Ubuntu, /etc/yum.repos.d/sysmanage-airgap.repo on the RHEL family, /etc/zypp/repos.d/sysmanage-airgap.repo on openSUSE, /etc/apk/repositories on Alpine, and /usr/local/etc/pkg/repos/sysmanage-airgap.conf on FreeBSD. A host with no mirror for its own release is left as it is. Each host picks up a new ingest the next time it sends its reports, which it does when it connects and on its schedule.

When an import completes, the Import panel also shows what it found: a SysManage tools repository that could not be built and why, and whether the security catalog was loaded (with its counts), refused because it does not match the signed manifest, or could not be loaded.

Per-distro install channels

For new child hosts created on the air-gapped network, sysmanage-agent itself needs to install from a substitutable channel -- direct GitHub-release downloads can't be substituted with a private mirror. The per-distro agent_install_commands consume the published upstream channels instead:

  • Ubuntu / Debian -- Launchpad PPA (ppa:bceverly/sysmanage-agent). On the air-gapped side the agent package comes from the tools repository instead, which the repoint adds beside the local mirror.
  • Fedora / RHEL / Rocky / Alma / Oracle Linux / CentOS Stream -- Fedora Copr (bceverly/sysmanage-agent). Substitutable via /etc/yum.repos.d/sysmanage-airgap.repo.
  • openSUSE / SLES -- Open Build Service (home:bceverly/sysmanage-agent). Substitutable via the same yum/zypper repo file pattern.
  • FreeBSD / OpenBSD / NetBSD -- direct downloads. On the air-gapped side, FreeBSD's agent package is in the tools repository, which the repoint adds beside the local pkg mirror. OpenBSD and NetBSD have no mirror or tools repository, so their agents are installed by hand.

The SysManage tools repository

The mirrors carry the operating systems' own packages. The SysManage agent, restate and restate-proxy come from elsewhere, so every collection run also brings them across, and the repository server serves them as a repository of their own.

  • Collected with every run. For each distribution and release on the run, the collector names the exact sysmanage-agent, restate and restate-proxy packages with their SHA-256, as their publishers list them, and fetches them beside the mirrors, checking each against its hash. Their names and hashes go into the disc's signed manifest. A package that cannot be fetched never fails the run.
  • Systems covered: Ubuntu, Debian 12 and 13, Fedora, RHEL and its rebuilds, openSUSE, Alpine and FreeBSD. OpenBSD, NetBSD, macOS and Windows have no tools repository.
  • Built on the inside. After each import, the repository server checks every tools file against the signed manifest, keeps only what matches, and builds a repository for each distribution and release under /airgap-tools/: an apt repository with a signed InRelease, an RPM repository with a signed repomd.xml, an Alpine index and a FreeBSD pkg catalog. The mirrors are left exactly as they came.
  • Signed with the site's own keys. The repository server makes them the first time it needs them, and they never leave it: an OpenPGP key (RSA 3072) for apt and RPM, and an RSA 4096 key for Alpine and FreeBSD. Their public halves are published beside the repositories as sysmanage-tools.asc and sysmanage-tools.rsa.pub.
  • Trusted by the hosts. The repoint installs the site's key on each host and adds the tools repository beside the mirror, with signature checks on: apt by signed-by, dnf and zypper by repo_gpgcheck=1, Alpine with the key in /etc/apk/keys, and FreeBSD with signature_type: "pubkey". A host refuses the tools repository without that key.
  • Served over plain HTTP. nginx serves /airgap-repo/ and /airgap-tools/ on port 80, where hosts' package managers fetch them, and redirects everything else there to HTTPS. Both trees are signed, and every host checks the signatures.

To build and sign these repositories, the repository server needs gnupg, apt-utils, createrepo-c and zstd; the server's Ubuntu package recommends them.

The security catalog across the gap

An air-gapped repository server reaches no CVE or advisory feed, so the collector carries its own catalog across: security-catalog/security-catalog.jsonl.gz on the media holds every CVE with its package mappings and every vendor advisory -- Ubuntu, Debian, the RHEL family, Fedora, SUSE, Alpine, FreeBSD and OpenBSD -- with its packages and CVEs.

When an ingest completes, the repository server loads the file only if its SHA-256 is the one the signed manifest names; a file that does not match is refused and logged. CVEs are matched by CVE id, so host findings keep pointing at the same rows, and every approved host's applicable advisories are recomputed afterwards. A full catalog (about 150,000 CVEs and 47,000 advisories) loads in under a minute.

A repository server never refreshes CVEs or advisories online: the media is its only source, and the catalog is as current as the last media transfer. The Advisories and Vulnerabilities pages show when it last arrived.

Backups on an air-gapped site

Backups never cross the gap. The hosts on the air-gapped network, and the repository server itself, back up to a storage host on that network. The collector, on the internet-connected side, backs up to a separate storage host of its own. Each side is set up as Fleet Backups describes.

  • Equip from the site's own repositories. On a server whose role is Air-Gap Repository, Equip for backup tells each host's agent to install from the repositories the host already uses, which the repoint has pointed at the mirror and the tools repository. The agent installs restate by name with the system's own package tool, and never adds a PPA or a COPR, downloads from GitHub, or uses Homebrew. The server still sends no package name or command.
  • The NFS client. Equip also installs the NFS client when the host's repositories have it, which they do when the site mirrors the host's distribution. A host whose repositories do not have it is still equipped: a target that uses restate-proxy never mounts NFS. For an NFS target, mirror the distribution of every host that backs up to it, so the NFS client can be installed.
  • restate-proxy too. On the storage host of a target that uses restate-proxy, the same Equip also installs restate-proxy, with apt, dnf or FreeBSD's pkg. Choose an Ubuntu, Debian, Fedora, RHEL-family or FreeBSD storage host for such a target.
  • Repoint first. Equip installs from the repositories the host already has, so it finds restate only once the host has been repointed at the mirror and the tools repository for its release, which happens with its next reports after an import.
  • When there is no package. A system the tools repository does not cover, such as macOS, answers This air-gapped site has no restate package for this system in its own repository. Install restate on it by hand.
  • Once, on the storage host: the storage path and the backup account. As on any site, you create the storage path and the backup account (restate by default) yourself; Fleet Backup Storage has the commands. SysManage sets up restate-proxy to run as that account only once it exists; if it does not, the storage host reports it and nothing is started. After you create it, restart the storage host's agent (or use Request Host Data): its storage check finds the proxy down and the storage host is sent its setup again.
  • Nothing reaches out. The restate-proxy certificate is signed by SysManage's own certificate authority, captures, checks and restores go host to storage host, and restore readiness (recovery point and restore time) is worked out from the server's own records. A backup, a full-read verification and a restore have been run on an isolated network with nothing leaving it.
  • The repository server's own agent. The repository server reads the import media through its own SysManage agent, so install the agent there too, from the agent package for the server's release brought on the server media: sudo dpkg -i sysmanage-agent_<version>.deb (or sudo rpm -i). The package carries its Python environment and needs only the system's Python, so it installs with no network. Then approve the host on the Hosts page.
  • Upgrading SysManage on the site. The agent packages carry everything they need: an upgrade keeps the agent's packaged Python environment, and an install that cannot finish leaves the running agent in place. The server package installs its Python dependencies from wheels, so bring them on the server media and install with sudo PIP_NO_INDEX=1 PIP_FIND_LINKS=<the media's wheels folder> dpkg -i sysmanage_<version>.deb, then sudo sysmanage-migrate. A server install that cannot get its dependencies keeps the previous environment.
  • Recovering the server from media. The server recovery runbook works on an air-gapped site, with the server, agent and Pro+ bundle media in place of package repositories. See Recovering the server from its own backup.
  • No iCloud Photos backup. It needs the internet, so an air-gapped server does not offer it.

Compliance context across the gap

The repository's freshness state is part of compliance reports so operators can distinguish two failure modes that look identical without context:

  • not_applied -- a newer version is on the local mirror but hasn't been installed on this host yet. Fix locally; cheap.
  • not_transferred -- the public CVE feed (captured by the collector at last media transfer) lists a fix that isn't on the local mirror at all. Fix requires a new collection / burn / ingest cycle; expensive.
  • current -- the host's installed version matches the mirror's latest, and no public-side CVE has surfaced since last transfer.

Each repository tracks days since last ingest. Compliance UI surfaces a freshness label: current (≤ 7 days), stale (8-30 days), very_stale (> 30 days), or never. Use this to size the air-gap transfer cadence against your organization's tolerance for delayed patch availability.

Troubleshooting

Ingestion fails with "signature does not match manifest payload"

No key in the repository's trusted-collector keyring matches the private key that signed this disc. Either the disc was tampered with in transit, or the operator regenerated the keypair on the collector without distributing the new public key to the repository. Copy the public key from the collector and import it in the repository's Trusted Collector Keys card.

Ingestion fails with "manifest format_version exceeds repository's max"

The collector has been upgraded to a new SysManage version that changed the manifest format, but the repository hasn't been upgraded yet. Upgrade the repository server to the same version, then re-ingest. The format-version check is a deliberate forward-compat fail-safe -- older repositories cannot be tricked into ingesting media with new fields they don't understand.

Role chip in the header bar is red

The server role is set to collector or repository, but the corresponding Pro+ engine isn't loaded. Most common cause: the Enterprise license isn't valid (expired, missing, or doesn't include the air-gap engines). Check the License page in Settings; if the license is fine, check /var/log/sysmanage/server.log for module-loader errors.

Multi-hour collection cycle gets killed mid-run

Should not happen: the agent writes a per-plan in-flight journal at ~/.sysmanage-agent/inflight/<message_id>.json before each subprocess starts, with a 30-second heartbeat. If the agent process restarts (or the WebSocket bounces), the journal carries enough state for the agent to either re-attach to the still-live subprocess or emit a synthetic command_result so the server's mirror row clears. If you see a hung mirror anyway, file an issue with the contents of the inflight journal.
