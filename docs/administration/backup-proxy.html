Backups over HTTPS with restate-proxy

A backup target can let its hosts reach the storage host in one of two ways: each host mounts its own NFS export, as Setting up the storage host describes, or each host talks HTTPS to restate-proxy, a service that runs on the storage host. This page covers the proxy: why to choose it, what SysManage sets up for it, and how hosts outside your network reach it through a firewall.

Why use the proxy

  • No mount. A host on the proxy mounts nothing and needs no NFS client. restate on the host reaches its repository at https://<proxy>/v1/<host id> by running curl.
  • Append-only by protocol. The proxy has no way to delete, rename or overwrite anything. Every upload is checked against restate's repository format before it goes in, and a host reaches only its own repository: the host id in the address must match the host's token. Prune, check, seal and protect still run only on the storage host.
  • Tokens the hosts make themselves. Each host makes its own token and keeps it in a file only root can read. Only the token's SHA-256 hash goes to the SysManage server and to the storage host, so no token is ever in a command, the message queue or a database.
  • Works from anywhere. Everything travels inside TLS, and hosts are known by their token, never by their address, so a host behind NAT or outside your network, such as a SysManage server in the cloud, can back up to the same storage host as the LAN.
  • Nothing else changes. Backups, restores, browsing a snapshot and comparing snapshots all go through the proxy. The repositories on the storage host are the same directories either way, and the storage host still protects, seals, prunes and checks them. With Professional+ encryption, the proxy and the storage host only ever see encrypted packs.

Backup data goes straight from each host to the storage host. It never passes through the SysManage server, which only sends the settings and collects the results.

Choosing NFS or the proxy for a target

On the Backups page, the target card shows How hosts reach the storage. Click Change how hosts reach storage and pick Reach the storage through:

  • NFS (each host mounts its own export) -- the storage host exports each host's repository to that host, and the agent mounts it while a job runs.
  • restate-proxy (HTTPS to the storage host) -- then give the Proxy address hosts reach, the name or address in the proxy's certificate as the hosts resolve it, and the Port (8443 by default).
  • Pinned key (SHA-256, optional) -- the SHA-256 of the proxy certificate's public key, as 64 hexadecimal characters. Hosts then accept only a proxy certificate with this public key.
  • Site CA certificate (PEM, optional) -- only for a proxy certificate your own certificate authority signed. Hosts trust it for their backups only. Once one is saved, leaving the field empty keeps it; Remove the saved CA and trust the system store takes it away.

Changing it needs the Manage Backups permission and is audited. SysManage then sends new job files to every host of the target and to the storage host. You can switch either way at any time: the repositories stay where they are on the storage host and keep their snapshots, because only the way in changes.

Each host moves to the proxy as far as its restate allows. With restate 3.1.0.0 or later, restores, browsing, status, comparisons and checks go through the proxy; with 3.2.0.0 or later, backups and snapshot listings do too, and the host mounts nothing at all. Until then, those jobs keep using NFS. A host that backs up through the proxy has no NFS export, so the storage host makes none for it, and the storage check leaves the export checks out for it. OpenBSD and NetBSD hosts, and Linux hosts without an NFS client, can back up only through the proxy.

What Equip installs on the storage host

On a target that uses the proxy, Equip for backup on the storage host installs restate-proxy beside restate, and upgrades it later, even when restate is already there: from restate's PPA on Ubuntu, its COPR on Fedora, and restate's release package on Debian 12 and 13 and FreeBSD, installed only when its checksum matches the release's list. On other systems Equip installs restate without the proxy, so choose one of these for the storage host. The server sends only that the proxy is wanted, never a package name or a command. When the storage host has no proxy, the target card warns restate-proxy is not installed on the storage host, so hosts cannot reach their backups through it. with an Install restate-proxy button.

The proxy package installs its service turned off. SysManage's storage setup then runs it as the target's backup account, which owns the repositories (on Linux with a systemd drop-in that sets User and Group to that account and UMask=0007; on FreeBSD with sysrc restate_proxy_user=restate restate_proxy_umask=007), and turns it on and starts it once it has its certificate. When the target goes back to NFS, the agent stops and turns off the service it started, and nothing else.

The proxy's certificate

The storage host makes the proxy's private key, which never leaves it, and asks the SysManage server for a certificate. The server's own certificate authority, the SysManage CA, signs it for the proxy address in the target only, for 365 days. The next storage setup installs the key and the certificate together, at /etc/restate/proxy.key (readable only by the backup account) and /etc/restate/proxy.crt, and restarts the proxy. The certificate is renewed 30 days before it ends, and again whenever the proxy address changes.

Hosts trust it through the SysManage CA, which SysManage gives them as the target's CA. The target card shows Certificate from the SysManage CA, valid until a date, or Waiting for the storage host to ask for its certificate. When you give a site CA of your own, it wins: the server issues nothing, and the card shows no certificate line. The certificate that CA signed, and its key, are then yours to put on the storage host, at the same two paths.

The allow list: one grant per host

The proxy lets in only clients it has a grant for: one file per client in /etc/restate/proxy.d. The storage host's agent writes one for each host of the target, /etc/restate/proxy.d/<host id>.conf, naming that host's repository, what the host may do (add backups, and read its own repository to restore) and the SHA-256 hash of the host's token. A host whose repository was encrypted with Professional+ after it had backups also gets a read-only grant for the repository from before, <host id>.previous.conf.

The agent marks every grant it writes with a label for the target, and only ever changes or removes those: a grant you write yourself is left alone. When a host leaves the target, or is deleted, its grant is removed, and the same token is refused on its next request. The proxy reads the directory again by itself when it changes, so nothing is restarted.

A token older than 90 days is replaced. The host makes the next one and reports only its hash; the storage host adds that hash to the grant beside the current one, and the host starts using the new token only once the server tells it the new hash is granted. The old hash is removed after that, so no backup fails in between.

Through the proxy, a host cannot make its own repository. Click Prepare storage on each host's Backups card before its first backup: the storage host then makes the repository itself, with the policy's public key when the repository is encrypted. Until it does, the target card lists the host under No repository on the storage host yet.

Restores, and a busy repository

A restore through the proxy needs the Restore Files permission and is audited, exactly as over NFS. The host reads its own repository with its own token, and the proxy holds the repository's read lock for as long as the restore runs, so a prune on the storage host cannot remove anything the restore is reading.

When a backup and a prune on the storage host want the same repository at the same time, one of them finds it locked, and the proxy answers that the repository is busy. A backup that does shows Busy, will retry and is due again 30 minutes later; it is not a failure. A prune that finds a backup or a restore running removes nothing, and is tried again the same way.

What the storage check says about the proxy

The storage check on the target card also covers the proxy, after every storage job and once a day:

  • restate-proxy is not installed on the storage host -- click Install restate-proxy on the warning.
  • restate-proxy is not running on the storage host -- start its service there.
  • The certificate is missing from /etc/restate/proxy.crt, cannot be read, has expired (hosts then refuse the proxy), or expires within 21 days.
  • restate-proxy does not accept the grant for the hosts named -- run restate-proxy --check-grants on the storage host to see why.
  • No repository on the storage host yet for the hosts named -- click Prepare storage on each one's Backups card.

Each host is also asked whether it can reach the proxy and complete a TLS connection with a certificate it trusts (and the pinned key, when there is one), at the same times as the NFS check: before Equip for backup, when its policy is saved, once a day, and when you click Check again. A host that cannot shows This host cannot reach the backup storage's restate-proxy, with the address, the port and the error, and its backups are held until it can. It needs a network path to the proxy and must trust its certificate.

Hosts outside your network, through a firewall

A host outside the storage host's network reaches the proxy through the firewall at the network's edge. The firewall passes the TLS connection through as it is, so TLS ends on the storage host: the firewall never holds the proxy's certificate or sees a token, and nothing crosses your LAN unencrypted. Use one name for the proxy everywhere, with split-horizon DNS:

  • Outside, the name resolves to the firewall's public address.
  • Inside, a DNS host override resolves the same name to the storage host itself, so LAN hosts reach the proxy directly and their nightly backups do not loop through the firewall.

Every host then uses the same address, port and certificate, so the target needs no setting of its own for remote hosts.

Example: pfSense with HAProxy in TCP mode

pfSense's HAProxy package, in TCP mode, reads the name the client asks for in the TLS handshake (SNI) and sends the connection to the backend for that name without decrypting it. These settings send backup.example.com on port 8443 of the WAN address to port 8443 of a storage host at 192.168.1.10:

  1. Backend (Services > HAProxy > Backend): a server with address 192.168.1.10, port 8443, Encrypt(SSL) and SSL checks off; server timeout 120000; health check method Basic, with the check frequency left empty; Transparent ClientIP off.
  2. Frontend (Services > HAProxy > Frontend): listen on the WAN address, port 8443, with SSL Offloading off; type ssl / https(TCP mode); an access control list matching the Server Name Indication TLS extension against backup.example.com, with the action Use Backend for it; no default backend; client timeout 120000.
  3. Firewall rule (Firewall > Rules > WAN): pass TCP to the WAN address, port 8443. No port forward is needed, because HAProxy listens on the WAN address itself. Where the remote hosts' addresses are known, limit the rule's source to them as an extra layer.
  4. DNS: backup.example.com resolves to the WAN address outside, and a host override in pfSense's DNS Resolver (Services > DNS Resolver > Host Overrides) resolves it to 192.168.1.10 inside.

Keep TCP mode with SSL Offloading off: offloading would put the proxy's certificate and key on the firewall and decrypt every backup there. HAProxy can match the name only once the handshake has arrived, so the frontend needs tcp-request inspect-delay 5s and tcp-request content accept if { req_ssl_hello_type 1 }; if the configuration pfSense writes (/var/etc/haproxy/haproxy.cfg) has neither, add them in the frontend's Advanced pass thru. Keep both timeouts at 120 seconds, longer than the proxy's own 60, because HAProxy's default of 30 seconds can cut off a large backup while it is committed. Do not turn on send-proxy: restate-proxy does not take the PROXY protocol.

Then set the target's Proxy address hosts reach to backup.example.com and its Port to 8443. The proxy's certificate from the SysManage CA is issued for that name. A remote host that passes the reach check is offered backups like any other.

What you need

  • restate-proxy on the storage host, which Equip for backup installs, and restate 3.2.0.0 or later on each host to back up through the proxy. The agent asks restate what it can do (restate features), so a host with an older restate keeps using NFS for what it cannot do through the proxy.
  • curl on each host, which restate runs to reach the proxy. restate's Debian and RPM packages recommend it; Equip does not install it.
  • The proxy's port, 8443 by default, open from the hosts to the storage host.

Edition requirements

The proxy as a transport is part of the Community edition: the setting on the target, Equip, the grants and tokens, the job files, restores, the storage check and the target's Backups at the same time. restate-proxy itself is part of restate and free to run by hand. Bandwidth limits by the hour of the day, set with Change bandwidth limits on the target card (Bandwidth through restate-proxy), need Professional+ and restate 3.2.1.4 or later on the storage host. Without the license the rules are kept but not applied, and backups through the proxy run at full speed.
