Hardware Health

A disk rarely fails without warning: media errors climb, a RAID array loses a member, a storage pool degrades. SysManage has each host's own agent judge its drives, RAID arrays, storage pools, temperature sensors and memory from the operating system's own sources, and shows the whole fleet worst first -- without installing anything extra on most hosts.

What is watched

The agent reads the operating system's own sources first, so most hosts need no extra package:

  • Linux The SMART health log of NVMe drives, read through the kernel (the agent must run as root); hwmon temperature sensors; md software RAID from /proc/mdstat; btrfs device error counters; LVM RAID volumes; ZFS pools; EDAC memory error counts; and machine-check errors recorded by rasdaemon.
  • FreeBSD NVMe drives through nvmecontrol; ZFS pools through zpool; GEOM mirror and RAID volumes; and ACPI thermal zones and CPU temperatures.
  • OpenBSD The kernel's hw.sensors: drives, RAID volumes and temperature sensors, each with the kernel's own verdict. Each RAID volume and its disks are read from bioctl as well.
  • NetBSD Sensors from envstat, judged against the limits each one declares; RAIDframe sets from raidctl; RAID volumes from bioctl; and ZFS pools.
  • macOS Each disk's SMART verdict from diskutil, and the system's thermal state.
  • Windows The storage cmdlets: physical disks with their reliability counters, Storage Spaces virtual disks, ACPI thermal zones, and the hardware errors WHEA has recorded.

SATA and SAS drives on Linux and FreeBSD can only be read with smartctl, from smartmontools. Without it such a drive is shown as not judged, with the reason, and SysManage recommends installing it. Virtual disks (virtio, Xen) have no SMART at all and are not listed: their health is the hypervisor's.

Where a hardware RAID controller's own tool is installed -- storcli or perccli (Broadcom, Dell), ssacli (HPE) or arcconf (Microchip) -- its logical and physical drives, the controller and its cache battery are read too. On a server with a BMC, ipmitool adds the BMC's sensors and the hardware problems in its event log over the last 24 hours.

What each status means

  • Healthy Every component the host reported is healthy.
  • Warning At least one component needs attention -- media errors, a degraded array, a temperature at its limit.
  • Failed At least one component has failed.
  • Not judged The host reported its hardware, but nothing could judge at least one component.
  • Not reported The host has never reported its hardware -- its agent is too old, or it has not connected.
  • No recent report The last report is more than an hour old; the host is probably not connected.

A host or a component that was not measured is never shown as healthy. Each report also lists its sources -- whether each one was read, is not present on the host, or failed -- so an empty report reads as not measured, not as nothing wrong. Temperatures are judged only against the limits the hardware itself declares; a sensor that declares none is shown, never guessed at.

Problems reported as they happen

Where the operating system announces a hardware problem, the agent listens: the kernel log on Linux, devd on FreeBSD, and the System event log on Windows (checked every 30 seconds). A disk failure, an array losing a member or a pool degrading is reported at once -- the hardware is read again and sent with the operating system's own lines as evidence, shown as an Operating system event -- rather than on the next periodic report. Listening needs an agent running with administrator rights.

On Linux the agent also follows what smartd, zed and mdadm write to the system journal, so a drive failing its SMART check, a ZFS device faulting or an md array losing a disk is caught the moment it is logged.

Otherwise the agent reports on its own schedule: a report that has not changed is not sent again, but one is sent at least every 15 minutes. macOS, OpenBSD and NetBSD use the periodic report only.

The Hardware Health page

Hardware Health, in the Fleet menu, shows how many hosts are in each status and lists every host worst first, with its most serious problems. Filter by status, site, tag or host name. Below the list are the unresolved events: every change in a component's state, and every problem the operating system reported. The dashboard has a tile counting the hosts whose hardware needs attention.

A host's hardware

The Hardware health card on a host's overview lists its components worst first, with the reason for each one that is not healthy and the values it was judged on. Healthy sensors are folded away so they do not bury the rest. The card also shows which sources were read and the host's recent events.

Temperature warnings

A temperature sensor warns when it reaches the limit its hardware declares, and fails at the hardware's critical limit. Once a sensor is at warning it stays there until it has cooled 5 C below its limit, so a host that idles at its limit raises one event instead of one at every report.

A host's own temperature limit

Some hosts run hot by design: an old laptop serving with its lid closed sits at its CPU's limit all day. On the host's Hardware health card, set the Temperature warning limit to the temperature at which you want to hear about it. Every temperature sensor on that host is then judged against your limit instead of the one its hardware declares, and shows warns at N C (host limit). The hardware's critical limit still applies: at or above it a sensor fails, whatever the host limit is. Use device limits removes the host limit.

One exception: a sensor whose own critical point is at or below the host limit, such as a drive that is critical at 85 C under a 95 C limit, keeps the warning mark its hardware declares, so it always warns before it fails.

The limit can be from 30 to 125 C. It applies from the host's next report; earlier events are not changed. Setting or clearing it needs the Manage Hardware Health role, and anyone without it sees the setting read-only. Every change is recorded in the audit log. It is available in all editions.

Through the API: PUT /api/v1/host/{id}/hardware-health/temperature-limit with {"limit_c": 95}, or {"limit_c": null} to return to the hardware's own limits.

Acknowledging and resolving events

An event can be acknowledged -- someone has it in hand -- or resolved, each with an optional note, from the Hardware Health page or the host's card. Both need the Manage Hardware Health role.

Installing smartmontools

Where a drive cannot be read without smartctl, the host's card and the Hardware Health page say so, and offer to install smartmontools on that host or on every host listed. Installing needs both the Manage Hardware Health and Add Package roles. On Debian and Ubuntu it is installed without its recommended packages, so no mail server comes with it. The drives are read at the host's next report.

On Enterprise, an administrator can let SysManage install smartmontools automatically wherever it is needed. It is off until someone switches it on, and is set per tenant under multi-tenancy. An install that fails is retried with a growing delay. Every install, and every change to the setting, is recorded in the audit log.

Alerts

The Hardware Health alert condition is raised when a host has a component at warning or worse -- or, if you choose, only when something has failed -- optionally for some kinds of component only (drives, arrays, pools, sensors or memory). Each host has one open alert while the problem lasts; it is critical when something has failed, and it is resolved automatically, with a notification saying so, when everything is healthy again. A host that is not reporting raises nothing and clears nothing.

The condition is evaluated the moment a report arrives, not on the next minute's check. An alert is notified again every 4 hours until someone acknowledges it. While a host is in a maintenance window its notifications are held, but the alert is still recorded. When many hosts at one site trip together, one notification names them all.

Measured on lab hardware: when a disk of a ZFS mirror went offline, the alert was raised and its email sent 11 seconds later; the alert itself was raised within 0.2 seconds of the report reaching the server.

Permissions

Anyone signed in can see hardware health. Acknowledging and resolving events needs the Manage Hardware Health role; installing smartmontools also needs Add Package; switching automatic installation on or off needs an administrator. On a server upgraded to this release, administrators receive Manage Hardware Health automatically.

Edition Requirements

Hardware collection, the statuses, real-time reporting, the Hardware Health page, the host card, the dashboard tile, acknowledging events and installing smartmontools by hand are available in all editions, including the Community Edition. Automatic smartmontools installation and the hardware alerts are part of Enterprise.
