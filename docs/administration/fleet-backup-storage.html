Setting Up the Backup Storage Host

The storage host serves every backed-up host's repository over NFSv4 and runs the jobs that lock, seal, prune and check the backups. It must be a managed host with the SysManage agent and restate 2.1.0.3 or later. You set up its storage and NFS server once, as this page describes; SysManage checks that setup and does everything per host itself.

What you do, and what SysManage does

  • You, once: the storage itself (a ZFS dataset or btrfs subvolume at the storage path), the backup account, and the NFS server's settings. SysManage never changes these. The storage check on the target card tells you when one is wrong, and what to change.
  • SysManage, per host: Prepare storage gives each host its own filesystem and an export to that host only; the agent mounts it on the host only while a job runs; and after every backup the storage host locks what was written.

1. A FreeBSD storage host with ZFS

Create the dataset the repositories live under -- each host's repository becomes a child dataset of it -- and the backup account. Root on a backed-up host must never be root on the storage host: every file a host writes belongs to this account.

zfs create -o mountpoint=/srv/backups zroot/sysmanage-backups
zfs create zroot/sysmanage-backups/restate
pw groupadd restate
pw useradd restate -g restate -d /nonexistent -s /usr/sbin/nologin -c "restate backup writer"

In /etc/exports, make /srv/backups the NFSv4 root, and add no other line: each host's own export is made by Prepare storage, through ZFS (sharenfs, which ZFS writes to /etc/zfs/exports).

V4: /srv/backups -sec=sys

In /etc/rc.conf:

rpcbind_enable="YES"
nfs_server_enable="YES"
nfsv4_server_enable="YES"
mountd_enable="YES"

In /etc/sysctl.conf:

vfs.nfsd.enable_locallocks=1
vfs.nfsd.server_min_nfsvers=4
vfs.nfsd.enable_stringtouid=1
vfs.nfs.enable_uidtostring=1

vfs.nfsd.enable_locallocks=1 is required: it makes a lock taken by a job on the storage host and a lock taken by a host over NFS see each other, so a backup and a prune never run on one repository at the same time. Then start the services, or reboot:

service rpcbind start
service mountd start
service nfsd start

2. A Linux storage host

Put the storage path on a ZFS dataset or a btrfs subvolume, so each host's repository can be its own filesystem. On ext4 or XFS backups work, but every host shares one filesystem and nothing can be sealed. Create the backup account, install the NFS server (nfs-kernel-server on Debian and Ubuntu), and serve NFSv4 only, in /etc/nfs.conf:

useradd --system --user-group --shell /usr/sbin/nologin restate

[nfsd]
vers3=n

Do not export the storage path yourself. Prepare storage writes each host's export to its own file in /etc/exports.d and reloads them with exportfs -ra.

3. The target in SysManage

On the Backups page, set up the target with this storage host, Path on the storage host /srv/backups/restate, Mount point on each host /mnt/backups, Backup account on the storage host restate, and Seal each backup as a ZFS snapshot of zroot/sysmanage-backups/restate. The seal snapshots that dataset and every host's dataset under it. See Fleet Backups for the rest.

4. Prepare storage for each host

On each host's Backups card, click Prepare storage. The storage host's agent then, for that host only:

  • On ZFS, creates the host's repository as a child dataset of the one at the storage path. On FreeBSD its export is the dataset's sharenfs; on Linux it is a file in /etc/exports.d. Either way it serves that host's address only, and maps every client to the backup account. On Linux the agent creates and mounts the dataset in the storage host's own mount namespace, not its service's private one, and checks that it is mounted where the export serves it before exporting it or setting its permissions.
  • On btrfs, creates a subvolume and its export file; on ext4 or XFS, a directory and its export file. A FreeBSD storage host needs ZFS: FreeBSD exports whole filesystems, so a repository without its own dataset cannot have its own export.
  • Makes the repository directory owned by root and the backup account's group, writable by that group but append-only. On Linux that is mode 0770 with the append-only flag (chattr +a), and the protect step makes each finished pack and snapshot immutable; on FreeBSD it is mode 0770 with an NFSv4 ACL that says the same. It is never the sticky bit: a Linux backed-up host with fs.protected_regular=2, the Ubuntu and systemd default, refuses to open a file it has just made in a sticky directory that its group can write.

It never moves backups: a repository that already holds files on the shared filesystem is refused, with the steps to move it. Run it again whenever you like; it exports to the host's current address and resets the directory. When a prepared host's address changes, SysManage runs it again by itself.

5. Mounts on the hosts

Nothing goes in a host's /etc/fstab. The storage host tells SysManage where each repository is exported, and the host's agent mounts it at <mount point>/<repository> -- NFSv4 over TCP, with hard,nosuid,nodev -- only when a backup, estimate, snapshot listing or restore starts, and unmounts it when the last one ends. Between jobs the host cannot reach its backups at all. A job that cannot mount is refused with the reason, so restate never writes to the host's own disk. Before a backup writes anything, the agent also checks that it can open the repository, that locking works on it, and that at least 1 GB and 1% of the space is free; if not, the backup is refused and Recent jobs says why.

Each host needs the NFS client. Equip for backup installs it: nfs-common on Debian and Ubuntu, nfs-utils on Fedora, RHEL and Alpine, nfs-client on openSUSE. A host without it shows Install the NFS client, and a backup on it is refused with that reason instead of failing to mount. If you already mount the share yourself, with fstab or autofs, the agent uses that mount and leaves it alone.

6. Locking finished backups

After each good backup, before the seal, the storage host runs restate protect: every finished pack and snapshot becomes root's and read-only, so a host can add backups but change or remove none. This needs restate 2.1.0.1 or later, and 2.1.0.3 or later on FreeBSD with ZFS. Tested from a backed-up host as root: deleting, renaming, overwriting or changing the mode of a finished pack or snapshot is refused, and new backups still work.

Right after a backup, the host's NFS client can still hold its newest files for a minute or two, and the storage host cannot lock a file until it lets go. restate 2.2.0.14 and later wait for those files, for up to about three minutes. If any are still unlocked, the job ends Incomplete, and SysManage runs protect again five minutes later, up to three times in a row.

The seal after each backup is a ZFS or read-only btrfs snapshot. The storage host keeps its seals for the target's Keep sealed snapshots for (days) and removes older ones itself, always keeping the newest; it removes only the seals it made (ZFS snapshots named sysmanage- followed by a job id, and btrfs seals it recorded making).

When the storage host's restate is upgraded, SysManage sends it new job files and runs protect once by itself, so a repository locked by an older version is brought to the new form before the next backup.

7. The storage check

The storage host's agent checks this setup whenever it is configured and after every job it runs, reading files and settings only. The target card shows each problem, the hosts it affects, and what to change. An error means backups are not protected or will not work; a warning means they work, with a weakness.

  • NFS server not running (error) -- enable and start it: on FreeBSD nfs_server_enable="YES", on Linux the nfs-server service.
  • No NFSv4 (error) -- on FreeBSD, nfsv4_server_enable="YES".
  • Older NFS versions served (warning) -- on FreeBSD vfs.nfsd.server_min_nfsvers=4, on Linux vers3=n.
  • Locks not shared (error) -- on FreeBSD, vfs.nfsd.enable_locallocks=1. Without it a prune could run during a backup.
  • No V4 root (error) -- on FreeBSD, the V4: line in /etc/exports.
  • Backup account missing (error) -- create the user and group named in the target.
  • Not on its own filesystem (warning) -- click Prepare storage for the host. On ext4 or XFS this warning stays.
  • Reachable through a shared export (error) -- an export of the storage path reaches the host's repository, so a host that is broken into could reach other hosts' backups. Once every host is prepared, remove that export.
  • Without an export of its own (warning) -- click Prepare storage for the host.
  • Export not limited to the host (warning) and clients not mapped to the backup account -- click Prepare storage for the host again.
  • Not append-only (warning) -- finished backups or directories a host could still change. The next backup's protect fixes it (restate 2.1.0.1 or later).

When the storage host's agent does not run as root, add its user to the backup account's group, so the check can read the repository directories.

8. Moving an existing repository onto its own filesystem

A repository made before Prepare storage sits on the shared filesystem, and Prepare storage refuses to touch it. To move one, turn the host's schedule off so no job runs, then:

  1. On the storage host, move the repository aside: mv /srv/backups/restate/HOST /srv/backups/restate/HOST.old
  2. Click Prepare storage for the host.
  3. Copy the backups in as root, keeping owners and modes: cp -Rp /srv/backups/restate/HOST.old/ /srv/backups/restate/HOST/
  4. Click Prepare storage again, turn the schedule back on, and back the host up.
  5. Once a check of the repository passes, remove HOST.old. When every host is prepared, remove the shared export from /etc/exports, keeping the V4: line.

In testing, an 18 GB repository moved this way, and the next backup reused every pack it held.

A FreeBSD storage host

FreeBSD has no systemd, so on a FreeBSD storage host the agent starts restate's storage jobs itself, under daemon(8), so they keep running if the agent restarts. restate is found in /usr/local/sbin. A FreeBSD host can only be a storage host; choosing one as a backed-up host is refused.

When the agent does not run as root, its sudoers file allows exactly restate run of a prune, check, copy, du, repack or protect job file in /etc/restate/jobs.d, and exactly the zfs create, zfs set sharenfs and setfacl commands Prepare storage runs -- each through a regular expression rather than a wildcard, so no other option can be added. It needs sudo 1.9.10 or later.

Other storage

The storage host must be a managed host running the agent, because it does everything that could remove a backup. A NAS appliance that cannot run the agent is not supported as a target yet.
