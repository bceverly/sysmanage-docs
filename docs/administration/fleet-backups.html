Fleet Backups

SysManage backs up your hosts with restate, a backup tool that records what a fresh install of the operating system would not put back: your files, and on Debian and Ubuntu the packages too. Every host writes to its own repository on one storage host, which does everything that could remove a backup and locks every finished one. A host that is broken into cannot delete its own history.

This page is about backing up your managed hosts. To back up the SysManage server itself, see Backup & Recovery.

How it works

  • One target. The backup target is one storage host serving NFSv4. Every backed-up host reaches its repository under the same mount point, for example /mnt/backups.
  • One repository per host. Each host writes only to its own repository, named after the host and the start of its host id, such as web01.example.lan-1f3a9c2e. The id keeps two hosts with the same name apart, and keeps a renamed host's history. Prepare storage gives each repository its own filesystem and an export to that host only.
  • Hosts only add. A host's backup job can create new snapshots and nothing else; it never prunes. After each backup the storage host makes what was written root's and read-only, so even root on the host cannot change or delete a finished backup.
  • Mounted only while a job runs. The agent mounts the host's repository when a backup or restore starts and unmounts it when it ends, so between jobs the host cannot reach its backups at all. Nothing is added to /etc/fstab.
  • The storage host does the rest. After each good backup, the storage host's own agent protects it (makes it read-only), seals it with a read-only filesystem snapshot (ZFS or btrfs), then prunes old snapshots down to the number you keep, and on its own schedule checks the repository. A seal always comes before a prune, and a failed seal holds the prune back.
  • Sizes come from the storage host. After each prune the storage host measures the repository with restate du, which reads no backed-up data, so the size shown is what the repository really takes there, and each snapshot records what removing it alone would free. A prune that is stopped partway, for example because the storage host shuts down, stops cleanly and reports Incomplete (restate 2.0.0.5 or later); the next prune finishes it.

Why it is built this way: ransomware that takes a host also takes everything that host can reach. If the host could delete its backups, the attacker could too. Here the host can only add, and the sealed snapshots live on a machine the host cannot log in to.

The agent never builds a restate command line from what the server sends. It checks the server's settings against a fixed list, writes them as a root-owned job file in /etc/restate/jobs.d, and starts restate's own job unit. restate refuses a job file that anyone but root can change.

What you need

  • restate 2.0 or later on every host you back up and on the storage host. On Ubuntu: sudo add-apt-repository ppa:bceverly/restate and sudo apt install restate. Elsewhere, build it from source as its README describes (gmake build and sudo gmake install on FreeBSD).
  • restate 2.1.0.3 or later is recommended. The agent asks restate what it can do (restate features) and uses newer abilities only when they are there: create lets a host's first backup make its own repository, plan works out a restore preview from the snapshot index in seconds, protect (2.1.0.1, and 2.1.0.3 on FreeBSD with ZFS) locks finished backups on the storage host, and 2.1 reports which services it can pause on each host. An older restate 2.0 still works without them.
  • A storage host: a managed host with ZFS or btrfs that serves NFSv4. Setting up the storage host covers what you set up once; SysManage does the rest for each host. Each backed-up host needs the NFS client; Equip for backup installs it along with restate.
  • Backed-up hosts run Linux with systemd. The storage host can run Linux or FreeBSD; a FreeBSD host can be a storage host only.

The Coverage column shows what a backup of each host holds: Full (files and packages) on Debian and Ubuntu, Files only on other systems, and Not supported on Windows and macOS.

After you upgrade restate on a host or on the storage host, SysManage sends new job files on its own after the first job the new version runs, so new abilities are picked up without editing any policy. On the storage host it then runs protect once, so finished backups are locked in the form the new version uses.

Setting up the target

Open Backups in the Fleet menu and click Set up target:

  • Mount point on each host -- the agent mounts each host's repository at <mount point>/<repository> while a job runs. It must be under /srv, /mnt, /media or /var/backups. A job that finds no NFS mount there and cannot make one is refused, so restate never writes to the host's own disk.
  • Storage host and Path on the storage host -- the managed host that serves the share, and where the share's directory is on that host.
  • Seal each backup -- ZFS snapshot (give the dataset), btrfs snapshot (read-only) (give a snapshot directory on the same filesystem, outside the repositories), or Do not seal. Keep sealed snapshots for (days) -- the storage host removes its older seals itself after each new one, and always keeps the newest (default 14 days).
  • Warn when the storage is this full (%) and Critical when the storage is this full (%) -- when the target card warns that the storage path is filling up (default 85 and 95).
  • Write cache budget per host (GB) -- a host that backs up into an encrypted repository keeps a plain-text copy of what it wrote, under /var/cache/restate/repositories/, so that a backup needs no secret key. The host's Backup card shows Write cache on this host after each backup, and says when it is over this budget (default 20 GB). Needs restate 2.1.0.4 or later on the host. A repository that is not encrypted has no write cache, so the card shows no such line and this setting has no effect; encryption comes with Professional+.
  • Backup account on the storage host -- the account every host's export maps to, so nothing a host writes belongs to root there. The default is restate.
  • Backups at the same time -- how many hosts may back up to the target at once (1 to 50). Others wait their turn.

The target card then shows the storage host's side: how many hosts' job files it has confirmed, its last seal, prune and check, and the filesystem under the storage path. It warns, worst first, when there is no storage host (nothing is ever sealed, pruned or checked, and the repositories only grow), when the storage host cannot run restate, when the seal mode cannot work on that filesystem, and when a seal, prune or check is overdue. It also shows the storage check: whether the storage host is set up so hosts can only add, with what to change for each problem. See The storage check.

  • A storage path on a filesystem that cannot take snapshots, such as ext4 or XFS, works, but backups cannot be sealed there. The card says so.
  • For a btrfs seal the storage path must be a btrfs subvolume, not a plain directory. Create it on the storage host with btrfs subvolume create /srv/backups/restate.

Backing up a host

In the hosts table on the Backups page, click Configure on a host to set its backup policy:

  • Back up this host on a schedule, Every (hours), and an optional Start hour (UTC): backups then start only in the six hours from that hour. Start times are spread out a little per host, so a fleet does not all start at once.
  • Snapshots to keep -- the storage host prunes each repository down to this many.
  • Check the repository every (days) -- how often the storage host checks it.
  • Pause services while reading their data, and Services to pause: the services restate found on the host, such as postgresql, docker or nextcloud. Until a host has reported them, which it does after its policy is first saved, the list offers restate's built-in names instead. You can also type a name; it is saved even if you do not press Enter. A service that is not on the host is skipped.
  • Which to choose for common servers: nextcloud for Nextcloud, including the snap, which also dumps its database; mysql for a mail server or any host with MySQL or MariaDB, which dumps every database and stops the server only while its files are copied; postgresql for PostgreSQL; and unifi for a UniFi controller. A mail server's mailboxes need nothing paused.
  • Leave out (one path pattern per line) and Also back up (one path pattern per line) -- restate path patterns: * matches within one part of a path, ** across parts, and a pattern without a leading / matches at any depth. Where both match a path, Leave out wins.

restate already leaves out what can be downloaded or rebuilt: caches, ~/Downloads, build output, Python virtual environments, node_modules and the like. Also back up brings something back from those, even a folder inside one, such as /home/*/Downloads/contracts (restate 2.0.0.6 or later). A folder a sync client keeps, such as ~/Nextcloud, is a good candidate for Leave out when the server it syncs with is backed up as well.

A new policy starts as a daily backup. Without Professional+ it keeps the newest 30 snapshots; with it, the newest 7 plus the newest of each of the last 14 days, 8 weeks, 12 months and 3 years.

Saving sends the job files to the host and the storage host straight away. A policy with no schedule is configured too, so Back up now works for it. Back up now is on the Backups page and on the host's Backup tab; while a backup runs, the page shows how many paths and bytes it has read.

Before a host's first scheduled backup, SysManage asks the host for restate's estimate, which walks the files the policy would keep without reading any of them, and compares it with the free space on the storage. When it may not fit, the first backup waits and the host's Backup card says so: about how much there is to keep, how much is free, and the largest folders, the place to start adding paths to Leave out. The host also counts on the dashboard's backups card. restate compresses and de-duplicates, so a first backup usually needs less than the estimate; Back up now runs it anyway. A failed estimate never stops a backup, and once a host has a good backup the check is over.

To back up several hosts at once, tick them in the hosts table and click Back up selected. The first ones start at once, up to the target's Backups at the same time; the others show Waiting for a free slot and start as running backups finish. A host that cannot run a backup is skipped, and the page says why.

Set up backups for selected gives every ticked host that can run backups and has no policy those defaults, starting at 06:00 UTC, with start times spread across the window. Pausing services is left off, because which services a host has is known only once it reports them; set them per host with Configure. A ticked host that already has a policy, or cannot run backups yet, is skipped, and the page says why. A host you cannot tick says why when you point at its checkbox.

Prepare storage, on the host's Backups card, gives the host its own filesystem and an export to that host only on the storage host. Do it once for each host, before its first backup; see Prepare storage.

restate 2.0.0.4 and later create a host's repository on its first backup, with the create job key. With an older restate, create it once on that host before its first backup, for example sudo restate init /mnt/backups/web01.example.lan-1f3a9c2e.

The storage host checks a repository without its keys, so a check proves the repository's structure, not every byte in it. It is shown as Metadata check passed, never as Verified.

What each status means

  • Backed up The last backup succeeded and is recent.
  • Backing up A backup is running now. It takes the place of how the previous one ended.
  • Waiting for window A backup is queued, but the host's maintenance window is closed; it starts when the window opens. A host that is already overdue or failed keeps that status, with a note that its next backup is waiting for the window.
  • Incomplete The last backup finished but skipped files it could not read; the run lists the first of them.
  • Overdue There has been no good backup for more than twice the host's interval.
  • Failed The last backup failed, or restate did not trust what it found.
  • Never backed up The host has a policy but no backup yet.
  • Not equipped The host cannot run backups yet, with the reason: Install restate, Upgrade restate (older than 2.0, or its job unit is missing), Install the NFS client, Upgrade the agent (the agent predates backups), The agent must run as root, or Not supported on this OS.
  • Disabled The host has a policy but no schedule; it is backed up only with Back up now.
  • Not configured The host can run backups but has no policy.

Equipping a host for backup

When a host is Not equipped because restate or the NFS client is missing, or restate is too old, click Equip for backup on it, or select hosts and click Equip selected for backup. The host's agent installs both itself, from restate's own packages: its PPA on Ubuntu 22.04, 24.04 and 26.04, with nfs-common; its COPR on Fedora, with nfs-utils; and the package on restate's newest release, installed only when its checksum matches the release's list, on RHEL, AlmaLinux, Rocky Linux, CentOS Stream and Oracle Linux 9 and 10 (with nfs-utils), openSUSE Leap 16, SLE 16 and openSUSE Tumbleweed (with nfs-client), Alpine 3.21 to 3.24 (with nfs-utils), and FreeBSD, OpenBSD and NetBSD, which have NFS built in. On macOS it uses Homebrew, run as Homebrew's owner and never as root. The server sends no package name, address or command. The host shows Equipping until its agent answers. When the install fails, the reason appears below the host; point at it to see the tool's output.

Backups run through systemd for now, so a host can be equipped on every system above but backed up only on Linux with systemd; a FreeBSD host can also be the storage host. On Alpine, the BSDs and macOS, restate is installed but no backup runs until the agent has a job runner there, and an Alpine host keeps reading Upgrade restate, which equipping it does not change. Debian has no restate package, so build restate from source there; Windows is not supported.

On other systems, install restate by hand, as the host's row says. An agent older than this feature shows Upgrade the agent to equip this host from here. Check again asks the agent whether it can run restate now, so a host you equipped by hand reads correctly within seconds instead of after its agent's next restart.

Equip for backup installs software, so on a host with maintenance windows it waits for the next one, and the host shows Waiting for this host's maintenance window to install restate. The hour the agent has to answer starts only when the request is sent.

Hosts that cannot reach the storage

SysManage asks each host whether it can open a connection to the storage host's NFS port (2049): before Equip for backup, when its policy is saved, once a day, and when you click Check again. A host that cannot shows This host cannot reach the backup storage with the storage host, its address and the port, and Equip for backup, Configure, Back up now and its scheduled backups are held; the bulk actions skip it and say why. A host that has not been checked yet is never held.

A typical case is a SysManage server in the cloud that is itself a managed host, while the storage host is on a home or office network: it cannot mount that storage, so it cannot be backed up to it. Back it up to storage it can reach, or give it a network path to the storage host, such as a VPN.

Click a status above the table to show only the hosts with it; click it again, or Show all hosts, to see them all. A backup that skipped files it could not read says Files not read under its status, with the first of them when you point at it.

Last backup is the last successful backup. When a later attempt failed, the host's Backup card also shows Last attempt with how it ended. A backup that found the repository busy -- another job had it locked -- shows Busy, will retry and is tried again later; it is not a failure.

On the Home dashboard, Backups needing attention counts the hosts whose backup is overdue, incomplete or failed, plus the target once when its storage side has a problem: no storage host, a seal, prune or check that has not run in time, a failed drive, or storage that is critically full. It is red when a backup failed or the storage has a problem, and yellow when backups are only overdue or incomplete. Click it to open the Backups page.

Recent jobs

Recent jobs lists every backup, protect, seal, prune, check, storage use, repack, prepare storage and restore job. When a job fails, the Detail column gives the reason, for example a permission error on the share. For a backup that paused services, it also lists each one, how long it was paused, and any that could not be paused or resumed -- the reason a run is Incomplete.

Clear list takes finished jobs off the list; queued and running jobs stay. Nothing is removed from the audit log, and the backup status is not affected. SysManage also deletes finished jobs older than 30 days on its own, always keeping the newest of each kind for every host.

Restoring files

Click Restore files on a host, pick a snapshot, and list the paths to restore (empty means everything) and any to leave out. Preview comes first: it shows how many files and bytes would come back, and any paths that are not in the snapshot. Only then does Restore to staging run.

With restate 2.1.0.4 or later on the host, Browse the snapshot's folders shows them: click a folder to open it and Add to put a file or folder on the list of paths to restore. Each folder is read from the snapshot index alone, so it opens in seconds. Seeing file names needs the Restore Files role, as restoring them does.

With restate 2.0.0.7 or later, Preview is planned from the snapshot index alone and takes seconds, even for a whole host. It says that the backed-up data was not read: the storage host's regular check is what proves the data is intact. A real restore does read the data, and restate reads each pack from its start, so restoring a small folder whose files changed often can still take minutes. In testing, 4.5 GB of ~/.config took about 7 minutes over Wi-Fi.

By default, files are restored into a staging directory on the host, under /var/lib/sysmanage-agent/restore/, never over the live files. Move what you need into place yourself. Snapshots are not signed yet, so a restore asks you to confirm This snapshot is not signed. Restore it anyway.

Paths are matched against the files the snapshot recorded, by their real paths. A path through a symbolic link, such as /var/snap/nextcloud/current/..., matches nothing: use the path the link points to (readlink /var/snap/nextcloud/current) until a restate that follows links in a snapshot is released. Files a package installed and that were never changed are recorded by package version rather than copied, so a file restore does not bring them back; reinstall the package instead.

The database dumps that paused services made are in the snapshot under /var/lib/restate/dumps/, one folder per service, such as mysql-mariadb/mysqldump.sql.gz or nextcloud-nextcloud/mysqldump.sql.gz, and are restored like any other file. Nextcloud's config.php is recorded while Nextcloud is in maintenance mode, so after putting it back into place, run sudo nextcloud.occ maintenance:mode --off on a snap install.

To put files straight back where they were, choose Into place, replacing the host's files and name specific paths, such as /etc/nginx; a whole host is not restored in place, which is a rebuild. Preview then compares the snapshot with the host's files as they are now. Restore into place needs its own confirmation, Replace the files at these paths. restate checks the whole selection against the snapshot before it writes anything, writes each file beside its destination and renames it over the old one only when it matches the snapshot, and never follows a symbolic link on the way. The agent always leaves out its own state directory, so a restore cannot put back an old copy of the agent's database. Every restore into place is audited with who asked for it, the snapshot and the paths.

What changed since the last backup

With restate 2.1.0.4 or later on the host, its Backup card has What changed. It compares the host as it is now with its newest snapshot and lists how many files and folders were added, deleted and modified, with the first of them and what changed in each (content, mode or owner). A file whose size, times and inode are unchanged is not read, so the check is quick, and nothing is backed up or written. It needs the Manage Backups role, and one check runs at a time per host.

Permissions

Anyone signed in can see the Backups page. Setting up the target, setting policies and Back up now need the Manage Backups role; restoring files also needs Restore Files.

Edition Requirements

Everything on this page is in all editions, including the Community Edition: one target, per-host schedules and Back up now, keeping the last N snapshots, append-only hosts with sealing, pruning and checking on the storage host, the Backups page, and file restore into staging or into place. Backup safety is not a paid feature.

Professional+ adds encrypted backups with keys held in OpenBAO, automatic key rotation, a sealed break-glass key export, grandfather-father-son retention and backup alerts: see Fleet Backups (Professional+).

Still planned for Professional+: policies by tag or group, scheduled full-read verification, snapshot signing, reports, a timeline of what changed between snapshots, and package-level restore. Planned for Enterprise: several targets and per-site targets, off-site replication, bare-metal recovery and clones, fleet-wide restore jobs, four-eyes approval, legal hold and automated restore drills.
