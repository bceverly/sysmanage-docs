Fleet Backups

SysManage backs up your hosts with restate, a backup tool that records what a fresh install of the operating system would not put back: your files, and on Debian and Ubuntu the packages too. Every host writes to its own repository on one NFS share, and the machine that serves the share -- the storage host -- does everything that could remove a backup. A host that is broken into cannot delete its own history.

This page is about backing up your managed hosts. To back up the SysManage server itself, see Backup & Recovery.

How it works

  • One target. The backup target is one NFS share. Every backed-up host mounts it at the same place, for example /mnt/backups.
  • One repository per host. Each host writes only to its own directory on the share, named after the host and the start of its host id, such as web01.example.lan-1f3a9c2e. The id keeps two hosts with the same name apart, and keeps a renamed host's history.
  • Hosts only add. A host's backup job can create new snapshots and nothing else. It never prunes, so it never deletes.
  • The storage host does the rest. After each good backup, the storage host's own agent seals it with a read-only filesystem snapshot (ZFS or btrfs), then prunes old snapshots down to the number you keep, and on its own schedule checks the repository. A seal always comes before a prune, and a failed seal holds the prune back.

Why it is built this way: ransomware that takes a host also takes everything that host can reach. If the host could delete its backups, the attacker could too. Here the host can only add, and the sealed snapshots live on a machine the host cannot log in to.

The agent never builds a restate command line from what the server sends. It checks the server's settings against a fixed list, writes them as a root-owned job file in /etc/restate/jobs.d, and starts restate's own job unit. restate refuses a job file that anyone but root can change.

What you need

  • restate 2.0 or later on every host you back up and on the storage host. On Ubuntu: sudo add-apt-repository ppa:bceverly/restate and sudo apt install restate. Elsewhere, build it from source as its README describes (gmake build and sudo gmake install on FreeBSD).
  • An NFS share served by a managed host, mounted on every host you back up. Setting up the storage host walks through it on FreeBSD with ZFS.
  • Backed-up hosts run Linux with systemd. The storage host can run Linux or FreeBSD; a FreeBSD host can be a storage host only.

The Coverage column shows what a backup of each host holds: Full (files and packages) on Debian and Ubuntu, Files only on other systems, and Not supported on Windows and macOS.

Setting up the target

Open Backups in the Fleet menu and click Set up target:

  • Mount point on each host -- where every backed-up host has the share mounted. It must be under /srv, /mnt, /media or /var/backups, and the agent refuses to back up a host where it is not an NFS mount.
  • Storage host and Path on the storage host -- the managed host that serves the share, and where the share's directory is on that host.
  • Seal each backup -- ZFS snapshot (give the dataset), btrfs snapshot (read-only) (give a snapshot directory on the same filesystem, outside the repositories), or Do not seal. Old ZFS and btrfs snapshots are not removed for you yet; set their retention on the storage host.
  • Backups at the same time -- how many hosts may back up to the target at once (1 to 50). Others wait their turn.

The target card then shows the storage host's side: how many hosts' job files it has confirmed, its last seal, prune and check, and the filesystem under the storage path. It warns, worst first, when there is no storage host (nothing is ever sealed, pruned or checked, and the repositories only grow), when the storage host cannot run restate, when the seal mode cannot work on that filesystem, and when a seal, prune or check is overdue.

  • A storage path on a filesystem that cannot take snapshots, such as ext4 or XFS, works, but backups cannot be sealed there. The card says so.
  • For a btrfs seal the storage path must be a btrfs subvolume, not a plain directory. Create it on the storage host with btrfs subvolume create /srv/backups/restate.

Backing up a host

In the hosts table on the Backups page, click Configure on a host to set its backup policy:

  • Back up this host on a schedule, Every (hours), and an optional Start hour (UTC): backups then start only in the six hours from that hour. Start times are spread out a little per host, so a fleet does not all start at once.
  • Snapshots to keep -- the storage host prunes each repository down to this many.
  • Check the repository every (days) -- how often the storage host checks it.
  • Pause services while reading their data, with restate's hooks to use, such as postgres.

Saving sends the job files to the host and the storage host straight away. A policy with no schedule is configured too, so Back up now works for it. Back up now is on the Backups page and on the host's Backup card; while a backup runs, the page shows how many paths and bytes it has read.

restate 2.0.0.1 does not create a host's repository on its own. Before a host's first backup, create it once on that host, for example sudo restate init /mnt/backups/web01.example.lan-1f3a9c2e. When the host's restate offers the create job key, the agent uses it and the first backup creates the repository itself.

The storage host checks a repository without its keys, so a check proves the repository's structure, not every byte in it. It is shown as Metadata check passed, never as Verified.

What each status means

  • Backed up The last backup succeeded and is recent.
  • Backing up A backup is running now. It takes the place of how the previous one ended.
  • Incomplete The last backup finished but skipped files it could not read; the run lists the first of them.
  • Overdue There has been no good backup for more than twice the host's interval.
  • Failed The last backup failed, or restate did not trust what it found.
  • Never backed up The host has a policy but no backup yet.
  • Not equipped The host cannot run backups yet, with the reason: Install restate, Upgrade restate (older than 2.0, or its job unit is missing), Upgrade the agent (the agent predates backups), The agent must run as root, or Not supported on this OS.
  • Disabled The host has a policy but no schedule; it is backed up only with Back up now.
  • Not configured The host can run backups but has no policy.

Last backup is the last successful backup. When a later attempt failed, the host's Backup card also shows Last attempt with how it ended. A backup that found the repository busy -- another job had it locked -- shows Busy, will retry and is tried again later; it is not a failure.

Restoring files

Click Restore files on a host, pick a snapshot, and list the paths to restore (empty means everything) and any to leave out. Preview comes first: it shows how many files and bytes would come back, and any paths that are not in the snapshot. Only then does Restore to staging run.

Files are restored into a staging directory on the host, under /var/lib/sysmanage-agent/restore/, never over the live files. Move what you need into place yourself. Snapshots are not signed yet, so a restore asks you to confirm This snapshot is not signed. Restore it anyway.

Permissions

Anyone signed in can see the Backups page. Setting up the target, setting policies and Back up now need the Manage Backups role; restoring files also needs Restore Files.

Edition Requirements

Everything on this page is in all editions, including the Community Edition: one target, per-host schedules and Back up now, keeping the last N snapshots, append-only hosts with sealing, pruning and checking on the storage host, the Backups page, and file restore into staging. Backup safety is not a paid feature.

Planned for Professional+: policies by tag or group, maintenance-window-aware schedules, grandfather-father-son retention, scheduled full-read verification, encryption keys held in OpenBAO, snapshot signing, alerts and reports, a timeline of what changed between snapshots, and package-level restore. Planned for Enterprise: several targets and per-site targets, off-site replication, bare-metal recovery and clones, fleet-wide restore jobs, four-eyes approval, legal hold and automated restore drills.
