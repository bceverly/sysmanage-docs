Backing Up iCloud Photos

SysManage can keep a copy of the photos and videos in one or more iCloud libraries on your own backup storage. The work runs on your backup storage host only -- the machine that already holds the fleet's backups -- never on a backed-up host. It uses icloudpd, an open-source downloader, at a version SysManage pins and checks.

Before you start

  • A backup target with a storage host. See Setting up the storage host. The storage host must run Linux (x86_64 or aarch64), FreeBSD, OpenBSD or NetBSD; on the BSDs it also needs Python 3.10 to 3.13 (for example pkg install python311).
  • Two-factor authentication on each Apple ID. Apple's older two-step verification is not supported.
  • Web access to iCloud data. If the Apple ID uses Advanced Data Protection, turn on Access iCloud Data on the Web on the iPhone (Settings, your name, iCloud). Without it Apple refuses every download, and SysManage says so.
  • The Manage Cloud Backups role for whoever sets it up and signs in. Administrators have it.

1. Enable iCloud backup

Open Backups and find Cloud backup. It names your storage host. Press Enable iCloud backup. In one step the storage host's agent downloads the pinned icloudpd and checks its SHA-256 before keeping it (on Linux the release's own program; on the BSDs a private Python environment built from the release's checked package), makes the cloud-photos place under the storage path (a ZFS dataset when the storage path is one, so the target's seal covers it), and makes a private directory for the sign-in sessions. If something fails, the panel says why and shows the tool's output.

Press it again at any time to repair the installation. A newer SysManage agent may pin a newer icloudpd; it is only installed when you press the button again.

2. Add the accounts

Press Add iCloud account and enter the Apple ID, a name to show, and the password. The password goes straight to OpenBAO under your organization's own path. It is never stored in the database, never written to a log and never shown again. The storage host receives it for one job at a time, at the moment the downloader asks for it, and passes it on without putting it in a command line, an environment variable or a file. Every hand-over is in the audit log.

Each account has its own place under cloud-photos. Photos are filed by date, as originals with their Live Photo videos and XMP sidecar files, and their names are kept as Apple has them.

3. Sign in with the two-factor code

Press Connect on the account. Apple sends a six-digit code to the account's devices; when the account shows Waiting for the two-factor code, press Enter code, type it, and send it within 15 minutes. The code reaches the waiting job once and is then erased. Then use List libraries if the account has a shared library, and choose it in the account's settings.

Apple's sign-in lasts about two months. Ten days before it ends, the account says so on the Backups page and on the dashboard's backup card, and the cloud backup managers get an e-mail when e-mail is configured. Press Connect again to renew it. If Apple refuses a sign-in, or wants a new one before then, the account shows Needs sign-in and is not run again on schedule until someone signs in. It is never shown as "no new photos".

4. The schedule

Each account downloads every 24 hours by default, optionally inside a window that starts at a UTC hour you choose, like a backup policy. The first download takes the whole library. After that a download stops once it has seen 50 photos in a row that are already present (you can change the number), and once a week a full pass checks the whole library. Downloads share the target's limit on jobs at once with the hosts' backups. Run now starts one as soon as there is room. Each run reports how many files were downloaded, already present and failed, the bytes and how long it took.

Deleting from iCloud

By default nothing is ever deleted from iCloud. An account can be set to delete photos from iCloud once they are downloaded; the setting warns that the photos then leave every device signed in to that Apple ID and that the backup storage holds the only copy, and it must be confirmed. Keeping only the most recent days in iCloud is not offered.

Getting photos back

The photos are ordinary files under cloud-photos/<account>/YYYY/MM/DD on the storage path. Copy them from the storage host, or from a seal (a ZFS snapshot of the storage path), with any tool you like; the XMP files beside them carry the dates and descriptions. Deleting an account in SysManage removes its password and sign-in only. Its photos stay where they are until you remove them.

Where it runs and what it keeps

The downloader runs as the agent's own account on the storage host, with no network listener. Its sign-in sessions are kept in the agent's state directory, readable by that account only, outside the backup storage, and are left out of the storage host's own backup. The FreeBSD agent's sudoers file allows exactly the two zfs create commands that make the cloud-photos datasets. Every account change, sign-in and run is audited. An air-gapped repository server has no internet access, so it does not offer this feature.
