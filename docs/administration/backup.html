Backing Up and Recovering the SysManage Server

Everything a SysManage server needs to come back after a disk failure, a lost machine or a bad change: what to back up, where it lives on each platform, the commands to back it up, and the order in which to put it back. Written to be followed during an outage.

The server does not back itself up yet

Nothing on this page happens on its own. A built-in "Back up this SysManage server" policy is planned (roadmap Phase 25.9) and is not available yet. Until then, schedule the commands below yourself and copy the result off the machine. The host backups protect your managed hosts, not the SysManage server itself.

What to back up, most important first

  1. The agents' CA and the server identity -- /etc/sysmanage/certs/ (ca.crt, ca.key, server.crt, server.key), or the directory set by certificates.path. The CA signs every approved host's certificate. If it is missing, the server quietly creates a new one the next time it needs it.
  2. OpenBAO -- its data directory /var/lib/openbao/data, its key file /var/lib/openbao/init.json (unseal key and root token), its configuration /etc/openbao/openbao.hcl, and the server's token file /etc/sysmanage/openbao-token. OpenBAO holds the tenant database credentials, backup encryption keys, SSH keys and any server secrets that were moved out of sysmanage.yaml (the JWT secret, password salt, recovery password, database password and SMTP password).
  3. PostgreSQL -- the database named in the registry: block of /etc/sysmanage.yaml (normally sysmanage), which holds the control-plane registry, the shared reference data and, on a single-tenant server, all host data. With multi-tenancy on, also every tenant database. Back up the roles too (pg_dumpall --globals-only).
  4. /etc/sysmanage.yaml -- the database connection and password, the JWT secret, the password salt, the recovery account and the license key.
  5. The TLS certificate nginx serves -- /etc/sysmanage/tls/server.crt and server.key, or wherever your nginx site file points (for example /etc/letsencrypt/), and the nginx site file itself if you edited it.
  6. The license -- the key is license.key in /etc/sysmanage.yaml. The server also caches the license server's public key in /var/lib/sysmanage/license/public_key.pem; a connected server fetches it again, but an offline or air-gapped server needs the copy.
  7. Other keys in /var/lib/sysmanage -- the federation identity (federation/) and the air-gap collector keys (airgap/), when you use those features.
  8. Optional -- the Professional+ engines in /var/lib/sysmanage/modules are downloaded again with your license, and logs are not needed to recover. Leave both out unless the server is air-gapped, where engines come from the bundle you imported.

Risk: the unseal key is stored on the same server

The key that unseals OpenBAO is kept next to the data it protects. A package install writes it to /var/lib/openbao/init.json (root only, mode 0600). A configuration made with sysmanage_secure_installation also carries the unseal key in /etc/sysmanage.yaml as vault.server.unseal_keys, with the root token as vault.token, beside the database password. Anyone who can read that file, or any backup of it, holds every secret. Encrypt your backups, keep them off the server, and limit who can read them. Moving the unseal key out of the server is planned (roadmap Phase 25.9).

Where it lives on each platform

The commands on this page use the Ubuntu and Debian paths. The OpenBAO data directory and key file are the same on every Unix platform; the other paths differ as shown.

Platform Configuration TLS certificate and nginx site OpenBAO Services
Ubuntu, Debian /etc/sysmanage.yaml, /etc/sysmanage/ /etc/sysmanage/tls/, /etc/nginx/sites-available/sysmanage-nginx.conf /var/lib/openbao/, /etc/openbao/openbao.hcl sysmanage, openbao, sysmanage-openbao-init, nginx
RHEL family, openSUSE /etc/sysmanage.yaml, /etc/sysmanage/ /etc/sysmanage/tls/, /etc/nginx/conf.d/sysmanage-nginx.conf /var/lib/openbao/, /etc/openbao/openbao.hcl sysmanage, openbao, sysmanage-openbao-init, nginx
FreeBSD /etc/sysmanage.yaml, /usr/local/etc/sysmanage/ (including config.yaml), /etc/sysmanage/ /usr/local/etc/sysmanage/tls/, /usr/local/etc/nginx/sysmanage-nginx.conf /var/lib/openbao/, /usr/local/etc/openbao/openbao.hcl service sysmanage, service openbao (unseals when it starts), service nginx
macOS /etc/sysmanage.yaml, /etc/sysmanage/ /usr/local/etc/sysmanage/tls/, etc/nginx/servers/sysmanage-nginx.conf under the Homebrew prefix /var/lib/openbao/, /usr/local/etc/openbao/openbao.hcl launchd jobs com.sysmanage.server and com.sysmanage.openbao; nginx through brew services
Windows C:\ProgramData\SysManage\sysmanage.yaml; the CA is in C:\ProgramData\SysManage\certs C:\ProgramData\SysManage\tls\, C:\Program Files\SysManage Server\nginx\conf\sysmanage-nginx.conf C:\ProgramData\SysManage\openbao\ (data\, init.json, openbao.hcl) SysManageServer, SysManageOpenBAO, SysManageNginx

On FreeBSD the package writes its settings to /usr/local/etc/sysmanage/config.yaml, while the server reads /etc/sysmanage.yaml unless SYSMANAGE_CONFIG_PATH says otherwise. Back up both.

Taking a backup (Ubuntu and Debian)

Run these as root (sudo -i). The database dump does not need the server stopped. OpenBAO uses the file storage backend (storage "file" in openbao.hcl), which has no online snapshot: copy it with OpenBAO stopped. Stop SysManage first, so nothing asks OpenBAO for a secret while it is down. If you changed OpenBAO to the raft backend, use bao operator raft snapshot save instead of the copy.

1. Record the version and the tenant databases

mkdir -p /var/backups/sysmanage && chmod 700 /var/backups/sysmanage
cd /var/backups/sysmanage
dpkg-query -W sysmanage > package-version.txt

# Multi-tenancy only: every tenant database and the server that holds it
sudo -u postgres psql -d sysmanage -Atc \
  "SELECT t.slug, p.host, p.port, p.dbname
     FROM registry_tenant t
     JOIN registry_tenant_placement p ON p.tenant_id = t.id
    ORDER BY t.slug" > tenants.txt

2. Dump the databases

# Roles (the sysmanage owner and any roles OpenBAO created), then the bootstrap database
sudo -u postgres pg_dumpall --globals-only > globals.sql
sudo -u postgres pg_dump -Fc sysmanage > sysmanage.dump

# Multi-tenancy only: one dump per tenant database on this PostgreSQL server
# (remove from tenants.txt any whose host column names another server)
for db in $(cut -d'|' -f4 tenants.txt); do
  sudo -u postgres pg_dump -Fc "$db" > "tenant-$db.dump"
done

A tenant database on another PostgreSQL server (its host column) is dumped on that server the same way, with its own pg_dumpall --globals-only. A remote bootstrap database can be dumped from the SysManage server as its owner: pg_dump -h <host> -U sysmanage -Fc sysmanage > sysmanage.dump.

3. Copy OpenBAO with it stopped

systemctl stop sysmanage
systemctl stop openbao
tar -C /var/lib -czf openbao.tar.gz openbao
systemctl start openbao
systemctl restart sysmanage-openbao-init     # unseals OpenBAO again
systemctl start sysmanage

4. Copy the configuration, certificates and keys

tar -czf files.tar.gz -C / \
  --exclude=var/lib/sysmanage/modules \
  --exclude=var/lib/sysmanage/airgap-iso \
  --exclude=var/lib/sysmanage/airgap-staging \
  etc/sysmanage.yaml etc/sysmanage etc/openbao \
  etc/nginx/sites-available/sysmanage-nginx.conf \
  var/lib/sysmanage
# Add etc/letsencrypt if nginx serves a Let's Encrypt certificate

Then encrypt /var/backups/sysmanage and copy it to storage off this machine. Take the database dumps and the OpenBAO copy in the same run: OpenBAO creates database roles for tenants, so the two must describe the same moment.

With multi-tenancy on, the server can also run your own per-tenant backup tool on a schedule and record each tenant's recovery point: set backup.command (for example a pgBackRest command) in sysmanage.yaml. It runs the command you give it; it does not back up OpenBAO, the CA or the configuration.

Rebuilding the server on a new machine

  1. Install the same package version recorded in package-version.txt (for example apt install sysmanage=<version>), and the same or a newer major version of PostgreSQL. Do not create the sysmanage database by hand: the restore creates it. The new install creates its own configuration and its own empty OpenBAO; the next steps replace both.
  2. Stop everything SysManage runs: systemctl stop sysmanage openbao.
  3. Restore the databases: roles first, then the bootstrap database, then each tenant database.
cd /var/backups/sysmanage
sudo -u postgres psql -f globals.sql
sudo -u postgres pg_restore -C -d postgres sysmanage.dump
for f in tenant-*.dump; do sudo -u postgres pg_restore -C -d postgres "$f"; done
  1. Restore the configuration, certificates and keys over the fresh install, and put OpenBAO back as one piece: its data and its init.json only work together.
tar -C / -xzpf files.tar.gz
rm -rf /var/lib/openbao
tar -C /var/lib -xzpf openbao.tar.gz
chown root:openbao /var/lib/openbao && chmod 750 /var/lib/openbao
chown -R openbao:openbao /var/lib/openbao/data
chown root:root /var/lib/openbao/init.json && chmod 600 /var/lib/openbao/init.json
chown -R sysmanage:sysmanage /etc/sysmanage /var/lib/sysmanage
chown sysmanage:sysmanage /etc/sysmanage.yaml && chmod 640 /etc/sysmanage.yaml
  1. Start and unseal OpenBAO, and check that the unseal step succeeded.
systemctl start openbao
systemctl restart sysmanage-openbao-init
systemctl status sysmanage-openbao-init
  1. Check the schema: sudo sysmanage-migrate --status. With the same package version every chain and tenant reads up to date. If anything is PENDING, the backup is from an older release: run sudo sysmanage-migrate.
  2. Start the server: nginx -t && systemctl reload nginx, then systemctl start sysmanage.
  3. Point the agents' server name at the new machine. Each agent connects to server.hostname in its /etc/sysmanage-agent.yaml. If the new machine keeps that name, change the DNS record. If the name changes, every agent's configuration must change, and the TLS certificate must be valid for the new name.
  4. Verify: https://<server>/api/health and https://<server>/api/health/db answer healthy, you can sign in, and hosts turn active again as their agents reconnect.

Why agents reconnect without enrolling again

An agent proves which host it is with its host token, which it keeps locally and which the server stores in the host's database row. Restore the database and the token matches again, so the agent reconnects as the same host and needs no new approval. Hosts that were registered after the backup was taken are not in the restored database and come back as new hosts.

The agent checks the server's TLS certificate the ordinary way: it must be valid for the name the agent uses (agents verify by default, server.verify_ssl). Agents do not pin the server or present their own certificates yet; that is planned (roadmap Phase 25.10). So today what lets agents in is the restored database plus a trusted certificate for the same name, not the CA. Restore the CA anyway: without it the server makes a new one, the host certificates already issued no longer chain to it, and pinning will depend on it once it ships.

Losing one piece

Only OpenBAO

Replace /var/lib/openbao as a whole from the last backup, data and init.json together, as in step 4 above, with sysmanage and openbao stopped. Then start openbao, restart sysmanage-openbao-init and start sysmanage. Secrets written after that backup are lost, for example the database credentials of a tenant created since then or a backup key created since then; recreate them. With no OpenBAO backup at all, its secrets cannot be recovered: the tenant databases still exist, but the server has no credentials to reach them.

Only one tenant database

Other tenants are not touched. Stop sysmanage so nothing holds a connection to that database, then restore it on the PostgreSQL server that holds it and bring it to the current schema:

sudo -u postgres dropdb --if-exists <dbname>
sudo -u postgres pg_restore -C -d postgres tenant-<dbname>.dump
sudo sysmanage-migrate --tenants-only
sudo sysmanage-migrate --status
systemctl start sysmanage

That tenant's hosts return to the moment of the dump; agents reconnect with their tokens as above. The per-tenant migration step leases credentials from OpenBAO, so OpenBAO must be running and unsealed.

Only the configuration or the certificates

Extract just that path from files.tar.gz, for example tar -C / -xzpf files.tar.gz etc/sysmanage.yaml, fix its owner as above and restart sysmanage (or reload nginx for the TLS certificate).

Test the restore

A backup you have not restored is a guess. At least once, and after every major upgrade, rebuild a test server from the backup alone on a separate machine, following this page with the production server out of the picture, and time it. Keep the production agents on production: give the test server a name of its own and point one test agent at it.
