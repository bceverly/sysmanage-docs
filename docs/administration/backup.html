Backing Up and Recovering the SysManage Server

Everything a SysManage server needs to come back after a disk failure, a lost machine or a bad change: what to back up, where it lives on each platform, the commands to back it up, and the order in which to put it back. Written to be followed during an outage.

The server backs itself up

The server is one of the hosts SysManage manages, and it backs itself up the same way, with restate. On the Backups page, Back up this SysManage server creates a policy for the server's own host, preset to everything the server needs to come back. The host backups page describes targets, schedules and retention, which work the same way here.

What it needs

  • The server's own agent, approved. SysManage finds the server's host by name; if it cannot tell which host is the server, it asks you to pick it.
  • restate on the server's host, installed with Equip for backup like any backed-up host. restate 3.0.0.0 or later copies the databases without stopping them (see below).
  • A backup target the server can reach. Today the server mounts the storage host's repository over NFS, so the storage host must be on a network the server can reach. A server in a cloud cannot mount a storage host at home or in an office yet; until it can, back it up by hand as described further down.
  • Professional+, for encryption: a break-glass escrow key, saved in a host's Encryption panel. The server's backup is encrypted to it.

Setting it up

  1. On the Backups page, choose Back up this SysManage server. If no host is named as the server is, pick the one its agent runs on.
  2. Choose the target and the schedule. Pick a quiet start hour.
  3. Save, then choose Back up now once and check that the run ends ok.
  4. Copy the files listed under Never backed up to safe keeping away from the server, such as a password manager or a sealed envelope, and keep them up to date. Recovery needs them, and the backup never holds them.

Until the server has a recent good backup, the Backups page says so at the top.

What goes in the backup

How it is handled What it covers
Backed up The agents' certificate authority and the server identity (/etc/sysmanage/certs), OpenBAO's data, PostgreSQL, /etc/sysmanage.yaml, the TLS certificates (including /etc/letsencrypt), /var/lib/sysmanage with the license, and the rest of the host.
Left out Downloaded again when needed: engine bundles, the GeoIP database, package mirrors and logs.
Never backed up OpenBAO's unseal or recovery key and root token (/var/lib/openbao/init.json) and the server's OpenBAO token (/etc/sysmanage/openbao-token). A stolen backup therefore cannot unseal the OpenBAO copy inside it.

Consistent databases

PostgreSQL keeps running. With restate 3.0.0.0 or later on the server's host, restate takes one consistent dump of every database on the server's cluster (the registry and every tenant database, with their roles) while SysManage keeps serving, and leaves the cluster's own files out. The dump is the copy you restore from. With an older restate, PostgreSQL is stopped while its files are copied, and SysManage may show errors for that time.

OpenBAO is copied stopped. A packaged OpenBAO keeps its data in files, which cannot be copied while it runs. restate stops it, copies its data, starts it again and waits until it is unsealed, usually within a second or two. With raft storage, restate saves a snapshot instead.

Encryption

Community: the server's backup is not encrypted, and it holds the database password from the configuration. Keep the backup storage as safe as the server itself.

Professional+: the server's backup is encrypted to your break-glass escrow key, never to a key kept in the server's own OpenBAO: restoring OpenBAO cannot depend on a key that is inside it. SysManage holds only the public half. The repository's name ends in -enc, and it is restored by hand with the secret half of the key, as the recovery steps below describe.

Keep these in escrow, never in the backup

  • /var/lib/openbao/init.json: OpenBAO's unseal (or recovery) key and its root token.
  • /etc/sysmanage/openbao-token: the server's own OpenBAO token.
  • Professional+ only: the secret half of your break-glass escrow key (gpg --armor --export-secret-keys).

Recovering the server from its own backup

Follow these steps with SysManage down and only restate and the backup. Nothing here needs SysManage to be running. The commands use the Ubuntu and Debian paths; the table below gives the other platforms'. In tests, a server rebuilt this way on a new machine was serving again about four minutes after the old one stopped, and its agents came back on their own with the same host identities.

What you need before you start

  • The backup storage, holding the server's repository, <storage path>/<server name>-<short host id>. Its name ends in -enc when it is encrypted. The storage path is shown on the target's card on the Backups page.
  • The files you keep in escrow, listed above.
  • A machine on the same operating system release as the old server, with restate installed, ideally with the same host name. Agents find the server by name, so keep the name and move its DNS record rather than renaming.

Below, REPO is the repository's path as this machine sees it, and KEY stands for the options that read and trust it: --decrypt-with /root/escrow-secret.asc on Professional+; --trusted-key /root/signing.pub.asc when snapshot signing is on; --allow-unverified when it is not. restate refuses an unsigned snapshot without that last option.

1. Install the server package, and keep it stopped

Install the SysManage version the backup was taken with (restate packages REPO lists what the old server had installed). Then stop it before anything starts writing:

sudo systemctl stop sysmanage nginx openbao postgresql
sudo systemctl disable --now sysmanage-openbao-init

2. Reach the repository

SysManage exports each repository only to its own host's address, so the new machine cannot mount it as it is. On the storage host, export it read-only to the new machine's address for the recovery, then mount it on the new machine:

# On the storage host
sudo exportfs -o ro,sync,no_subtree_check,root_squash,all_squash,anonuid=<restate uid>,anongid=<restate gid> \
  <new address>:<storage path>/<repository>

# On the new machine
sudo mkdir -p /mnt/restore
sudo mount -t nfs4 -o ro <storage host>:<storage path>/<repository> /mnt/restore
sudo restate snapshots --no-lock /mnt/restore

Pick the newest good snapshot. With restate 3.0.0.0 or later, add --no-lock to every restate command on this page and restore straight from the read-only mount (REPO is /mnt/restore); make sure no prune runs on the storage host meanwhile. An older restate takes a lock inside the repository, so copy the repository to local disk first and use the copy as REPO.

3. See what comes back, then put it back

The plan reads only the index, takes seconds and writes nothing. The restore then checks every file against the index before it writes anything, and refuses the whole image if any file is damaged:

sudo restate restore --plan --no-lock KEY REPO::SNAPSHOT
sudo restate restore --check-first --root / --no-lock KEY REPO::SNAPSHOT

This brings back the certificate authority and the server identity, /etc/sysmanage.yaml, the TLS certificates, /var/lib/sysmanage, OpenBAO's data, the PostgreSQL dump (pg_dumpall.sql under /var/lib/restate/dumps/postgresql-*/) and the host's own identity files. A backup taken with an older restate also holds the cluster's own files, copied while PostgreSQL was stopped.

Set the old host name now, before anything starts

The restore puts back /etc/hostname, but the running system keeps the new name until it reboots. Run sudo hostnamectl set-hostname <old short name> now. The server's own agent registers by name: started under another name, it enrolls as a new host waiting for approval and replaces the identity it had. If that happened, set the name, stop the agent, restore its identity with --include "/var/lib/sysmanage-agent/**", delete the new pending host on the Hosts page, and start the agent again.

Remove the temporary export now, before SysManage starts: unmount it on the new machine (sudo umount /mnt/restore), then run sudo exportfs -u <new address>:<storage path>/<repository> on the storage host. Left in place, it hides the read-write export SysManage makes for the new address, and the next backup fails with "Read-only file system". If you removed it after SysManage started, run sudo exportfs -ra on the storage host to put SysManage's own exports back.

4. Put the escrowed OpenBAO files back

The package made an init.json and a token of its own when it was installed. They belong to an OpenBAO that no longer exists, so replace them with the ones you kept in escrow:

sudo install -o root -g root -m 0600 init.json /var/lib/openbao/init.json
sudo install -o sysmanage -g sysmanage -m 0640 openbao-token /etc/sysmanage/openbao-token

5. Start OpenBAO and unseal it

With file storage (packaged installs) the data came back in step 3: start OpenBAO and let the unseal unit unseal it from init.json. With raft storage, start OpenBAO and then load the snapshot: bao operator raft snapshot restore /var/lib/restate/dumps/openbao-*/openbao.snap.

sudo systemctl start openbao
sudo systemctl enable --now sysmanage-openbao-init
bao status        # Sealed: false

6. Start PostgreSQL, load the databases and check the schema

From the dump (restate 3.0.0.0 or later): the package left a new, empty cluster. Load every database into it. One error, role "postgres" already exists, is expected. The dump directory is readable by root alone, so let root expand the *, as sudo sh -c does:

sudo systemctl start postgresql
sudo sh -c 'cat /var/lib/restate/dumps/postgresql-*/pg_dumpall.sql' | sudo -u postgres psql -X -q -d postgres
sudo sysmanage-migrate --status

From the cluster's own files (an older restate): they came back in step 3, copied while PostgreSQL was stopped, so start it as it is and run sudo sysmanage-migrate --status. To move to another PostgreSQL major version instead, load that backup's dump into a new cluster: sudo sh -c 'zcat /var/lib/restate/dumps/postgresql-*/pg_dumpall.sql.gz' | sudo -u postgres psql -X -q -d postgres.

Every chain and every tenant should read up to date. If the backup was taken with an older SysManage than the one installed, run sudo sysmanage-migrate now.

7. Start SysManage and check it

sudo systemctl start sysmanage nginx

With a Professional+ license the first start takes about a minute, while the license is checked and the engines are downloaded again. Then check:

  • The agents reconnect on their own within a few minutes, without enrolling again: the Hosts list shows them active and nothing waits for approval.
  • Every tenant's hosts and data are there.
  • Settings -> Secrets reads every secret, which shows OpenBAO is whole.

Two things are expected afterwards. The backup run that took this snapshot shows as failed ("restate stopped before writing a result"), because the database was copied while that run was in progress; the snapshot itself is good. And within one scheduler pass (5 minutes) SysManage notices the server's new address and has the storage host export the repository to it, so Back up now works again.

Moving to a machine with a new address

Keep the host name and point its DNS record at the new address before step 7. A Let's Encrypt certificate restored in step 3 keeps its key, so the agents' pins still match, and one issued again later is accepted through the server's signed identity statement (see Agent Certificates and TLS). If the name itself must change, every agent's server setting must change too: do that before the old server is gone.

When only one piece is lost

OpenBAO alone. PostgreSQL and SysManage keep running. Stop OpenBAO (sudo systemctl stop openbao), restore only its directory, put init.json back from escrow as in step 4, then start it and unseal it (sudo systemctl start openbao && sudo systemctl restart sysmanage-openbao-init). In tests this took two seconds.

sudo restate restore --check-first --root / --include "/var/lib/openbao/**" KEY REPO::SNAPSHOT

One tenant's database alone, without touching the others. The dump holds every database, so restore it beside the live system, load it into a throwaway PostgreSQL cluster on another port, and copy the one database across. <version> is the PostgreSQL major version, and role "postgres" already exists is expected:

sudo install -d -m 0700 /srv/side
sudo restate restore --check-first --root /srv/side \
  --include "/var/lib/restate/dumps/postgresql-*/**" KEY REPO::SNAPSHOT

sudo install -d -o postgres -g postgres -m 0700 /srv/side-pg
sudo -u postgres /usr/lib/postgresql/<version>/bin/initdb -D /srv/side-pg -A trust
sudo -u postgres /usr/lib/postgresql/<version>/bin/pg_ctl -D /srv/side-pg \
  -o "-p 5499 -k /tmp -c listen_addresses=" -l /tmp/side-pg.log start
sudo sh -c 'cat /srv/side/var/lib/restate/dumps/postgresql-*/pg_dumpall.sql' \
  | sudo -u postgres psql -X -q -h /tmp -p 5499 -d postgres

Then copy the database across. Use the first command if the database is gone, the second if it is there but damaged:

sudo -u postgres pg_dump -h /tmp -p 5499 -Fc tenant_<slug> | sudo -u postgres pg_restore --create -d postgres
sudo -u postgres pg_dump -h /tmp -p 5499 -Fc tenant_<slug> | sudo -u postgres pg_restore --clean --if-exists -d tenant_<slug>

Finally stop the throwaway cluster, remove both directories, and check the schema with sudo sysmanage-migrate --status. In tests a tenant's database came back this way in 14 seconds while the other tenants kept working.

sudo -u postgres /usr/lib/postgresql/<version>/bin/pg_ctl -D /srv/side-pg stop -m fast
sudo rm -rf /srv/side /srv/side-pg

Backing up the server by hand

Use the rest of this page when the server cannot reach a backup target, or to keep a second copy made another way. It also lists where everything lives on each platform.

What to back up, most important first

  1. The agents' CA and the server identity -- /etc/sysmanage/certs/ (ca.crt, ca.key, server.crt, server.key), or the directory set by certificates.path. The CA signs every approved host's certificate. If it is missing, the server quietly creates a new one the next time it needs it.
  2. OpenBAO -- its data directory /var/lib/openbao/data, its key file /var/lib/openbao/init.json (unseal key and root token), its configuration /etc/openbao/openbao.hcl, and the server's token file /etc/sysmanage/openbao-token. OpenBAO holds the tenant database credentials, backup encryption keys, SSH keys and any server secrets that were moved out of sysmanage.yaml (the JWT secret, password salt, recovery password, database password and SMTP password).
  3. PostgreSQL -- the database named in the registry: block of /etc/sysmanage.yaml (normally sysmanage), which holds the control-plane registry, the shared reference data and, on a single-tenant server, all host data. With multi-tenancy on, also every tenant database. Back up the roles too (pg_dumpall --globals-only).
  4. /etc/sysmanage.yaml -- the database connection and password, the JWT secret, the password salt, the recovery account and the license key.
  5. The TLS certificate nginx serves -- /etc/sysmanage/tls/server.crt and server.key, or wherever your nginx site file points (for example /etc/letsencrypt/), and the nginx site file itself if you edited it.
  6. The license -- the key is license.key in /etc/sysmanage.yaml. The server also caches the license server's public key in /var/lib/sysmanage/license/public_key.pem; a connected server fetches it again, but an offline or air-gapped server needs the copy.
  7. Other keys in /var/lib/sysmanage -- the federation identity (federation/) and the air-gap collector keys (airgap/), when you use those features.
  8. Optional -- the Professional+ engines in /var/lib/sysmanage/modules are downloaded again with your license, and logs are not needed to recover. Leave both out unless the server is air-gapped, where engines come from the bundle you imported.

Keep the unseal key out of every backup

The key that unseals OpenBAO is kept on the server, in /var/lib/openbao/init.json (root only, mode 0600), never in /etc/sysmanage.yaml. Anyone who holds both that file and a copy of OpenBAO's data holds every secret. The built-in backup leaves it out; when you back up by hand, copy it separately into escrow, not into the same archive. Encrypt your backups, keep them off the server, and limit who can read them.

Where it lives on each platform

The commands on this page use the Ubuntu and Debian paths. The OpenBAO data directory and key file are the same on every Unix platform; the other paths differ as shown.

Platform Configuration TLS certificate and nginx site OpenBAO Services
Ubuntu, Debian /etc/sysmanage.yaml, /etc/sysmanage/ /etc/sysmanage/tls/, /etc/nginx/sites-available/sysmanage-nginx.conf /var/lib/openbao/, /etc/openbao/openbao.hcl sysmanage, openbao, sysmanage-openbao-init, nginx
RHEL family, openSUSE /etc/sysmanage.yaml, /etc/sysmanage/ /etc/sysmanage/tls/, /etc/nginx/conf.d/sysmanage-nginx.conf /var/lib/openbao/, /etc/openbao/openbao.hcl sysmanage, openbao, sysmanage-openbao-init, nginx
FreeBSD /etc/sysmanage.yaml, /usr/local/etc/sysmanage/ (including config.yaml), /etc/sysmanage/ /usr/local/etc/sysmanage/tls/, /usr/local/etc/nginx/sysmanage-nginx.conf /var/lib/openbao/, /usr/local/etc/openbao/openbao.hcl service sysmanage, service openbao (unseals when it starts), service nginx
macOS /etc/sysmanage.yaml, /etc/sysmanage/ /usr/local/etc/sysmanage/tls/, etc/nginx/servers/sysmanage-nginx.conf under the Homebrew prefix /var/lib/openbao/, /usr/local/etc/openbao/openbao.hcl launchd jobs com.sysmanage.server and com.sysmanage.openbao; nginx through brew services

Taking a backup by hand (Ubuntu and Debian)

Run these as root (sudo -i). The database dump does not need the server stopped. OpenBAO uses the file storage backend (storage "file" in openbao.hcl), which has no online snapshot: copy it with OpenBAO stopped. Stop SysManage first, so nothing asks OpenBAO for a secret while it is down. If you changed OpenBAO to the raft backend, use bao operator raft snapshot save instead of the copy.

1. Record the version and the tenant databases

mkdir -p /var/backups/sysmanage && chmod 700 /var/backups/sysmanage
cd /var/backups/sysmanage
dpkg-query -W sysmanage > package-version.txt

# Multi-tenancy only: every tenant database and the server that holds it
sudo -u postgres psql -d sysmanage -Atc \
  "SELECT t.slug, p.host, p.port, p.dbname
     FROM registry_tenant t
     JOIN registry_tenant_placement p ON p.tenant_id = t.id
    ORDER BY t.slug" > tenants.txt

2. Dump the databases

# Roles (the sysmanage owner and any roles OpenBAO created), then the bootstrap database
sudo -u postgres pg_dumpall --globals-only > globals.sql
sudo -u postgres pg_dump -Fc sysmanage > sysmanage.dump

# Multi-tenancy only: one dump per tenant database on this PostgreSQL server
# (remove from tenants.txt any whose host column names another server)
for db in $(cut -d'|' -f4 tenants.txt); do
  sudo -u postgres pg_dump -Fc "$db" > "tenant-$db.dump"
done

A tenant database on another PostgreSQL server (its host column) is dumped on that server the same way, with its own pg_dumpall --globals-only. A remote bootstrap database can be dumped from the SysManage server as its owner: pg_dump -h <host> -U sysmanage -Fc sysmanage > sysmanage.dump.

3. Copy OpenBAO with it stopped

systemctl stop sysmanage
systemctl stop openbao
tar -C /var/lib -czf openbao.tar.gz openbao
systemctl start openbao
systemctl restart sysmanage-openbao-init     # unseals OpenBAO again
systemctl start sysmanage

4. Copy the configuration, certificates and keys

tar -czf files.tar.gz -C / \
  --exclude=var/lib/sysmanage/modules \
  --exclude=var/lib/sysmanage/airgap-iso \
  --exclude=var/lib/sysmanage/airgap-staging \
  etc/sysmanage.yaml etc/sysmanage etc/openbao \
  etc/nginx/sites-available/sysmanage-nginx.conf \
  var/lib/sysmanage
# Add etc/letsencrypt if nginx serves a Let's Encrypt certificate

Then encrypt /var/backups/sysmanage and copy it to storage off this machine. Take the database dumps and the OpenBAO copy in the same run: OpenBAO creates database roles for tenants, so the two must describe the same moment.

With multi-tenancy on, the server can also run your own per-tenant backup tool on a schedule and record each tenant's recovery point: set backup.command (for example a pgBackRest command) in sysmanage.yaml. It runs the command you give it; it does not back up OpenBAO, the CA or the configuration.

Rebuilding from a backup taken by hand

  1. Install the same package version recorded in package-version.txt (for example apt install sysmanage=<version>), and the same or a newer major version of PostgreSQL. Do not create the sysmanage database by hand: the restore creates it. The new install creates its own configuration and its own empty OpenBAO; the next steps replace both.
  2. Stop everything SysManage runs: systemctl stop sysmanage openbao.
  3. Restore the databases: roles first, then the bootstrap database, then each tenant database.
cd /var/backups/sysmanage
sudo -u postgres psql -f globals.sql
sudo -u postgres pg_restore -C -d postgres sysmanage.dump
for f in tenant-*.dump; do sudo -u postgres pg_restore -C -d postgres "$f"; done
  1. Restore the configuration, certificates and keys over the fresh install, and put OpenBAO back as one piece: its data and its init.json only work together.
tar -C / -xzpf files.tar.gz
rm -rf /var/lib/openbao
tar -C /var/lib -xzpf openbao.tar.gz
chown root:openbao /var/lib/openbao && chmod 750 /var/lib/openbao
chown -R openbao:openbao /var/lib/openbao/data
chown root:root /var/lib/openbao/init.json && chmod 600 /var/lib/openbao/init.json
chown -R sysmanage:sysmanage /etc/sysmanage /var/lib/sysmanage
chown sysmanage:sysmanage /etc/sysmanage.yaml && chmod 640 /etc/sysmanage.yaml
  1. Start and unseal OpenBAO, and check that the unseal step succeeded.
systemctl start openbao
systemctl restart sysmanage-openbao-init
systemctl status sysmanage-openbao-init
  1. Check the schema: sudo sysmanage-migrate --status. With the same package version every chain and tenant reads up to date. If anything is PENDING, the backup is from an older release: run sudo sysmanage-migrate.
  2. Start the server: nginx -t && systemctl reload nginx, then systemctl start sysmanage.
  3. Point the agents' server name at the new machine. Each agent connects to server.hostname in its /etc/sysmanage-agent.yaml. If the new machine keeps that name, change the DNS record. If the name changes, every agent's configuration must change, and the TLS certificate must be valid for the new name.
  4. Verify: https://<server>/api/health and https://<server>/api/health/db answer healthy, you can sign in, and hosts turn active again as their agents reconnect.

Why agents reconnect without enrolling again

An agent proves which host it is with its host token, which it keeps locally and which the server stores in the host's database row. Restore the database and the token matches again, so the agent reconnects as the same host and needs no new approval. Hosts that were registered after the backup was taken are not in the restored database and come back as new hosts.

The agent also checks the server's TLS certificate: it must be valid for the name the agent uses, and its key must match what the agent pinned when it enrolled, which chains to the server's CA. Restore the CA with everything else. A server rebuilt with a new CA is refused by every agent, and the host certificates already issued no longer chain to it. See Agent Certificates and TLS.

Losing one piece, with a backup taken by hand

Only OpenBAO

Replace /var/lib/openbao as a whole from the last backup, data and init.json together, as in step 4 above, with sysmanage and openbao stopped. Then start openbao, restart sysmanage-openbao-init and start sysmanage. Secrets written after that backup are lost, for example the database credentials of a tenant created since then or a backup key created since then; recreate them. With no OpenBAO backup at all, its secrets cannot be recovered: the tenant databases still exist, but the server has no credentials to reach them.

Only one tenant database

Other tenants are not touched. Stop sysmanage so nothing holds a connection to that database, then restore it on the PostgreSQL server that holds it and bring it to the current schema:

sudo -u postgres dropdb --if-exists <dbname>
sudo -u postgres pg_restore -C -d postgres tenant-<dbname>.dump
sudo sysmanage-migrate --tenants-only
sudo sysmanage-migrate --status
systemctl start sysmanage

That tenant's hosts return to the moment of the dump; agents reconnect with their tokens as above. The per-tenant migration step leases credentials from OpenBAO, so OpenBAO must be running and unsealed.

Only the configuration or the certificates

Extract just that path from files.tar.gz, for example tar -C / -xzpf files.tar.gz etc/sysmanage.yaml, fix its owner as above and restart sysmanage (or reload nginx for the TLS certificate).

Test the restore

A backup you have not restored is a guess. At least once, and after every major upgrade, rebuild a test server from the backup alone on a separate machine, following this page with the production server out of the picture, and time it. Keep the production agents on production: give the test server a name of its own and point one test agent at it.
