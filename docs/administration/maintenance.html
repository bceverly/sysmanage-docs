Maintenance

Routine upkeep for a SysManage server: upgrades and database migrations, logs, database care, agent updates, and capacity.

Paths for a Linux package installation; other platforms use their own equivalents.

Upgrading the Server

  1. Read the release notes for the new version.
  2. Back up the database and /etc/sysmanage.yaml; see Backup & Recovery.
  3. Upgrade the package with your platform's package manager (for example apt, dnf, zypper, apk, pkg or pkg_add), or install the new MSI on Windows. The Debian and Ubuntu package stops the service for the upgrade and does not restart it.
  4. Apply the database migrations: sudo sysmanage-migrate --status shows what is pending, and sudo sysmanage-migrate applies it. On a multi-tenant server it migrates every tenant database too, which needs OpenBAO running. It is safe to run when nothing is pending. Some platforms' packages run the migrations for you.
  5. Restart the server: sudo systemctl restart sysmanage. Professional+ engines that were refused because the schema was out of date load only after this restart.
  6. Check that /api/health answers, that no migration banner is shown, and that agents reconnect.

From a source checkout, make migrate stops the server and runs the same sysmanage-migrate tool.

A single SysManage server is offline while it restarts; agents reconnect on their own and messages queued in the database are delivered afterward. Running several SysManage servers for failover is not supported yet. The database can be made highly available with an HA PostgreSQL cluster; see PostgreSQL High Availability.

Database migration banner

SysManage displays a yellow banner across the top of the UI when one or more Pro+ modules cannot load because the database schema is older than the module requires. The banner is a fallback safety net -- the normal upgrade procedure runs alembic upgrade head as part of installing a new release, and the banner only fires when that step was missed (e.g. when a Pro+ module is downloaded after an OSS upgrade but before migrations are applied).

When the banner appears

Each affected module is listed individually with the alembic revision it requires and (if a row was readable) the current revision the database is at. Modules that fail this check are not loaded; the corresponding UI features remain unavailable until migrations catch up.

What to do

  1. Stop sysmanage on the server.
  2. Run sudo sysmanage-migrate (from a source checkout, make migrate).
  3. Restart sysmanage.
  4. The banner clears once the affected modules successfully reload at the new schema revision.

A module refused at startup is only loaded when sysmanage starts again: running the migrations alone does not load it. If the migrations ran while sysmanage was running, the banner changes to "Restart SysManage to load Pro+ engines", and the features of those modules stay off until you restart sysmanage.

Programmatic check

The same data is exposed at GET /api/v1/license/module-compat; a non-empty incompatibilities array indicates pending migrations. Monitoring systems and pre-flight checks should poll this endpoint to detect schema drift before users see the banner.

Log Management

  • The server rotates backend.log at midnight, compresses the old file with gzip, and keeps 14 of them. No separate logrotate rule is needed.
  • Set the level with logging.level in /etc/sysmanage.yaml.
  • To also send logs to journald, syslog or the Windows Event Log, set logging.native: true. The nginx access and error logs are kept by nginx in its usual location.
  • See Logging Configuration for all options, including forwarding to a remote syslog server (Professional and Enterprise).

Database Upkeep

  • PostgreSQL's autovacuum is on by default and handles routine vacuuming and statistics. Leave it on; check that it keeps up on busy tables if the database grows quickly.
  • Take regular backups (for example with pg_dump) and test restoring them.
  • Messages between the server and agents pass through a queue table in the database. Expired messages are cleaned up automatically (message_queue.expiration_timeout_minutes, default 60, and message_queue.cleanup_interval_minutes, default 30).
  • Watch free disk space on the database host; package and inventory data grows with the number of hosts.

Agent Updates

  • Update agents through their native packages, or select hosts on the Hosts page and use Update Agent on Selected.
  • Update the server first, then agents. Try a new agent release on a few hosts before the rest.
  • Use maintenance windows to keep changes on production hosts to agreed times.

Capacity Planning

How many agents one server can handle depends on the number of worker processes, the hardware and the database. The measured figures, and how to size workers and the database connection pool, are in the Scaling Guide. Track the number of hosts, database size and server CPU and memory over time so you can plan ahead of growth.

Troubleshooting Procedures

# Service status and recent log lines
sudo systemctl status sysmanage
sudo tail -n 100 /var/log/sysmanage/backend.log

# Is the server answering?
curl -sS https://localhost/api/health -k

# Pending database migrations
sudo sysmanage-migrate --status

# Is PostgreSQL reachable?
sudo -u postgres psql -c "SELECT 1"
