Upgrading and Rolling Back

How to move a SysManage server to a new release, what each platform's package does on its own and what it leaves to you, how to update the agents, and what to do if the new release has to come off again.

Before you upgrade

  1. Read the release notes for every release between yours and the new one.
  2. Take a full backup -- databases, OpenBAO, configuration and certificates -- as described in Backing Up and Recovering the Server. It is your way back if a rollback is not enough.
  3. Check the current schema: sudo sysmanage-migrate --status should show nothing pending, so the upgrade's migrations are the only ones that run.
  4. Professional+: check the engines. GET /api/v1/license/module-compat lists engines that cannot load on this server (incompatibilities) and engine updates held back because they need a newer server (pending_updates). Held-back updates install after the server upgrade; the installed engine stays in use until then.
  5. Plan a short outage. A single server is offline while it restarts. Agents reconnect on their own and messages queued in the database are delivered afterward; see Scaling for how long a large fleet takes to reconnect.

Upgrading the package

The packages differ in whether they restart the server and whether they apply the database migrations. None of them loses your configuration.

Platform Upgrade command What the package does
Ubuntu, Debian sudo apt update && sudo apt install --only-upgrade sysmanage Stops the server for the upgrade and leaves it stopped. Does not migrate. Prints the two steps that remain: migrate, then restart.
RHEL family (Copr) sudo dnf upgrade sysmanage Restarts the server if it was running, without migrating. The new release then runs on the old schema until you migrate.
openSUSE sudo zypper refresh && sudo zypper update sysmanage Restarts the server after the update (the openSUSE default, unless DISABLE_RESTART_ON_UPDATE=yes is set in /etc/sysconfig/services), without migrating.
FreeBSD Install the new sysmanage-X.Y.Z.pkg as in Installation Removing the old version stops the server; the new one does not start it or migrate. Migrate with cd /usr/local/lib/sysmanage && doas -u sysmanage .venv/bin/python scripts/sysmanage_migrate.py, then service sysmanage start.
macOS brew upgrade --cask bceverly/tap/sysmanage Does not migrate or restart the server. Migrate with cd /usr/local/lib/sysmanage && sudo .venv/bin/python scripts/sysmanage_migrate.py, then sudo launchctl kickstart -k system/com.sysmanage.server.
Windows winget upgrade --id sysmanage.sysmanage --exact, or run the new MSI Applies the migrations and starts SysManageServer by itself. If the migration fails, the server still starts, shows the migration banner, and the failure is written to the install log and to the Application event log (source SysManage, event 1001) with the command to run again.

Applying the migrations and restarting

On Linux, after the package upgrade:

sudo sysmanage-migrate --status   # what is pending; changes nothing
sudo sysmanage-migrate            # apply it; safe to run again
sudo systemctl restart sysmanage
sudo systemctl status sysmanage

sysmanage-migrate runs the server's own migration tool as the sysmanage user against /etc/sysmanage.yaml: the registry, shared and tenant chains of the bootstrap database, then every tenant database. It only moves forward. --dry-run shows what would run, --no-tenants skips the tenant databases and --tenants-only runs only them.

Restart after migrating, even if the server was already running. A Professional+ engine that was refused at startup because the schema was too old loads only when the server starts again. If you migrated while the server was running, the yellow banner changes to "Restart SysManage to load Pro+ engines", and those engines' features stay off until you restart. See Maintenance for the banner.

Then check that /api/health and /api/health/db answer, that no migration banner is shown, and that hosts turn active as their agents reconnect.

Multi-tenant servers

  • The tenant step leases each tenant's database credentials from OpenBAO, so OpenBAO must be running and unsealed when you migrate.
  • Tenant databases are migrated one at a time, with a progress bar. A tenant that fails does not stop the others; the command reports how many failed and exits with an error.
  • Fix the cause, then run sudo sysmanage-migrate --tenants-only. --status lists every tenant with its revision and marks the ones still PENDING.
  • While the tenants are migrated, the running server serves migrated and unmigrated tenants side by side. Migrations are written for exactly this: a release only adds to the schema.

Updating the agents

The server has no minimum agent version. Each agent reports what it can do, and the server sends a host only the commands its agent supports; a host whose agent lacks a capability is shown as limited, and an older agent that reports nothing is never blocked. Mixed versions are therefore fine. New features need both a new server and a new agent, so upgrade the server first, then the agents at your own pace.

  • From the console: Update Agent on a host's page, or Update Agent on Selected in the Hosts list (needs the Update Agent role). This works for agents on Linux and FreeBSD.
  • With the package manager: Windows and macOS agents answer that self-update is not supported yet, and OpenBSD and NetBSD agents do not update themselves either. Update those with winget, Homebrew or the platform's package tools, or through your own software distribution. See Agent Installation.

Rolling back

sysmanage-migrate has no downgrade option, and rolling the schema back is not the way back: a downgrade drops what the upgrade added, data included. Instead, releases follow the expand-contract rule: a release only adds tables and columns, and removing anything waits for a later release. The previous release is designed to keep running against a database that one release has migrated. So to roll back, put the previous package back and leave the database as it is.

  1. Stop the server: sudo systemctl stop sysmanage.
  2. Install the previous version: sudo apt install sysmanage=<version>, sudo dnf downgrade sysmanage-<version> or sudo zypper install --oldpackage sysmanage-<version>. If the repository no longer offers it, install the package file you kept (apt keeps downloaded packages in /var/cache/apt/archives until they are cleaned). On Windows, macOS and FreeBSD, install the previous release's package from the releases page.
  3. Start the server and check /api/health, the banner and the agents, as after an upgrade.

Never remove the package to reinstall it

Removing the RHEL or openSUSE package (dnf remove, zypper remove), or purging the Debian package (apt purge), deletes /etc/sysmanage -- the agents' CA, the TLS certificate and the OpenBAO token -- and /var/lib/sysmanage. Downgrade in place as shown above.

Professional+ engines after a rollback. The previous release does not know the newest migration in the database, so an engine that declares a minimum schema revision can be refused, with a banner asking for migrations that cannot help. If engines you depend on stay refused, use the fallback below.

The fallback: restore the pre-upgrade backup. Install the previous package, then restore the databases and OpenBAO from the backup you took before upgrading, as in Backing Up and Recovering the Server. Everything that happened since that backup is lost, so this is the last resort, not the first.

On a multi-tenant server the same applies to every tenant database: rolling back the package leaves all of them migrated; restoring means restoring every tenant database from the same backup run.
