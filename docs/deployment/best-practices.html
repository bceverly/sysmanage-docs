Best-Practice Deployment Models

How to run SysManage in production: a public endpoint for agents beside a protected console, a hardened host, and a canary that watches the server from the outside.

A Server Reachable from the Internet

Agents and administrators need different things from the server. Agents must reach it from wherever they run; the console should be reachable by administrators only. Give them separate hostnames:

  • A public agent hostname (for example agents.example.com) that agents connect to. New agents enroll with enrollment tokens, so finding the hostname is not enough to register a host, and the server limits connection attempts per agent and per address.
  • A protected console hostname (for example console.example.com) that only administrators can reach: an IP allowlist, client certificates, or single sign-on through an identity provider that requires multi-factor sign-in (see External Identity Providers).

The Host

  • Ubuntu 24.04 LTS: a long-term-support release with five years of security updates, and the packages SysManage publishes for it.
  • A cloud firewall in front of UFW: the provider's firewall admits only HTTPS, and SSH from where you administer the server; UFW on the host does the same, so one mistake does not expose the server.
  • fail2ban on the login paths only: ban addresses that repeatedly fail to sign in to the console. Do not point it at the agent endpoints: a fleet behind one address reconnecting after an outage looks like an attack and would be locked out.
  • nginx is the only network listener: the SysManage server listens on the loopback address behind it.

Production Canary

Everything that alerts inside SysManage stops when the server, its database or its network is what failed. sysmanage-canary is a separate program that watches the server from the outside and emails when something stops working. It runs as its own service and user, with its own configuration and its own Python, never the server's virtual environment, so it keeps running when the server, its virtual environment or its database is broken. Run it on the server, or better, on another machine.

Installing It

The canary is its own package, so it can go on a machine that runs no SysManage server: sysmanage-canary for Debian and Ubuntu, the sysmanage-canary subpackage of the RPMs, the sysutils/sysmanage-canary FreeBSD port, and the sysmanage-canary macOS package and Windows MSI (x64 and ARM64) on the release page. The FreeBSD, OpenBSD and NetBSD server packages include it. On macOS the package gives the canary a private Python environment, and on Windows the MSI carries its own Python, so neither shares anything with the server.

What It Watches

  • web_ui: the console URL answers, over a TLS handshake that verifies, within max_response_ms.
  • backend: /api/health answers within its limit.
  • database: connects, runs SELECT 1 within its limit, and compares the connections in use with PostgreSQL's max_connections (alerting above max_connections_percent). Give it its own read-only role.
  • network: every name under resolve resolves and every host:port under connect accepts a connection, for example the license server and your package mirrors.
  • inbound_silence: an agent has reported within max_silence_minutes, read from the database, so a dead listener, a broken firewall rule or a lapsed DNS record is noticed even when every local check passes. With multi-tenancy, list each tenant database under extra_dsns.

The Configuration File

/etc/sysmanage-canary.yaml (FreeBSD and macOS /usr/local/etc/, NetBSD /usr/pkg/etc/, Windows C:\ProgramData\SysManage\), owned by the canary user with mode 0600 (on Windows, readable only by SYSTEM, Administrators and the service), because it holds passwords. The package installs it from a commented example. Every check has enabled, interval_seconds, timeout_seconds and failures_before_alert; the example explains the rest. A file with any problem is refused as a whole, with every problem listed.

Alerts

One email when a check has failed failures_before_alert times in a row, a reminder every email.reminder_minutes while it stays down, and one when it recovers; never one per check. Emails are written in the configured language.

Who watches the canary: set heartbeat.url to a dead-man's-switch service (healthchecks.io and similar), which alerts you when the canary's pings stop, and heartbeat.daily_email_hour for a daily email with the state of every check.

Sending Through Gmail

  1. Turn on 2-Step Verification for the Google account that will send the alerts.
  2. Create an App Password (Google account, Security, App passwords) and copy it.
  3. Set email.host to smtp.gmail.com, port to 587, security to starttls, username and from to the address, and password to the App Password.

Testing It

As the canary user, sysmanage-canary --check-config validates the file, sysmanage-canary --test-email sends a test message, and sysmanage-canary --once runs every enabled check once and prints the results (on Windows the command is sysmanage-canary.cmd in the install folder, run as an administrator). Then enable the service: systemctl enable --now sysmanage-canary (FreeBSD sysrc sysmanage_canary_enable=YES, OpenBSD rcctl enable sysmanage_canary, NetBSD sysmanage_canary=YES in /etc/rc.conf, macOS sudo launchctl bootstrap system /Library/LaunchDaemons/org.sysmanage.canary.plist, Windows Set-Service SysManageCanary -StartupType Automatic then Start-Service SysManageCanary).
