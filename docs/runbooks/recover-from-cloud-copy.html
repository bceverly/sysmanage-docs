Recover From the Cloud Copy

The cloud copy is the backup of last resort: the storage host's backups, encrypted, in your own Amazon S3 bucket. This runbook prepares for the day it is needed, then brings the backups back -- from the Backups page while SysManage is running, or by hand when the server, the storage host and everything else at the site are gone.

When to use it

  • Now, before anything is wrong: part A. A copy whose keys exist only on the server it protects cannot be read once that server is gone.
  • The storage pool is lost but SysManage is running: part B.
  • The SysManage server is gone too: part C, with only the export file and your OpenPGP private key.

What you need

  • Professional+ to set up the copy and keep it uploading. Restoring, Check the bucket and Export keys work in every edition, also after a license lapses.
  • A storage host on ZFS, on Linux or FreeBSD, and an Amazon S3 bucket in your own AWS account. See Cloud copy: S3 Glacier Deep Archive for how the copy works.
  • An OpenPGP key pair of your own. Its public key is saved in SysManage as the break-glass escrow key; its private key never is.
  • Time: S3 Glacier Deep Archive takes up to 12 hours (Standard) or 48 hours (Bulk) to thaw before anything can be downloaded. Plan the recovery around that.

Part A: before anything goes wrong

A1. Set up the copy

On the Backups page, find the Cloud copy (off-site) card and choose Set up the cloud copy. Enter the bucket, its region and the upload access key; keep the other defaults. Then open Bucket setup and apply what it shows in AWS: the bucket with Object Lock, its lifecycle rules and an IAM user that can upload, read and thaw but never delete. Finally choose Check the bucket.

Expect: the card shows Object Lock on. If it says Object Lock OFF, the bucket was made without Object Lock and a stolen credential could overwrite the copy: make a new bucket with it on.

A2. Let the first full copy finish

The first upload is a full copy of every dataset and can take days for a large pool, at the bandwidth cap during working hours. Choose Run now to start it instead of waiting for 02:00 UTC. The card shows each dataset's progress; an upload that is interrupted resumes from the parts already in the bucket.

Expect: the card says how much is stored, with the last good upload and the next one, and an estimate of the monthly cost.

A3. Export the keys and keep them off the site

  1. On the card, choose Export keys. Leave OpenPGP public key empty to seal the export to the saved escrow key, or paste another public key you hold the private half of.
  2. Under Why you are exporting them, write a reason of at least 10 characters, such as "Break-glass copy for the password vault". It goes into the audit log.
  3. Choose Export and download. The browser saves a file named like sysmanage-offsite-keys-20261127T122641Z.tar.asc. It is encrypted to your key, so the server never sees it readable and the download can sit in your downloads folder until you move it.
  4. On the machine that holds your private key, prove it opens, without writing anything readable to disk:
gpg --decrypt sysmanage-offsite-keys-20261127T122641Z.tar.asc | tar -tvf -

Expect: README.txt, copy.json, credentials.json, streams.json, smoc_decrypt.py, keys/index.json and one keys/<key id>.key per key the copy has held.

  1. Attach the .tar.asc file, as it is, to an entry in your password vault, and note the date and the key id the card shows. Keep it sealed: the vault protects it once, the OpenPGP seal a second time.
  2. Make sure your OpenPGP private key is kept somewhere that does not depend on the site either: a hardware token, or an encrypted copy in the same vault under a separate entry, with its passphrase known to someone who can act without you.
  3. Delete the downloaded file from the machine you exported it on.

Export again after every New key. An earlier export does not hold a key made after it, and what is uploaded under that key cannot be read without it. The card says so when you press New key.

A4. Prove a restore

A copy that has never been restored is a hope, not a backup. Once a year, and after any change to the storage host, run part B for one small dataset into a new dataset, compare a few files with the originals, and destroy the restored dataset afterwards. A Standard thaw of a small dataset costs cents.

Part B: restore with SysManage

  1. On the Backups page, on the Cloud copy (off-site) card, choose Restore in its row of buttons. It needs the Restore Files role.
  2. Under Restore point, choose the dataset and when to go back to; each entry reads dataset@snapshot, and the snapshot's name is its time in UTC. Under Thaw speed, choose Bulk (cheapest, up to 48 hours) or Standard (up to 12 hours). The dialog shows the time and the cost before anything starts.
  3. New dataset to restore into is filled in as the dataset's name with -restored added; change it if you like, to any dataset that does not exist yet. A restore never writes over an existing dataset.
  4. Choose Thaw and restore. The card shows Thawing: 0 of N parts ready, then how much has been downloaded and received. You can close the browser; the storage host does the work.

Expect: the card's last job reads Restore done, and zfs list on the storage host shows the new dataset. It holds the restate repository as it was at that point; restore files from it as from any repository (see Fleet Backups).

Part C: restore by hand, without SysManage

Use this when there is no SysManage server to restore through. You need a machine with ZFS (any Linux or FreeBSD machine with a pool), the AWS command line (aws), Python 3 with its cryptography package, gpg and your private key. Work as a user that may run zfs receive; the commands below use sudo for it.

C1. Open the export

mkdir -m 700 ~/cloudcopy && cd ~/cloudcopy
gpg --decrypt /path/to/sysmanage-offsite-keys-20261127T122641Z.tar.asc | tar -xf -
cat copy.json
export AWS_ACCESS_KEY_ID=$(python3 -c 'import json; print(json.load(open("credentials.json"))["access_key"])')
export AWS_SECRET_ACCESS_KEY=$(python3 -c 'import json; print(json.load(open("credentials.json"))["secret_key"])')
export AWS_DEFAULT_REGION=$(python3 -c 'import json; print(json.load(open("copy.json"))["region"])')
B=$(python3 -c 'import json; print(json.load(open("copy.json"))["bucket"])')
P=$(python3 -c 'import json; print(json.load(open("copy.json"))["prefix"] or "")')

The credentials are the copy's own upload key, which can list, read and thaw under the copy's prefix but delete nothing. If it has been deactivated since, use another key of yours with the same rights. If the copy uses an S3-compatible store rather than AWS, add --endpoint-url with the endpoint from copy.json to every aws command.

C2. Read the manifests

streams.json lists what was in the bucket when you exported. Uploads made since are described by the manifests in the bucket, which are kept in S3 Standard and need no thaw. Download and decrypt them all:

mkdir -p manifests
aws s3api list-objects-v2 --bucket "$B" --prefix "${P:+$P/}m" --query 'Contents[].Key' --output text \
  | tr '\t' '\n' | grep . | while read -r key; do
    out="manifests/$(echo "$key" | tr '/' '_')"
    aws s3api get-object --bucket "$B" --key "$key" "$out.smoc" >/dev/null
    for k in keys/*.key; do
        python3 smoc_decrypt.py "$k" "$out.smoc" > "$out.json" 2>/dev/null && break
    done
done
ls manifests/*.json | wc -l

A manifest that none of the keys opens was written under a key made after this export; its .json file is left empty, and the streams it describes cannot be read with this export. Restore to an older point instead.

C3. Work out the chain for a dataset

A restore point is a full copy plus each incremental after it, in order. Save this as chain.py; it prints, for one dataset, every part to fetch, as a tab-separated list of the stream's number, its key id, the part's object key and its SHA-256:

import glob, json, sys

dataset = sys.argv[1]
streams = {}
for name in glob.glob("manifests/*.json"):
    try:
        found = json.load(open(name))
    except ValueError:
        continue  # a manifest under a newer key
    if found.get("dataset") == dataset:
        streams[found["snapshot"]] = found
for found in json.load(open("streams.json")):
    if found["dataset"] == dataset:
        streams.setdefault(found["snapshot"], found)
if not streams:
    sys.exit("nothing stored for " + dataset)
point = sys.argv[2] if len(sys.argv) > 2 else max(streams)
chain = []
while point in streams:
    chain.append(streams[point])
    if streams[point]["kind"] == "full":
        break
    point = streams[point]["base_snapshot"]
if not chain or chain[-1]["kind"] != "full":
    sys.exit("no full copy under " + str(point) + "; choose an older point")
for number, stream in enumerate(reversed(chain)):
    for part in sorted(stream["parts"], key=lambda p: p["index"]):
        print(number, stream["key_id"], part["key"], part["sha256"], sep="\t")
python3 -c 'import glob,json; print("\n".join(sorted({s["dataset"] for s in json.load(open("streams.json"))} | {json.load(open(f))["dataset"] for f in glob.glob("manifests/*.json") if open(f).read().strip()})))'   # the datasets stored
python3 chain.py zfs-pool/backups/restate/hosta > chain.tsv
cut -f1 chain.tsv | uniq -c   # parts per stream: the full first

Without a second argument the newest point is used. To go back further, for example to before a ransomware attack, give a snapshot name such as sysmanage-offsite-20261120T020000Z as the second argument.

C4. Thaw the parts

cut -f3 chain.tsv | while read -r key; do
    aws s3api restore-object --bucket "$B" --key "$key" \
      --restore-request '{"Days":7,"GlacierJobParameters":{"Tier":"Bulk"}}'
done

Use "Tier":"Standard" instead of Bulk for up to 12 hours rather than 48, at a higher price. The thawed copies stay readable for 7 days. Check on them every few hours; every line reads ongoing-request="false" when all are ready:

cut -f3 chain.tsv | while read -r key; do
    aws s3api head-object --bucket "$B" --key "$key" --query Restore --output text
done | sort | uniq -c

C5. Download, check, decrypt and receive

Each stream is received in turn into one new dataset: the full creates it, and each incremental adds the next snapshot. Every part's SHA-256 is checked before it is decrypted, and decryption itself fails on any change, so a damaged or altered part stops the restore instead of being received.

TARGET=tank/restored-hosta   # must not exist yet
rm -f failed
for n in $(cut -f1 chain.tsv | sort -nu); do
    awk -F'\t' -v n="$n" '$1 == n' chain.tsv | while IFS="$(printf '\t')" read -r _ kid key sum; do
        aws s3api get-object --bucket "$B" --key "$key" part >/dev/null || { touch failed; exit 1; }
        [ "$(openssl dgst -sha256 -r part | cut -d' ' -f1)" = "$sum" ] || { echo "bad part $key" >&2; touch failed; exit 1; }
        python3 smoc_decrypt.py "keys/$kid.key" part || { touch failed; exit 1; }
    done | sudo zfs receive -u "$TARGET" || touch failed
    [ -e failed ] && { echo "stream $n failed: stopped" >&2; break; }
done
rm -f part
zfs list -t snapshot -r "$TARGET"

Expect: one snapshot per stream, the last named after the point you chose. The dataset holds the restate repository as it was; mount it (sudo zfs mount) and restore from it with restate, using the repository's own key from your backup key export.

C6. Clean up

Remove ~/cloudcopy once the restore is done: it holds the readable keys and credentials. The thawed copies expire by themselves after the days you asked for; the copy in Deep Archive is untouched.

If something goes wrong

  • "this object needs the key ..." The part was uploaded under a key this export does not hold. Use a newer export, or restore to an older point.
  • InvalidObjectState on download: the part has not finished thawing, or its thawed copy has expired. Check with head-object and thaw it again if needed.
  • AccessDenied: the access key is deactivated or lacks the read and thaw rights; use another key of yours with s3:GetObject, s3:RestoreObject and s3:ListBucket on the bucket.
  • zfs receive fails on an incremental: the dataset was changed after the full was received. Destroy it and start C5 again; the parts already downloaded are fetched again, but the thaw is not repeated while it lasts.
