Replace a Failed Server

The SysManage server is gone -- a dead disk, a lost virtual machine, a data center you are leaving. This runbook brings up a replacement, moves the agents to it, and checks that every host came back without being enrolled again.

When to use it

Use it when the server cannot be repaired in place, or when you move it to new hardware on purpose. For a planned move, take a fresh backup just before you start, so nothing is lost between the backup and the cut-over.

What you need

  • Any edition: the server backup, the restore and the cut-over are all Community.
  • A backup of the old server taken as described in Backing Up and Recovering the SysManage Server: the databases, OpenBAO, /etc/sysmanage.yaml, and the certificates and keys.
  • A new machine with the same operating system family, and the same SysManage version as the backup.
  • Control of the DNS name the agents use, or, if they use an IP address, a way to change every agent's configuration.

How the agents find the server

Each agent reads one setting, server.url in its configuration file, when it starts. It connects out to that address on port 443 and identifies itself with the host token it received when it first registered, which it keeps in its local database. Three things decide whether a replacement server just works for an agent:

  • The name. If url holds a DNS name and you move that name to the new machine, the agent needs no change. If it holds an IP address and the new machine has another one, every agent's file must be edited.
  • The certificate. The new server must present a certificate for that name, from a CA the agent trusts. Restoring the old certificate and key from the backup is the simplest.
  • The database. A restored database still holds each host and its token, so the agent is recognized and carries on. On an empty database the server has never heard of the host: the agent registers again and the host waits for approval as a new one.

1. Lower the DNS time-to-live (planned moves)

A day before a planned move, lower the time-to-live of the server's DNS record to a few minutes, so agents and browsers pick up the new address quickly. After a failure there is no time for this; the agents still follow as their resolvers' caches expire.

2. Restore the server

On the new machine, follow the section on rebuilding the server on a new machine in Backing Up and Recovering the SysManage Server: install the same server version, restore the configuration, the certificates, OpenBAO and the databases, run the migrations, and start the services. Check it locally before any agent is pointed at it:

curl --resolve sysmanage.example.com:443:127.0.0.1 https://sysmanage.example.com/api/health/db

Expect: {"status":"healthy","database":"up"}, without a certificate error. Sign in to the web interface the same way and check that the hosts are listed; they show Down until their agents reconnect.

If the old server is still running in any form, stop it now (sudo systemctl stop sysmanage nginx). Two servers answering for the same name split the fleet between them.

3. Move the name or the address

  • Agents use a DNS name: point the record at the new machine's address. Nothing changes on the agents.
  • Agents use an IP address: either give the new machine the old address, or change url on every agent and restart it. Use the same configuration-management tool you installed the agents with; on Linux and FreeBSD:
# Linux
sudo sed -i 's|url: "https://192.0.2.10"|url: "https://sysmanage.example.com"|' /etc/sysmanage-agent.yaml
sudo systemctl restart sysmanage-agent

# FreeBSD
sed -i '' 's|url: "https://192.0.2.10"|url: "https://sysmanage.example.com"|' /usr/local/etc/sysmanage-agent/config.yaml
service sysmanage_agent restart

While you are touching every agent anyway, switch them to a DNS name: the next move then needs only a DNS change. The certificate must cover whichever name or address url holds.

4. What the agents do

  • While the server is unreachable, each agent keeps retrying, waiting a little longer after each failure, up to five minutes between attempts, with random spread so the fleet does not return all at once. It never gives up.
  • What the agent could not send while disconnected stays in its local queue and is sent after it reconnects. Commands it had already received keep running.
  • Each attempt looks the name up again, so a DNS change is picked up without restarting the agent. A change to the agent's configuration file is read only when the agent restarts.
  • On a restored database, the agent presents its host token, the server recognizes it, and the host is Up again with its history, tags and approval intact.

5. Confirm it worked

  • On Fleet > Hosts, every host is Up within about five minutes of the cut-over, and none shows Approval Needed.
  • Compare the numbers with the old server's last known count: GET /api/v1/hosts/summary returns total, approved_up and approved_down (see API Examples).
  • On a sample of hosts, the agent log has a new "Connected to server successfully" line.
  • Commands you queued on the old server after the last backup are not on the new one. Check recent work -- updates, installations, scripts -- and send again what is missing.

If a step fails

What you seeWhat to do
Hosts reappear as Approval NeededThe server does not know them: the database was not restored, or the backup is older than those hosts. Approve them; on an empty database, reapply their tags too.
The agent log says certificate verify failedThe new server's certificate is not one the agent trusts, or does not cover the name in url. Restore the old certificate, or follow Renew the Server Certificate.
Some hosts stay Down for more than ten minutesThey still resolve the old address (a cached record or an entry in /etc/hosts), or their url holds an IP address. Check with curl https://sysmanage.example.com/api/health from the host.
The server log shows a refused agent session with host_credential_required or host_credential_invalidThe agent lost its local database (for example the host was reinstalled) while the server still has the host. Delete the host on Fleet > Hosts and let the agent register again, then approve it.
Some hosts talk to the old server, some to the new oneThe old server is still answering. Stop it, then restart the agents that are still connected to it.
