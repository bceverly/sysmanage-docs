Renew the Server Certificate

The server's TLS certificate protects the web interface, the API and every agent connection, all on port 443. This runbook renews it, or replaces it with one from a different certificate authority, without losing the agents.

When to use it

  • The certificate is close to expiry and does not renew by itself.
  • You are moving to a different certificate authority, for example from a self-signed evaluation certificate to your company's CA or Let's Encrypt.
  • The server gets a new name, which the certificate must cover.
  • The private key may have been exposed.

What you need

  • Any edition: this is all Community.
  • Root access to the server, and to the agents if their trusted CA changes.
  • The new certificate (with its intermediate certificates) and its private key, or certbot set up to obtain one.

Where the certificate lives

Only nginx presents the certificate; the SysManage server behind it listens on loopback port 8080 and never sees it. The package's nginx site (on Ubuntu, /etc/nginx/sites-available/sysmanage-nginx.conf) reads:

ssl_certificate     /etc/sysmanage/tls/server.crt;
ssl_certificate_key /etc/sysmanage/tls/server.key;

If you followed the Let's Encrypt steps in the server installation guide, these two lines point at /etc/letsencrypt/live/<name>/fullchain.pem and privkey.pem instead. Check what yours says, and when the certificate expires:

sudo grep -E 'ssl_certificate(_key)?\s' /etc/nginx/sites-available/sysmanage-nginx.conf
echo | openssl s_client -connect sysmanage.example.com:443 -servername sysmanage.example.com 2>/dev/null |
  openssl x509 -noout -subject -issuer -enddate -ext subjectAltName

A. Let's Encrypt with certbot

certbot renews by itself, about a month before expiry, with the hooks you gave it the first time: with the HTTP challenge it stops nginx for a few seconds and starts it again; with a DNS challenge and --deploy-hook "systemctl reload nginx", nginx keeps running. Check that renewal works:

sudo certbot renew --dry-run

If nginx reads copies in /etc/sysmanage/tls/ rather than the files in /etc/letsencrypt/live/, a renewal changes nothing nginx sees. Either point the two nginx lines at the live files, or add a deploy hook that copies them after each renewal. certbot runs every executable file in this directory after a successful renewal; --dry-run does not run it.

sudo tee /etc/letsencrypt/renewal-hooks/deploy/sysmanage.sh >/dev/null <<'EOF'
#!/bin/sh
install -m 644 "$RENEWED_LINEAGE/fullchain.pem" /etc/sysmanage/tls/server.crt
install -m 600 "$RENEWED_LINEAGE/privkey.pem"   /etc/sysmanage/tls/server.key
nginx -t && systemctl reload nginx
EOF
sudo chmod 755 /etc/letsencrypt/renewal-hooks/deploy/sysmanage.sh

Agents trust Let's Encrypt through their operating system's trust store, so they need nothing.

B. A certificate from your own or a commercial CA

  1. If the issuing CA changes, tell the agents first. An agent with ca_bundle in its configuration trusts only the CA in that file. Put the old and the new CA certificates in the file, one after the other, on every such agent before you swap the server's certificate. The agent reads the file again on each new connection; restarting the agent applies it at once. Agents without ca_bundle use the operating system's trust store, so add a private CA there instead.
  2. Check the new certificate. Its subjectAltName must include the name (or address) in the agents' server.url, and the key must match it -- these two commands print the same value:
openssl x509 -in new.crt -noout -ext subjectAltName -enddate
openssl x509 -in new.crt -noout -pubkey | openssl sha256
openssl pkey -in new.key -pubout | openssl sha256
  1. Install it and reload nginx. Put the server certificate first in server.crt, followed by any intermediate certificates. Keep the old files until the new ones are proven.
sudo cp -p /etc/sysmanage/tls/server.crt /etc/sysmanage/tls/server.crt.old
sudo cp -p /etc/sysmanage/tls/server.key /etc/sysmanage/tls/server.key.old
cat new.crt intermediate.crt | sudo tee /etc/sysmanage/tls/server.crt >/dev/null
sudo install -m 600 new.key /etc/sysmanage/tls/server.key
sudo nginx -t && sudo systemctl reload nginx
  1. When every agent is back (see below), remove the old CA from the agents' ca_bundle files, and delete the .old files.

What the agents do during the swap

  • A reload keeps nginx running: connections already open stay on the old certificate until they close, and new connections get the new one. With certbot's HTTP challenge, nginx stops for a few seconds and the agents reconnect.
  • An agent that loses its connection keeps trying, waiting a little longer each time, up to five minutes between attempts. It never gives up, so it comes back by itself once it trusts the certificate.
  • An agent that does not trust the new certificate logs certificate verify failed and keeps retrying. Fix its ca_bundle (step B1); there is nothing to re-enroll.
  • A host that has not checked in for five minutes shows Down. Commands sent to it meanwhile wait on the server and are delivered when it reconnects.
  • Agents pin the server, and a new certificate does not break the pin. An agent that sees a new key accepts it once the server's signed identity statement names that key. The server reads the keys nginx serves on this machine and checks again every ten minutes, so agents come back on their own within about ten minutes of the reload. If nginx runs on another machine, add the new key's SHA-256 SPKI hash to agent_tls_spki in Settings, beside the old one, before you reload it. See Agent Certificates and TLS.

Agent certificates

Each approved host has a client certificate of its own, for a key it generated itself, issued by SysManage's own certificate authority. The agents renew them on their own, 30 days before they expire, so this runbook does not touch them. Renewing or replacing the server's TLS certificate does not change that certificate authority. See Agent Certificates and TLS.

How to confirm it worked

  • The openssl s_client command above shows the new issuer and expiry date.
  • The web interface opens without a certificate warning.
  • Within five minutes, every host on Fleet > Hosts is Up. On a host, the agent log has a new "Connected to server successfully" line.

If a step fails

What you seeWhat to do
nginx -t fails with "key values mismatch"The key does not belong to the certificate. Compare the two sha256 values from step B2. nginx keeps serving the old certificate until a reload succeeds.
Agents stay Down and log certificate verify failedThey do not trust the new CA, or server.crt lacks the intermediate certificates. Fix the bundle on the agents, or put the old files back and reload nginx while you do.
The agent log says server.ca_bundle points at a file that does not existThe agent will not fall back to the system trust store when ca_bundle is set. Fix the path, or remove the setting.
Hostname mismatch errorsThe certificate does not cover the name in the agents' server.url. Reissue it with that name in its subjectAltName.
