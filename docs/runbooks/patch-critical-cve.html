Patch a Critical Vulnerability Across the Fleet

A critical vulnerability has been published for a package you run. This runbook finds every host that has it, decides when the fix may run, applies it, proves it is gone, and leaves a record of who did what.

When to use it

Use it when a vendor or a security notice names a package and a fixed version, and you need the fixed version on every affected host -- today, or in the next maintenance window.

What you need

  • Community is enough for every step. You find the exposed hosts by package name under Patching > Updates instead of by vulnerability ID.
  • Professional adds Security > Vulnerabilities, which finds the hosts by vulnerability ID and shows the fixed version.
  • A user with the Apply Software Update role to apply updates, View Audit Log to read the record, and an administrator account to create maintenance windows and emergency overrides. The recovery account from sysmanage.yaml is not enough: sign in as a user created in SysManage.

What SysManage can apply depends on the host's operating system:

Operating systemUpdates
LinuxApplied on Debian, Ubuntu, RHEL and Fedora families; detected but not yet applied on openSUSE and Arch; not on Alpine.
WindowsDetected and applied.
macOSHomebrew updates applied; MacPorts and App Store updates detected only.
FreeBSDDetected and applied.
OpenBSDsyspatch and sysupgrade; third-party package updates not detected.
NetBSDpkgin updates detected but not yet applied.

Where an update is detected but not applied, SysManage still shows you the exposed hosts; patch those by hand or with a script from Automation > Scripts (Community).

1. Find the exposed hosts

By vulnerability ID (Professional)

Open Security > Vulnerabilities. Every host is listed with its Critical, High, Medium and Low counts and its Last Scanned time. Sort by Critical, choose View on a host, and type the vulnerability ID (for example CVE-2026-12345) in Search vulnerabilities. The row shows the Package, the Installed Version and the Fixed Version. If the host was scanned before the vulnerability was published, choose Run Scan first.

On Linux, vendor data covers Ubuntu, Debian and Red Hat; other distributions are matched against the National Vulnerability Database only. On OpenBSD the base system is covered, from OpenBSD errata.

By package name (Community)

Open Patching > Updates, tick Security Updates Only, and type the package name in Search for package updates.... Each row is one host that has an update waiting for that package, with its current and available versions. On Fleet > Hosts, a red SW Updates chip in the Status column marks every host with security updates waiting.

The search box filters the page of results shown (50 rows). With more rows than that, narrow the list first with the package manager selector or All Affected Hosts, or ask the API for the whole list:

curl -s -H "Authorization: Bearer $SYSMANAGE_API_KEY" \
  "https://sysmanage.example.com/api/v1/updates/?security_only=true&limit=100000" |
  jq -r '.updates[] | select(.package_name == "openssl")
         | [.hostname, .current_version, .available_version, .package_manager] | @tsv'

Creating the API key is described in API Examples.

2. Decide when the fix may run

Maintenance windows (Community) decide when changes reach a host. A host with no window is unrestricted: the update starts as soon as you apply it. A host inside an Allow window, and outside any Blackout, receives it at once. Any other host holds the update until its next window opens; nothing is dropped. While it waits, the host's Status column shows Held: 1.

To patch in waves, give each wave a tag (Administration > Settings > Tags > Add Tag, then Add Tag on each host's Info tab), and give each tag its own window: Patching > Maintenance Windows > Schedule Maintenance, Kind Allow, Recurrence One-time, the Starts at (UTC) and Ends at (UTC) of that wave, and Applies to Hosts by tag. Then apply the update to every host in step 3: each wave runs when its own window opens. Enterprise rolling deployments do not include a package-update operation, so windows are the way to stage a patch.

In an emergency, an administrator can let changes through now. On the host's page, open the Info tab and choose Emergency override on the Maintenance Window card; give a Reason and a Duration (minutes). The host's held commands are released at once and the override is written to the audit log. For a command that is already waiting, the Held commands list on Patching > Maintenance Windows has Release host now. The same override through the API:

curl -s -X POST -H "Authorization: Bearer $SYSMANAGE_API_KEY" -H "Content-Type: application/json" \
  -d '{"host_id": "HOST-ID", "reason": "CVE-2026-12345 emergency patch", "duration_minutes": 120}' \
  https://sysmanage.example.com/api/v1/maintenance-windows/overrides

3. Apply the update

  • Across the fleet: on Patching > Updates, with Security Updates Only ticked and the package name in the search box, tick Select All, then choose Execute Selected Updates. Select All covers the page shown; repeat for each page.
  • On one host: open the host's page and choose Updates. Patching > Updates opens filtered to that host; tick the package and choose Execute Selected Updates.
  • Through the API, for any number of hosts at once. host_ids and package_names are required; package_managers is optional.
curl -s -X POST -H "Authorization: Bearer $SYSMANAGE_API_KEY" -H "Content-Type: application/json" \
  -d '{"host_ids": ["HOST-ID-1", "HOST-ID-2"], "package_names": ["openssl"]}' \
  https://sysmanage.example.com/api/v1/updates/execute | jq '.results[]'

Each result names the host and says "success": true with "Update execution started", or false with the reason. Rows on Patching > Updates show Update Requested until the agent reports back. If the update needs a restart, the host's Status column shows Reboot Required; select those hosts on Fleet > Hosts and choose Reboot Selected (this needs a privileged agent, and maintenance windows hold reboots too).

4. Confirm it worked

  • After applying, the agent sends a fresh list of available updates. Repeat the search of step 1 on Patching > Updates: it should say No updates match the current filters, and the hosts' red SW Updates chips should be gone.
  • Professional: on each host's vulnerability page choose Run Scan; the vulnerability ID should no longer be found.
  • On any host, the Software tab shows the installed version of the package.
  • To check the whole fleet at once, list the hosts that still report security updates:
curl -s -H "Authorization: Bearer $SYSMANAGE_API_KEY" https://sysmanage.example.com/api/v1/hosts |
  jq -r '.[] | select(.security_updates_count > 0) | [.fqdn, .security_updates_count] | @tsv'

5. Record it

Open Security > Audit Log (on servers before 3.12.1.7, open https://<server>/reports/audit-log directly; the audit log itself is Community). Search for the package name: there is one entry per package per host, "Initiated update of package ... from ... to ... on host ...", with who did it and when. Emergency overrides appear as "Emergency maintenance override for host ...". To keep a copy outside SysManage, see API Examples.

If a step fails

What you seeWhat to do
There is no Execute Selected Updates buttonYour user lacks the Apply Software Update role. An administrator grants it under Administration > Users.
The host shows Held: 1 and the update does not startA maintenance window is holding it. Wait for the window, or use the emergency override in step 2.
The API answers "No matching updates found for specified packages"That host does not report an update for that package: it is already fixed, or its list is out of date. Select the host on Fleet > Hosts and choose Refresh All Data, then look again.
The row stays at Update RequestedIf the host shows Down, the command waits on the server and is delivered when the agent reconnects. If the host is Up, check that its operating system can apply updates (the table above).
The row shows Update FailedThe package manager refused it. Read the agent log on the host (/var/log/sysmanage-agent/agent.log on Linux and the BSDs) for the package manager's error, fix the cause, and apply again.
Emergency override answers "Permission denied: administrator required"Overrides and windows need an administrator account. Ask one to create the override.
